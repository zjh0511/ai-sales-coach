## 2. 核心設計概念（換平台也不該丟掉的部分）

這一節是整份文件最重要的內容。以下十個概念**不依賴 Web、不依賴 Gemini**，
移植到 Swift、Kotlin 或任何平台都應該保留。

### 2.1 Deterministic Engine + LLM 分工

> **不要讓 LLM 成為唯一的控制器。**

實作方式：

```
程式負責（確定性）              LLM 負責（生成）
─────────────────────          ─────────────────
現在在哪個階段                  客戶說什麼
何時該結束演練                  痛點內容
信任度數值的累加                回饋文字
合規判定（規則優先）            示範話術
隱藏需求的記錄                  評分依據說明
模型選擇與降階
```

**為什麼重要：** 規格 §92 就寫了這條，實作後完全驗證。
每一次我們把判斷交給 LLM，就出現一次 bug（見 §5 D004、D009）。

### 2.2 明確狀態機

```
INTAKE → READY → ROLEPLAY → COMPLETED → FEEDBACK_READY
```

狀態轉移由程式判定，LLM 只能「提供訊號」。
例如 LLM 回傳 `end: true`，程式只在「使用者已完成至少 4 個回合」時才採信。

### 2.3 Model Gateway 抽象

所有模型呼叫都經過單一介面：

```
generate(text, { system, temp, max, json, tier, file, history, timeout })
  → { text, ms, model }
```

`tier` 只有兩個值：`fast`（角色扮演，要快）與 `judge`（評分分析，要準）。
上層引擎**完全不知道**背後是哪家服務商、哪個模型。

**實際效益：** 這一版換過三次模型策略、加過六家服務商、
從伺服器搬到純前端，Coach Engine 的核心邏輯**一行都沒改**。

### 2.4 難度必須是「有力的控制」，不是一行描述

第一版的難度只有一行文字（例如「1: 友善、願意聊、幾乎不拒絕」），
實測發現**完全控制不了模型行為**——連 Level 1 的客戶都會冷淡、說忙、想掛電話。

使用者的回饋是：「一開始 AI 的防備心有點過高，不適合新進夥伴練習，容易打擊信心。」

**這對訓練工具是致命的。** 打擊信心的訓練工具，使用者不會練第二次。

現在每一級都明確規定五件事，而且**其中三件由程式控制而不是靠模型自律**：

| 控制項 | 由誰決定 | Level 1 | Level 5 |
|---|---|---|---|
| 態度與語氣 | 提示詞 | 溫和、會幫使用者接話 | 不耐煩、連續拒絕 |
| **初始信任度** | **程式夾在區間內** | 62～80 | 12～30 |
| **能否主動結束對話** | **程式判定** | ❌ 不能 | ✅ 可以 |
| **引導次數上限** | **程式判定** | 5 次 | 3 次 |
| trust_delta 傾向 | 提示詞 | 偏正向（0～+8） | 偏負向（-10～+4） |

**關鍵設計：Level 1 的客戶不會掛電話。** 新手講到卡住時，客戶會說
「你慢慢說沒關係」「你的意思是……嗎？」——**幫他，而不是罰他**。

實測對照（同樣餵入結巴、沒重點的爛開場）：

```
Level 1：「嗯，您好啊。沒關係你慢慢說，請問今天打來是有什麼事嗎？」  信任 70 → 80
Level 4：「保險喔？我都說了不用了，你們怎麼一直打來啦！」            信任 25 → 15
```

**預設難度改為 Level 1。** 進階使用者可以自己往上調，但預設值決定了大多數人的第一印象。

### 2.5 個性由使用者指定，難度只控制抗拒程度

使用者反映想自己指定客戶個性。實作上把兩件事明確分開：

| | 由誰決定 | 影響什麼 |
|---|---|---|
| **個性** | **使用者**在「客戶背景」欄自由描述 | 說話方式、話多話少、思考習慣 |
| **難度** | 使用者選 1～5 | 抗拒程度、信任度、願意透露多少 |

兩者可以並存，例如「愛聊天」＋高難度 ＝ 話很多但一直閃避重點、不願意約時間。

提示詞明確宣告**使用者指定優先於模型自己的判斷**：

```
「客戶背景」欄位是使用者自己填的。如果裡面已經描述了個性、說話方式或態度，
那是使用者刻意指定要練習的對象，你必須完全照著設定，不得改成你自己想的個性。
```

實測（背景只差最後一句）：

| 使用者寫的 | AI 實際演出 |
|---|---|
| （沒指定個性） | 「沒關係你慢慢說，請問今天打來是有什麼事嗎？」 |
| 個性很愛聊天、話特別多 | 「哎喲我跟你說，我今天剛好在忙我們家那個剛滿四個月的小寶，他剛剛又溢奶了啦！」 |
| 個性非常冷淡，只回一兩個字 | 「嗯，請說。」→「聊什麼？」 |

**踩到的坑：** 當使用者指定的個性與難度看似衝突時（「很冷淡」＋「新手友善」），
模型會把自己的推理寫進人設欄位：

> 「個性非常冷淡，**但因為難度設定為新手友善**，其實有耐心且願意聽人講……」

提示詞加規則擋不住。依 §2.6 的兩層防護原則，加了程式層 `scrubMeta()`
把含後設用語的子句刪掉。這是「提示詞擋不住就用程式擋」的又一個實例。

### 2.6 資訊邊界（這是本專案最重要的產品發現）

Persona 有「業務員知道的」與「業務員不知道的」兩層，
而**示範話術只能使用前者**。

```
接觸情境（六種）→ 定義「此刻業務員合理知道什麼」→ 示範話術的唯一依據
```

沒有這一層，模型會把「客戶心裡的事」洩漏成「業務員已經知道的事」，
產出「您那筆五百萬的保單……」這種在實務上會直接得罪客戶的話術。

**這個問題不是話術品質問題，是架構問題。** 詳見 §5 D012。

### 2.7 兩層防護：提示詞 + 程式規則

任何「不能出錯」的規則都做兩層：

| 規則 | 提示詞層 | 程式層 |
|---|---|---|
| 不預設保險公司 | `NO_BRAND` 指示 | `scrubBrands()` 過濾 |
| 話術不越界 | 已知資訊清單 | `demoLeaksPrivateInfo()` 檢查＋重新產生 |
| 不得跳出角色 | Role Lock 規則 | `validateRoleplay()` 檢查＋重試 |
| 合規用語 | 提示詞提醒 | `checkCompliance()` 規則引擎（優先於 LLM） |

**原則：** 提示詞是「請你這樣做」，程式是「你沒這樣做時我攔下來」。
只做提示詞層必然會漏，因為模型不是每次都聽話。

### 2.8 知識結構化：一次解析，之後查摘要

```
上傳文件 → 一次 LLM 呼叫 → 結構化 JSON 摘要 → 存起來
查詢時 → 只帶摘要（小）→ 快且省
例外：理賠查詢 → 回頭附上條款原文（準確度優先於成本）
```

**為什麼有例外：** 理賠答錯的代價遠高於多花 token。
這種「哪裡可以省、哪裡不能省」的判斷要寫進文件，否則後人會為了效能一致性而把例外拿掉。

### 2.9 錯誤處理三原則

1. **在源頭正規化。** 底層錯誤（逾時、網路失敗）在最靠近 API 的那一層就轉成固定字樣，
   不要讓上層去猜瀏覽器或 OS 的措辭。
2. **認不出來就說認不出來。** 錯誤轉譯函式若無法分類，回傳 `null` 而不是原文，
   由呼叫端明確決定要不要顯示。用關鍵字白名單過濾訊息一定會漏。
3. **錯誤要能行動。** 「剛剛好像卡了一下」是最後的退路，不是預設。
   能告訴使用者「去哪裡做什麼」就一定要說。

### 2.10 使用者選擇權 vs. 系統智慧

> **預設聰明，指定時單純。複雜度留在系統裡，不外露給使用者。**

實例一：模型設定只讓使用者選**一個**模型。
但「自動」模式下，系統仍會為角色扮演挑最快的、為評分挑最準的。
使用者不需要理解這層區別，想知道的人看得到，不想管的人完全不用碰。

**反面教材：** 第一版做成「角色扮演模型」與「評分模型」兩個欄位，
使用者直接回報「太複雜」。那是把架構細節推給使用者承擔。

實例二：難度只讓使用者選 1～5，背後的信任度區間、引導次數、能否掛電話都由系統決定。
使用者只需要判斷「我今天想練簡單的還是難的」。

## 4. 踩過的坑與解法

按「會不會再遇到」排序，最前面的最值得記住。

### 4.1 模型層

| 現象 | 真正原因 | 解法 |
|---|---|---|
| 建立客戶要 18.8 秒 | Gemini 3.x 的**思考 token 計入 `maxOutputTokens`**，額度不足時回空字串 | 放寬 max（Persona 4000／回合 1200／評分 8000） |
| 降級後每回合 26～36 秒 | 免費方案把 `gemini-3.5-flash` 重度限流，但 `flash-lite` 只要 1.1 秒 | 依**實測延遲**排降級順位，不依模型大小 |
| 免費模型「卡住」 | 有時完全不回應，而逾時 120 秒 × 重試 3 次 = 6 分鐘 | 單次逾時＋**整體總時限**；逾時不重試同一模型 |
| 「Free 卻說額度用盡」 | 免費模型是**所有使用者共用上游流量池**，被限流 ≠ 你的額度用完 | 分開兩種 429，訊息與冷卻時間都不同 |
| 選免費模型卻報「餘額不足」 | 降級鏈掉到付費模型 | 指定免費模型時，備援也只走免費模型 |
| 音樂生成模型出現在對話模型清單 | 依名稱過濾看不出來（`google/lyria-3-*`） | 用 API 回報的 `output_modalities`，只保留「僅輸出 text」 |
| 假金鑰也能登入 OpenRouter | 它的 `/models` 是**公開端點** | 改打需要驗證的 `/api/v1/key` |
| 模型改版導致 App 壞掉 | 把模型 ID 寫死在程式裡 | 登入時查詢實際可用模型，用名稱特徵挑選 |

### 4.2 提示詞層

| 現象 | 真正原因 | 解法 |
|---|---|---|
| 客戶第一回合就掛電話 | LLM 自行把 `end` 設為 true | 結束條件由程式判定（至少 4 回合） |
| 隱藏需求一項都記錄不到 | 要求模型「原字照抄」長字串太苛刻 | 改回傳**編號**，程式映射回文字 |
| 示範話術講出客戶的保額 | Persona 與 demo 同次生成，隱藏資訊外洩 | 明確定義資訊邊界＋程式檢查＋重新產生 |
| 教練建議業務員說謊 | 「給他一個好用的藉口」是業界常見話術，但屬不實招攬 | 提示詞加明確紅線 |
| 客戶講粗話 | 難度高的人設加上被忽略三次 | 提示詞加用語護欄 |
| 輸出夾雜 Markdown 記號 | 純文字氣泡顯示成亂符號 | 提示詞要求純文字＋前端清洗 |
| 拿掉 JSON 模式想提高相容性 | **反而讓輸出品質變差**（gemma 開始夾雜俄語、印尼語） | 依模型的 `supported_parameters` 判斷，支援就送 |
| 難度 1 的客戶還是很防備 | 難度只有**一行文字描述**，而且模式規則寫死「你隨時可以說忙、可以想掛電話」套用到所有難度 | 難度改成完整規則表，模式規則區分難易，信任度與引導次數改由程式控制 |
| 人設欄位出現「因為難度設定為…」 | 使用者指定的個性與難度衝突時，模型把自己的推理寫進人設 | 提示詞禁止後設用語＋程式層 `scrubMeta()` 刪掉含後設用語的子句 |

### 4.3 架構層

| 現象 | 真正原因 | 解法 |
|---|---|---|
| 理賠查詢回「條款查不到」 | `getDoc()` 因改用 IndexedDB 變成非同步，**漏了一個 `await`** | 全面檢查呼叫端。**這類錯誤不拋例外，只會安靜地給錯答案** |
| 雲端部署冷啟動 30～60 秒 | 免費方案 15 分鐘休眠 | 改為純前端，冷啟動問題消失 |
| 上傳的文件會消失 | 免費方案檔案系統是暫時性的 | 改存 IndexedDB（使用者自己裝置，永久保留） |

### 4.4 錯誤處理層（這一層踩得最深）

| 現象 | 真正原因 | 解法 |
|---|---|---|
| 逾時錯誤變成未捕捉例外 | `AbortSignal.timeout()` 的訊息是「aborted due to **timeout**」，不含判斷用的「timed **out**」 | 在 `_fetch` 源頭把底層錯誤正規化 |
| 正確的錯誤訊息被換成通用訊息 | 上層用**關鍵字白名單**決定要不要顯示原文，新訊息不在名單裡 | 轉譯函式認不出就回 `null`，由呼叫端明確決定 |
| 餘額不足把使用者踢回登入畫面 | 錯誤分類把「額度」和「金鑰」混在一起 | 只有金鑰無效／無權限才退回登入 |
| 401 後畫面停在錯誤位置 | 呼叫端的 `show('intake')` 蓋掉登出的畫面切換 | 認證錯誤加 `auth` 標記，呼叫端不再切換畫面 |

**共同教訓：用訊息文字比對來分類錯誤非常脆弱。** 這一類 bug 我在同一個專案裡犯了三次。

### 4.5 介面層

| 現象 | 真正原因 | 解法 |
|---|---|---|
| 使用者找不到模型設定 | 入口是首頁底部 13px 灰色小字 | 改成與功能磁磚同份量的區塊，並顯示目前狀態 |
| 模型清單無法選 | 342 個模型照 API 原始順序排列 | 推薦排前面＋標 ★＋搜尋框＋只顯示前 30 個 |
| 兩個模型欄位太複雜 | 把架構細節推給使用者 | 簡化為一個，智慧留在系統裡 |
| 純文字檔卻提示「內容大多是圖片」 | 警告條件沒判斷檔案類型 | 條件加上格式判斷 |
| TTS 沒結束導致流程卡死 | iOS `speechSynthesis` 的 `onend` 偶爾不觸發 | 加保險絲逾時 |

**教訓：「功能做完了」不等於「使用者找得到」。**
我測的是「點下去會不會動」，沒測「使用者會不會知道它在那裡」。

### 4.6 測試層

| 現象 | 解法 |
|---|---|
| 測試不穩（隱藏需求揭露數會浮動） | 把模型相關的結果當**觀察值**，另加確定性的邏輯驗證 |
| 測試失敗但看不出原因 | 把參與判斷的所有欄位都印出來（不只印人看的那幾個） |
| `process.exit()` 在 Windows 觸發 libuv 斷言 | 改用 `process.exitCode` |
| 測試殘留資料汙染下次執行 | 測試結束刪除自己建立的文件 |

## 6. 引擎共用策略（開發原生 App 前必須先決定）

你的目標是 iOS → iPadOS → Android。Coach Engine 要不要共用一份？

### 方案 A：各平台獨立實作（Swift + Kotlin）

- 優點：原生體驗最好、工具鏈最單純
- 缺點：**教練邏輯有兩份副本**，改一邊忘另一邊 → 兩個平台行為不一致
- 適合：兩個平台預計會有不同的產品方向

### 方案 B：沿用現有 JS 引擎（JavaScriptCore / QuickJS）

- 優點：**引擎已通過 60 項測試，不必重新驗證**；只寫一次
- 缺點：多一層橋接、除錯較麻煩、JS 引擎啟動成本
- 適合：想快速拿到原生語音體驗，同時保住已驗證的邏輯

### 方案 C：Kotlin Multiplatform 共用引擎

- 優點：一份程式碼同時支援 iOS 與 Android，型別安全
- 缺點：要先把 1,300 行邏輯重寫成 Kotlin，前期投入大
- 適合：確定兩個平台都要長期維護

### 建議

> **先用方案 B 做 iOS PoC，確認原生語音體驗（尤其 Barge-in）真的比網頁版好，
> 再決定要不要投入方案 C。**

理由：現在最大的未知不是「引擎能不能跑」（已證明能跑），
而是「原生語音對談是否真的讓使用者願意天天練」。
用最低成本先驗證這件事，不要在還不確定產品方向時就付重寫的代價。

## 7. 延伸方向一：原生 iOS / iPadOS App → Android

### 7.1 為什麼要做原生（用實際限制說明，不是「原生比較好」）

目前網頁版有四個**只有原生能解決**的限制：

| 限制 | 網頁版現況 | 原生能做到 |
|---|---|---|
| **Barge-in（打斷 AI）** | 只能「點麥克風打斷」，因為 iOS Safari 無法在 TTS 播放時穩定收音 | `AVAudioEngine` 的 voice processing 提供回音消除，可真正邊聽邊說 |
| **語音辨識是否本地** | Web Speech API 會把音訊送到 Apple 伺服器 | `SFSpeechRecognizer` 可指定 `requiresOnDeviceRecognition = true`，完全不出裝置 |
| **本地模型** | 分頁記憶體約 1～1.5GB，跑不動 | 可用完整 App 記憶體預算 |
| **背景／鎖屏** | 必須保持前景 | 背景音訊模式可支援 |

**不要為了「原生比較潮」而做。** 上面四項才是理由。

### 7.2 技術選擇建議

| 層 | 建議 | 備註 |
|---|---|---|
| UI | SwiftUI | iPad 用 `NavigationSplitView` 適配大螢幕 |
| 語音辨識 | `SFSpeechRecognizer`（`requiresOnDeviceRecognition`） | 繁中支援需實測；不足時再評估 Whisper |
| 語音合成 | `AVSpeechSynthesizer` | zh-TW 語音內建、離線、免費 |
| 音訊管線 | `AVAudioEngine` + voice processing | Barge-in 與回音消除的關鍵 |
| 儲存 | SwiftData | 對應現在的 IndexedDB |
| 文件解析 | PDFKit（PDF）＋ ZIP 解壓（docx/pptx） | 或延續現在「PDF 交模型」的做法 |
| 引擎 | 見 §6 | |

**Android 對應：** `SpeechRecognizer`（離線需下載語言包）、
`TextToSpeech`、`AudioRecord` + `AcousticEchoCanceler`、Room。

### 7.3 語音引擎是重點，也是最大獲益

規格 `04_VOICE_ENGINE.md` 定義的 Voice State Machine 在網頁版被迫簡化。
原生階段應完整實作：

```
IDLE → LISTENING → PROCESSING → THINKING → SPEAKING
                        ↑                       │
                        └──── INTERRUPTED ←─────┘
```

**必須實測的項目**（規格 §110、§123 已列，這裡補上實作後的補充）：

```
□ 繁體中文／台灣口音辨識率（安靜、辦公室、車內、戶外）
□ AI 說話時使用者插話 → 能否正確停止 TTS 並切到收音
□ 回音消除是否有效（AI 自己的聲音不會被辨識成使用者說話）
□ 咳嗽、背景雜音不會誤觸發 Barge-in
□ 連續 10／20／30 分鐘：溫度、電量、記憶體、是否卡頓
□ 藍牙耳機／AirPods／CarPlay 路由切換
□ 來電、Siri 中斷後能否恢復演練狀態
□ Voice-to-Voice 延遲（T5 - T1）
```

### 7.4 分階段計畫

| 階段 | 目標 | 完成條件 |
|---|---|---|
| **N0** | 語音 PoC | Swift App：說話 → 辨識 → 呼叫 Gemini → TTS 播放，**含真正的 Barge-in**。連續 10 分鐘不崩。 |
| **N1** | 引擎接上 | 六大功能其中「電話邀約」完整跑通（Persona → 演練 → 評分 → 回饋） |
| **N2** | 功能補齊 | 其餘五項功能 + 訓練紀錄 + 文件管理 |
| **N3** | iPad 適配 | 大螢幕版面、分割視圖、外接鍵盤 |
| **N4** | 上架準備 | 隱私標籤、App Store 審查素材、麥克風權限說明、合規免責 |
| **N5** | Android 移植 | 依 §6 的引擎策略決定成本 |

**N0 不通過就不要往下走。** 如果原生 Barge-in 做不出比網頁版明顯更好的體驗，
那原生化的主要理由就不成立，該回頭重新評估。

### 7.5 上架前的合規檢查（網頁版不需要，原生一定要）

```
□ 麥克風權限說明文字（NSMicrophoneUsageDescription）要具體
□ 語音辨識權限說明（NSSpeechRecognitionUsageDescription）
□ App Store 隱私標籤：說明對話內容是否傳送、傳給誰
□ 首次啟動的合規提醒（規格 §25）不可省略
□ 「訓練工具，非保險／法律／財務建議」的免責必須在 App 內可見
□ 若保留雲端模式，須說明資料傳送對象
□ 保險業相關 App 可能觸發 App Store 的金融類審查，預留時間
```

## 8. 延伸方向二：本地模型完全離線

### 8.1 先講最重要的判斷

**不要一次全本地。** 六大功能對模型能力的要求差異極大：

| 功能 | 對模型的要求 | 本地可行性 |
|---|---|---|
| 電話邀約／發掘需求角色扮演 | 短句、口語、維持人設 | ⭐⭐⭐⭐ **最適合本地**（要快、要私密、輸出短） |
| 客戶潛在痛點分析 | 中等推理、結構化輸出 | ⭐⭐⭐ 可嘗試 |
| 商品行銷演練 | 需引用教材內容 | ⭐⭐ 需搭配本地 RAG |
| 五項評分與教練回饋 | **最難**：要有證據、不能諂媚、要校準 | ⭐ **建議最後才本地化** |
| 理賠諮詢建議 | 條款精確引用，答錯代價高 | ⭐ **建議永遠保留雲端選項** |

**評分是整個產品的價值所在。** 如果小模型把評分做成空泛稱讚
（「你表現很好，繼續加油」），使用者就不會想練第二次——
那麼「完全離線」這個技術成就反而毀掉了產品。

規格 §47 的 Judge Model 分離架構正是為這件事準備的：
**角色扮演本地（要快、要私密），評分走雲端（要準）。**

### 8.2 建議的分層策略

```
Tier 0  規則引擎          合規檢查、狀態機、資訊邊界檢查   ← 已經是本地了
Tier 1  裝置端小模型      角色扮演、卡住引導              ← 第一階段目標
Tier 2  裝置端中模型      痛點分析、商品說明              ← 第二階段
Tier 3  雲端模型（選用）  五項評分、理賠判斷              ← 建議保留
```

**注意 Tier 0 已經完成。** 現在的合規引擎、狀態機、話術邊界檢查全部是純程式，
不需要網路也不需要模型。這部分已經是離線的了。

### 8.3 技術路線候選

| 路線 | 優點 | 風險 | 建議 |
|---|---|---|---|
| **Apple Foundation Models 框架** | 系統內建、免下載、免費、不佔 App 體積 | 繁中角色扮演品質未知；受系統版本限制 | **第一個評估**——若可行，模型下載問題直接消失 |
| MLX Swift + 量化模型 | Apple Silicon 最佳化、彈性大 | 需自行處理模型下載與版本管理 | 第二選擇 |
| llama.cpp / GGUF | 生態成熟、量化選項多 | 整合工作較多 | 備案 |
| Core ML 轉換 | 系統整合好 | 轉換流程繁瑣、LLM 支援有限 | 視情況 |

**Android 對應：** ML Kit GenAI / AICore（Gemini Nano）、MediaPipe LLM Inference API。

### 8.4 記憶體現實（規格 §6 的假設，實作後要重新確認）

iPhone 14 Pro 有 6GB RAM，但 App 可用預算遠低於此（系統會回收）。粗略估算：

| 模型規模 | Q4 量化後權重 | 加上 KV Cache | 可行性 |
|---|---|---|---|
| 0.5～1B | 約 300～600 MB | < 1 GB | 輕鬆 |
| 2B | 約 1.2～1.5 GB | 1.5～2 GB | 可行，需監控 |
| 4B | 約 2.5 GB | 3 GB+ | 勉強，高風險 |
| 7B+ | 4 GB+ | — | 不建議 |

**這些是估算，必須實機量測。** 規格 §26 已列出要測的項目。

### 8.5 本地 RAG（商品教材離線化）

```
文件 → 本地解析 → 分段 → 本地 Embedding → 本地向量儲存 → 檢索 → 本地 LLM
```

- Embedding 模型與 LLM **應分開選擇**（規格 §103）：需要繁中、小、快
- 向量儲存：資料量小時，直接用 SQLite + 暴力餘弦相似度即可，不必引入向量資料庫
- **重要：現在的「一次結構化」策略在本地更有價值**，因為小模型的 context 更小

### 8.6 分階段計畫

| 階段 | 目標 | 通過條件 |
|---|---|---|
| **L0** | 模型選型 Benchmark | 用 §10 的測試集，比較 3～5 個候選模型的繁中角色扮演能力 |
| **L1** | 角色扮演本地化 | 首 token < 1 秒、每回合 < 2 秒、Persona 一致性 ≥ 90% |
| **L2** | 混合模式 | 角色扮演本地 + 評分雲端，使用者可切換 |
| **L3** | 痛點分析本地化 | 結構化 JSON 輸出成功率 ≥ 95% |
| **L4** | 本地 RAG | 商品演練可離線 |
| **L5** | 評分本地化（選用） | **只有在評分品質通過 Golden Reference 比對後才做** |

### 8.7 L0 必須先回答的問題

在投入任何整合工作之前，先用**最小 PoC**回答：

```
□ 這個模型能用自然的台灣繁體中文說話嗎？（不是「能講中文」，是「像台灣人講話」）
□ 連續 10 回合能維持客戶人設不崩嗎？
□ 能穩定輸出可解析的 JSON 嗎？（我們的引擎依賴這個）
□ 能理解「不要一次說出隱藏需求」這種抽象指令嗎？
□ iPhone 14 Pro 上首 token 幾秒？每秒幾個 token？
□ 連續 20 分鐘後溫度與電量如何？
□ 記憶體峰值多少？會不會被系統回收？
```

**前四項不通過，後三項不用測。** 跑得動但演不好，對這個產品沒有意義。

### 8.8 離線後的架構調整

| 項目 | 現在 | 離線後 |
|---|---|---|
| 登入畫面 | 必須輸入 API 金鑰 | 應可跳過（本地模式不需要金鑰） |
| 模型設定 | 選雲端模型 | 選「本地／雲端／自動」＋本地模型管理（下載、刪除、版本） |
| 錯誤處理 | 429／402／逾時 | 新增：模型載入失敗、記憶體不足、儲存空間不足 |
| Gateway 降階 | 換雲端模型 | 本地失敗 → 換較小的本地模型 → 雲端（若允許） |
| 首次啟動 | 直接可用 | 需要模型下載流程（規格 §90：顯示大小、是否需 Wi-Fi、可否稍後） |

## 9. 不要重複犯的錯（給未來的自己）

這一節請在每個階段開始前重讀一次。

### 9.1 關於 AI

1. **任何交給 LLM 的判斷，最後都會需要程式兜底。** 不要問「模型會不會聽話」，
   要問「不聽話的時候誰攔下來」。
2. **要模型做它擅長的形式。** 挑編號比複製字串準確；輸出 JSON 比輸出自然語言好解析。
3. **不要只看紙面規格選模型。** 決定體驗的是「這把金鑰、這個方案、這個時段」的實際延遲。
4. **移除限制不一定提升相容性。** 拿掉 JSON 模式反而讓輸出品質崩壞。
5. **模型 ID 不要寫死。** 查詢實際可用清單，用特徵挑選。

### 9.2 關於錯誤處理

6. **不要用訊息文字比對來分類錯誤。** 在源頭正規化。這個坑我踩了三次。
7. **每個錯誤都要能行動。** 使用者需要知道「去哪裡做什麼」。
8. **相似的錯誤代碼可能是完全不同的問題。** 429 上游限流 vs 429 額度用盡 vs 402 沒餘額，
   原因與解法都不同，混在一起會給錯建議。
9. **會安靜給錯答案的 bug 最危險。** 漏一個 `await` 不會拋例外，只會讓理賠查詢回「查不到」。

### 9.3 關於產品

10. **功能能用 ≠ 使用者找得到。** 可發現性要當成功能的一部分驗收。
11. **不要把架構細節推給使用者。** 複雜度留在系統裡。
12. **實務失禮比技術錯誤更難發現。** 「您那筆五百萬的保單」在程式上完全正確，
    在實務上會直接得罪客戶。**這類問題只有領域專家看得出來，要主動請他們檢視輸出。**
13. **穩定性 > 功能數量。** 給使用者選擇權，但不要讓他選到一個會讓 App 壞掉的設定。
14. **預設值決定大多數人的第一印象。** 難度預設 2 而非 1，讓新人第一次練習就被冷淡對待。
    **訓練工具打擊使用者信心，等於失去存在意義。** 每個預設值都要問「新手第一次會遇到什麼」。
15. **「一行文字的設定」通常等於沒有設定。** 難度靠一行描述完全控制不了模型；
    真正有效的是「明確規則＋程式夾住關鍵數值」。若某個參數很重要，
    就不要只用提示詞描述它。

### 9.4 關於測試

16. **不要讓測試依賴模型的浮動行為。** 把它當觀察值，另外做確定性驗證。
17. **測試失敗要看得出原因。** 把所有參與判斷的欄位都印出來。
18. **測試要自己清理。** 殘留資料會汙染下一次執行。

## 10. 測試與 Golden Reference 的延續

### 10.1 現有的 `tools/selftest.mjs` 為什麼有效

它不是單元測試，是**端到端行為驗證**：真的呼叫模型、真的跑完整流程、
斷言的是「產品行為」而不是「函式回傳值」。

它抓到的真實問題包括：隱藏需求記錄失效、`await` 遺漏、
話術越界、402 未處理、逾時未攔截。

### 10.2 移植到原生時要保留的結構

```
分節執行         node tools/selftest.mjs 5   ← 只跑第 5 節，省時省額度
規則層先測       不呼叫模型的部分先跑，快速失敗
確定性 + 觀察值  邏輯用斷言，模型行為用觀察值印出
效能一起量       每節記錄延遲，回歸時能看出變慢
自我清理         測試建立的資料自己刪除
```

原生版建議用 XCTest 實作同樣的分層，並保留「可以只跑某一節」的能力。

### 10.3 Golden Reference 還沒建立（規格 §41 要求）

這是 V1 的**已知缺口**。規格要求建立 50～100 個標準測試案例，
比較不同模型的表現。目前只有 `selftest.mjs` 的十幾個案例。

**導入本地模型前必須補上這件事**，否則無法回答
「小模型的評分品質是否可接受」這個關鍵問題。

建議格式：

```
案例 ID
接觸情境
客戶設定
使用者輸入序列
預期的客戶行為特徵（不是逐字比對，是行為描述）
預期的評分區間
預期回饋必須包含的要點
```

## 12. 最後一句

規格文件 §63 說：

> **AI業務教練不是一個「會回答業務問題的 AI」，
> 而是一個「會陪業務員反覆練習，並且讓業務能力逐步提升的 AI 教練」。**

V1 實作驗證了這句話的工程含義：

> **這個產品的價值不在模型多強，而在「程式有多懂業務實務」。**

最能證明這一點的，是那句「您那筆五百萬的保單」——
模型完全正常、程式完全正確、規格完全遵守，
但它在實務上會直接得罪客戶。

修好它需要的不是更大的模型，而是把「業務員此刻合理知道什麼」
這件領域知識，明確地寫成程式看得懂的規則。

**後續每一個階段，都請把「這個決策是否讓 AI 更像一位真正的業務教練」
放在「這個決策技術上是否更先進」之前。**
