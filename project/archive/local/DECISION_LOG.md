# DECISION LOG

記錄會影響架構、且事後容易忘記「為什麼這樣選」的決策。

---

## 2026-08-16｜D001 網頁測試版的 LLM 先接 Gemini API，而非本機模型

**決策：** V0.1 走 Gemini API（`gemini-3.7-flash`），本機模型延後到原生 iOS 階段。

**為什麼：** 規格 §27 要求 Local-first，但 iPhone Safari 分頁記憶體上限約 1～1.5GB，
Gemma 3n E2B 量化後仍需 2～3GB，網頁版在 iPhone 上不可能跑本機模型。
若為了「local-first」而在網頁版硬塞小模型，只有桌機能測，反而測不到真正的目標裝置。

**影響：** 未違反 Model-Agnostic 原則——所有模型呼叫都經過 `lib/gateway.js`。
原生 App 階段新增 local adapter 即可，Coach Engine 不需修改。

## 2026-08-16｜D002 語音採用瀏覽器內建 Web Speech API

**決策：** STT/TTS 使用 iOS Safari 內建的 `webkitSpeechRecognition` 與 `speechSynthesis`。

**為什麼：** 零下載、零費用、延遲低、支援 zh-TW，且錄音不需經過我方伺服器，
符合規格 §81「不得預設把完整錄音上傳第三方」。

**代價：** iOS 無法在 TTS 播放時穩定同時收音，因此規格 §31 的 Barge-in
在 V1 降級為「點麥克風打斷」。此限制已記錄於 `app/README.md`。

## 2026-08-16｜D003 核心教練邏輯放伺服器端，前端只留 UI 與語音

**決策：** Prompt、Persona 隱藏狀態、評分邏輯、合規規則全部在 `app/lib/`，
瀏覽器只收到 Public State。

**為什麼：** 規格 §36、§37 要求核心 IP 不明文放在 Client。
副作用是前端變得很小，也符合「程式碼精簡」的要求。

**驗證：** `tools/selftest.mjs` 有一項專門斷言 Client 回應不含 `hidden_needs`。

## 2026-08-16｜D004 演練的結束時機由程式判定，不交給 LLM

**決策：** LLM 回傳的 `end` 訊號，只有在使用者已完成至少 4 個回合後才採信；
連續三次無效回應則強制結束（規格 §17）。

**為什麼：** 實測發現難度 3 的客戶在第 1 回合就回「不用再打來了」並把 `end` 設為 true，
演練還沒開始就結束。這是規格 §92「重要產品邏輯由程式控制」的實例。

## 2026-08-16｜D005 Model Gateway 需處理過載降級

**決策：** 同一模型重試 3 次（指數退避），仍失敗則自動降級到偏好清單的下一個模型。

**為什麼：** 開發當天實際遇到 `gemini-3.7-flash` 回 503 過載與 429 額度用盡。
若不處理，使用者會在演練到一半時看到錯誤而中斷。

**另註：** Gemini 3.x 的思考 token 會計入 `maxOutputTokens`，額度不足時回傳空字串。
額度必須放寬（Persona 4000／回合 1200／評分 8000），這是很容易誤判成「模型不穩」的坑。

## 2026-08-16｜D006 角色扮演改用 flash-lite 作為主要降級目標

**決策：** `PREFER_FAST` 順序調整為 3.7-flash → 3.6-flash → **3.5-flash-lite** → 3.1-flash-lite
→ …→ 3.5-flash（墊底）。

**為什麼：** 實測（同一段提示詞、同一時間）：

| 模型 | 延遲 |
|---|---|
| gemini-3.5-flash-lite | 1.1 秒 |
| gemini-3.1-flash-lite | 1.4 秒 |
| gemini-3.5-flash | 26.5 秒（免費方案被重度限流） |

原本把 3.5-flash 排在 lite 前面，導致降級後每回合要等 26～36 秒，語音對練完全不可用。
客戶回話只有 1～3 句，lite 的品質實測足夠，且 1.1 秒直接達成規格 §29 的 ≤2 秒目標。

**啟示：** 規格 §81「不要只看 Benchmark Leaderboard」在這裡完全應驗——
真正決定體驗的是「這把金鑰、這個方案、這個時段」的實際延遲，不是模型的紙面能力。

## 2026-08-16｜D007 文件解析不裝任何套件：Office 自解，PDF 交給模型

**決策：** `.docx`／`.pptx` 用自寫的 ZIP+XML 解析（`lib/docx.js`，60 行）；
`.pdf` 直接把原始位元組交給 Gemini 讀。不使用 `pdfjs-dist` 等套件。

**為什麼：**
・`.docx`／`.pptx` 本質就是 ZIP 裡的 XML，Node 內建 zlib 就能解，沒必要引入相依。
・PDF 相反——中文 PDF 大量使用 CID 字型與子集嵌入，自寫解析器常常取出亂碼；
　掃描版更是完全取不到字。模型原生讀 PDF 可以連圖表與掃描頁一起理解。

**驗證：** 用使用者自己的 `【AiCoach】AI業務教練.pptx` 實測，13 頁全部正確取字分頁。

## 2026-08-16｜D008 知識庫採「一次結構化，之後查摘要」

**決策：** 上傳時呼叫一次模型，把文件轉成結構化 JSON（商品：FABE 賣點／條款：給付項目窮舉）。
之後的演練與查詢只帶這份摘要，不重送整份文件。

**為什麼：** 對應規格 §41 的 Knowledge Structuring。若每次查詢都重送 100 頁條款，
在免費方案的 TPM 限制下很快就會撞牆，且延遲不可接受。

**例外：** 理賠查詢會回頭附上條款原文（PDF ≤6MB 時送原始檔）。
理賠答錯的代價比多花 token 高，準確度優先。回覆會標示是否有比對原文。

## 2026-08-16｜D009 隱藏需求的揭露改用「編號」而非「原字照抄」

**決策：** 角色扮演時，模型回傳 `revealed: [1,3]` 這種編號，由程式映射回實際文字。

**為什麼：** 原本要求模型把透露的隱藏需求「原字照抄」回 JSON，實測 4 個回合下來
一項都沒記錄到，即使客戶明顯已經鬆口。改成編號後，同樣的情境正確記錄到 2／3 項。

**啟示：** 小任務要遷就模型擅長的形式。要模型在演戲的同時精確複製長字串，
是不必要的認知負擔；讓它挑編號就準確得多。

## 2026-08-16｜D010 教練不得建議捏造聯繫理由

**決策：** 在 `COACH_CHAT` 加入紅線：不得建議假名額、假優惠、假停售、假核保結果、
假裝「剛好經過」。

**為什麼：** 實測時教練回覆建議業務員「給他一個好用的藉口」「最近剛好有一個核保優勢／名額」。
這雖然是業界常見話術，但屬於不實招攬，且與規格 §54「不應鼓勵欺騙」直接衝突。
加上紅線後，同樣的問題模型會主動說「千萬不要假裝路過或用假的停售藉口」。

## 2026-08-17｜D011 示範話術一律不預設保險公司

**決策：** 所有系統產生的示範話術、建議開場、改善示範，公司一律寫「○○人壽」、
人名寫「○○」，自我介紹統一為「○○人壽的○○」。採兩層實作：

1. **提示詞層** — `NO_BRAND` 規則，注入痛點分析、Persona／示範話術、評分回饋、行銷諮詢四支提示詞。
2. **程式層** — `scrubBrands()` 保險絲，在回傳前掃掉漏網的公司名（規則優先，不依賴 LLM 自律）。

**為什麼：** 使用者可能任職於任何一家公司。示範話術若預設了某家公司，
會讓人誤以為那是該公司的標準話術，也不適合跨公司使用。

**不套用的範圍**（刻意）：
・**逐字稿與評分證據** — 那是使用者自己講的話，屬於原始紀錄，改寫會失真。
・**理賠諮詢與商品教材** — 使用者上傳的條款／教材本來就有真實商品與公司名，
　洗掉反而讓人搞不清楚在講哪一張保單。
・**客戶的台詞** — 客戶不會自稱保險公司。

**誤殺防範：** 「台灣」「中國」等字只有接在「人壽／產險／保險／金控」後面才視為公司名，
所以「台灣人的觀念」「中國信託的理專」不會被改掉，這兩個案例已寫進自我測試。

## 2026-08-17｜D012 示範話術必須受「接觸情境」的資訊邊界約束

**問題：** 使用者回報一句陌生開發的示範話術：
「林阿姨，您那筆五百萬的保單放了好幾年了，原來的業務員都沒跟您做過保單健檢嗎？」
第一通電話就講出對方的保額，實務上不但失禮，還會讓客戶覺得個資被調查。

**根因（架構問題，不只是話術不好）：** Persona 與 demo 是同一次生成的。
模型設計出客戶的 hidden_needs 與背景細節後，直接把「客戶心裡的事」
洩漏成「業務員已經知道的事」——這是資訊邊界沒有被明確定義。

**決策：**
1. 演練前新增「接觸情境」欄位，六種：陌生開發／客戶轉介紹／緣故／既有客戶服務／
   之前談過沒成交／活動後追蹤，另可補充自由說明。
2. 每一種情境在 `CONTEXTS` 明確定義「業務員此刻知道什麼」，
   personaPrompt 把這份清單當成設計 demo 的**唯一依據**。
3. 程式層 `demoLeaksPrivateInfo()` 掃描示範話術，若在陌生／轉介紹／緣故／活動後情境中
   出現保額、保單、繳費金額等字樣，**重新產生一次**（規格 §68 Output Validation）。
4. 角色扮演的客戶也知道這層關係——對方若講出他沒說過的私人資訊，
   客戶會直接反問「你怎麼會知道？」並變得防備。
5. 評分提示詞加入同一條檢查，越界提問會被列入 improvements。

**實測（陌生開發）：** 「王太太您好，我是○○人壽的○○……不知道您現在方便講話嗎？」
關鍵問題問的是生活安排，不是錢。
**實測（轉介紹）：** 開場第一句就交代介紹人「是王大哥特別拜託我打這通電話的」。

## 2026-08-17｜D013 話術設計導入 NLP 建立信任感原則

**決策：** 新增 `RAPPORT` 原則區塊，注入 Persona／示範話術、評分回饋、痛點分析、行銷諮詢四支提示詞。

七條原則：先跟後帶（Pacing & Leading）、語言同步（Matching）、尊重自主權（給對方退路）、
開場交代「我是誰／為什麼是現在／為什麼是你」、先處理情緒再處理事情、
第一次接觸只求一個小承諾、問句從生活出發而非從錢出發。

**倫理界線（依規格 §53）：** 明文禁止用 NLP 操控、製造恐懼、假裝熟識、
或暗示自己已掌握對方個資。技巧只能用於提升理解與尊重。

**效果：** 評分回饋開始自然引用這些原則，例如「在客戶表達忙碌時未能先承接情緒並給予退路」。

## 2026-08-17｜D014 改為每位使用者自帶 API 金鑰

**決策：** 進入主程式前新增登入畫面，使用者選擇 AI 服務商並輸入自己的金鑰。
伺服器不再持有任何金鑰，改為依每次請求所帶的憑證建立 adapter。

**為什麼：** 原本共用一把金鑰的模式有三個問題——
所有同事的用量都算在擁有者頭上、免費額度很快撞牆、網址外流等於額度外流。
使用者自帶金鑰後這三個問題同時消失，也不必再靠通行碼保護額度。

**支援的服務商：** Gemini、Anthropic 為原生實作；
OpenAI、Groq、OpenRouter、DeepSeek 走同一套 OpenAI 相容介面。
三條程式路徑涵蓋六家，`PROVIDERS` 新增一筆即可再擴充。

**模型選擇不寫死版本號**：登入時實際呼叫該服務商的 models API，
再用名稱特徵（flash / mini / haiku → fast；pro / sonnet / gpt → judge）挑選，
避免模型改版後整個 App 壞掉。

**金鑰安全措施：**
・只存在使用者瀏覽器的 localStorage，隨每次請求以 header 送出。
・伺服器只快取「已完成模型探測的 adapter 實例」，2 小時後回收；不寫入磁碟、不寫進日誌。
・`scrubKey()` 在回傳錯誤前洗掉可能夾帶的金鑰；已用測試確認回應與日誌都不含金鑰。
・登入時實際打一次該服務商的 API 驗證，問題在登入當下就浮現，不會等到演練到一半才爆。
・`friendlyError()` 把各家原始錯誤轉成使用者看得懂的中文。

**已知落差：** 只有 Gemini 有實際金鑰可測，其餘五家是照官方 API 規格實作但未實測。
登入驗證機制讓任何實作錯誤會在使用者第一次登入時就明確失敗，而不是靜默出錯。

**PDF 限制：** 只有 Gemini 與 Anthropic 能直接讀 PDF。
其餘服務商上傳 PDF 會得到明確的錯誤訊息與替代建議，而不是失敗得不明不白。

## 2026-08-17｜D015 移除伺服器，改為 GitHub Pages 純前端

**決策：** 拿掉 `server.js`，把整個 Coach Engine 搬進瀏覽器，
由瀏覽器直接呼叫 AI 服務商，網站放 GitHub Pages。

**為什麼：** Render 免費方案 15 分鐘沒人用就休眠，下一位使用者要等 30～60 秒。
對「讓業務員願意天天練」的產品來說，這個等待是致命傷。

**為什麼現在可以拿掉伺服器：** 原本伺服器存在的兩個理由都已消失——
1. 保護核心 IP（規格 §36）→ repo 已於 D011 後改為公開，提示詞本來就看得到。
2. 保護 API 金鑰 → D014 改為使用者自帶金鑰後，伺服器端沒有秘密可藏。

**實測前提：** 各家 API 的 CORS 支援（2026-08-17 實測）
Gemini ✅、OpenAI ✅、Groq ✅；Anthropic 需 `anthropic-dangerous-direct-browser-access` 標頭。

**技術移轉：**
・`docx.js` 的 `zlib.inflateRawSync` → `DecompressionStream('deflate-raw')`，
　Node 18+ 與瀏覽器都有，同一份程式碼兩邊都能跑（實測同一份 PPTX 結果完全一致，瀏覽器 17ms）。
・Node `Buffer` 的 readUInt32LE 等 → `DataView` + `TextDecoder`。
・文件儲存從伺服器檔案系統 → IndexedDB（`store.js`；Node 下自動退回記憶體版，
　讓 `tools/selftest.mjs` 仍可執行）。
・新增 `engine/api.js`，保留與伺服器版**完全相同的呼叫介面**，
　UI 層幾乎不需修改，日後若要切回伺服器架構也只換這一層。

**取捨：**
・失去：文件無法團隊共用，每個人要自己上傳教材。
・換得：無冷啟動、永久免費、更快（少一跳）、文件永久保留在自己裝置、
　對話不經過任何第三方伺服器、沒有伺服器要維護。

**注意事項：** `getDoc()` 因 IndexedDB 而變成非同步，所有呼叫端都必須加 `await`。
移轉時自我測試第 5 節就是因為漏掉一個 `await` 而失敗——拿到 Promise 當成文件用，
理賠查詢變成「條款查不到」。這類錯誤不會拋例外，只會安靜地給出錯誤答案，值得記一筆。

## 2026-08-17｜D016 模型可由使用者指定，但自動降階不關閉

**決策：** 新增「模型設定」畫面，使用者可分別指定角色扮演模型與評分模型。
指定後該模型排第一順位，**但降階鏈仍然保留**——額度用盡時照樣自動換下一個。

**為什麼不做成「指定就只用這個」：** 免費方案的額度隨時可能用盡（開發期間實測遇過多次）。
若指定後就不降階，使用者會在演練到一半直接失敗。
產品規格 §58「穩定性 > 功能數量」在這裡的具體應用：
選擇權給使用者，但不讓使用者選到一個會讓 App 壞掉的設定。

**UI 取捨：** 模型清單是即時查詢的（實測 Gemini 回傳 20 個），
API 原始順序把 `gemini-2.5-flash`、`gemma-4-26b` 排在前面，推薦的反而埋在後面。
對非工程背景的使用者，20 個原始代號隨機排列等於不能選。
因此 `status()` 額外回傳 `rank`，UI 依推薦順位排序並標 ★，且顯示服務商提供的友善名稱
（`gemini-3.7-flash` → 「Gemini 3.7 Flash」）。

**降階要讓使用者知道：** 新增 `onEvent` 回呼，額度用盡或改用備援模型時跳提示。
原本只寫 console.warn，使用者只會感覺「今天怎麼變慢／變差」卻不知道原因。

## 2026-08-17｜D017 加入 OpenRouter 一鍵登入；NVIDIA 與 ChatGPT OAuth 確認不可行

**實機驗證（瀏覽器直接呼叫）：**

| 端點 | 結果 |
|---|---|
| OpenRouter `/api/v1/*` | ✅ `access-control-allow-origin: *` |
| OpenRouter `/api/v1/auth/keys`（OAuth 換金鑰） | ✅ 允許 |
| OpenAI `auth.openai.com/oauth/token`（登入） | ✅ 允許 |
| **ChatGPT `chatgpt.com/backend-api/codex/*`（推論）** | ❌ 擋 CORS |
| **NVIDIA `integrate.api.nvidia.com/v1/*`** | ❌ 完全無 CORS 標頭，`Failed to fetch` |

**決策：**
1. **加入 OpenRouter OAuth PKCE**（`docs/engine/oauth.js`）。PKCE 用一次性亂數取代 client secret，
   全程瀏覽器完成，不需伺服器，符合 GitHub Pages 架構。
2. **放棄 NVIDIA。** 不是沒做，是瀏覽器根本呼叫不到。加一個必定失敗的選項只會讓使用者困惑。
3. **放棄 ChatGPT OAuth。** 登入那段可行，但拿到 token 後的推論端點擋 CORS，
   必須自架伺服器代轉每一次呼叫——那會失去無冷啟動與零維護，且條款疑慮未解。

**OpenRouter 的模型挑選問題：** 回傳 342 個模型（已濾掉 `:batch` 非同步介面）。
・自動挑選改為明確偏好中文表現好的：`google/gemini-*-flash` → `anthropic/claude-*-fast`（角色扮演）、
　`anthropic/claude-opus-*` → `google/gemini-*-pro`（評分）。
・`:free` 模型不列入自動挑選——實測 `dots-3-note-preview:free` 回簡體中文、
　`lfm-2.5-2.6b:free` 花 46 秒且中文破碎。但仍列在清單中並標「免費」，讓沒儲值的人能用。
・模型清單超過 30 個時加入搜尋框，未搜尋時只顯示前 30 個，否則數百列 DOM 會很慢。

**402 是新的錯誤類別。** 測試時 OpenRouter 餘額為 0，付費模型回 HTTP 402。
原本沒處理，使用者只會看到「剛剛好像卡了一下」。現在區分：
・402 餘額不足 → 明確告知去儲值或改選 `:free` 模型，**且不把使用者踢回登入畫面**（不是金鑰問題）
・429 額度用盡 → 自動降階並冷卻 10 分鐘
這兩者原因與解法完全不同，混在一起會給錯建議。

## 2026-08-17｜D019 模型選擇簡化為單一選項；免費模型標示 (Free)

**這是設計錯誤，不只是介面問題。** 分成兩區是把我的架構細節（規格 §47 的
Roleplay Model / Judge Model 分離）推給使用者承擔。使用者要練習業務技巧，

**相容性：** 舊版存的是 `{fast, judge}` 物件，`loadPin()` 讀到物件時取 `fast` 值並就地改寫成字串，

## 2026-08-17｜D020 免費模型的三種失敗模式，以及錯誤訊息比對的脆弱性

**使用者回報三個現象，實測後發現前兩個是同一個原因，第三個是免費模型的本質限制。**

實測（2026-08-17，OpenRouter）：

| 模型 | 結果 |
|---|---|
| `openai/gpt-oss-20b:free` | 有時 `429 temporarily rate-limited upstream`，有時完全不回應 |
| `google/gemma-4-31b-it:free` | `429 temporarily rate-limited upstream` |
| `google/gemma-4-26b-a4b-it:free` | 成功，但 6.9 秒（不送 response_format 時 14.2 秒且中文夾雜俄語、印尼語、孟加拉語） |

**根因與修正：**

1. **「額度用盡」訊息誤導。** 免費模型是所有 OpenRouter 使用者共用一個上游流量池，
   被限流跟「你的帳戶額度用完」完全不同。原本兩者都回報「額度用盡」，難怪使用者覺得矛盾
   （明明標示 Free 卻說額度用盡）。現在分開：上游限流 → 「使用的人太多，等一兩分鐘」，冷卻 1 分鐘而非 10 分鐘。

2. **降階會掉到付費模型。** 指定免費模型被限流後，備援鏈掉到付費模型，再回報「餘額不足」——
   使用者明明選了免費的。現在指定免費模型時，備援也只走免費模型。
   另外遇到 402 會記住「這個帳戶沒餘額」，之後直接跳過付費模型。

3. **「卡住」是逾時設計缺陷。** `gpt-oss-20b:free` 有時完全不回應，
   而評分層逾時 120 秒 × 3 次重試 = 最糟 6 分鐘。改為：
   單次逾時（角色扮演 25 秒／評分 45 秒）＋ **整個 generate() 的總時限**，
   且逾時後不重試同一個模型（重試沒意義），直接換下一個。實測從無限卡住變成 30 秒內完成。

4. **免費模型備援要排序。** 免費模型品質落差極大（實測有一個要 46 秒且中文破碎），
   依實測結果排序，別掉到那種。

5. **非對話模型混進清單。** `google/lyria-3-*` 是音樂生成模型，卻出現在備援鏈裡。
   依名稱過濾看不出來（名稱毫無線索），改用 API 回報的 `output_modalities`——
   只保留「輸出僅有 text」的模型。注意 lyria 輸出是 `["text","audio"]`，
   所以條件必須是「只有 text」而不是「包含 text」。

6. **OpenRouter 假金鑰可以登入。** 它的 `/models` 是**公開端點**，假金鑰也拿得到清單，
   所以「登入時驗證金鑰」形同虛設。改為先打需要驗證的 `/api/v1/key`（實測假金鑰回 401）。

7. **response_format 要保留。** 直覺上拿掉 JSON 模式可以提高相容性，
   實測相反——gemma 不用 JSON 模式時輸出品質明顯變差。改為依 API 回報的
   `supported_parameters` 判斷該模型支不支援，支援就送。同時用 `top_provider.max_completion_tokens` 夾住上限。

**最重要的教訓：用訊息文字比對來分類錯誤非常脆弱。**
・`AbortSignal.timeout()` 拋出的訊息是「aborted due to timeout」，不含我判斷用的「timed out」，
　導致逾時錯誤沒被攔截而直接成為未捕捉例外。已改為在 `_fetch` 源頭把底層錯誤正規化成固定字樣。
・`friendlyError()` 原本認不出錯誤時回傳原文，上層再用白名單決定要不要顯示——
　結果新增的逾時訊息不在白名單裡，被換成通用的「剛剛好像卡了一下」。
　已改為認不出來就回 `null`，由呼叫端明確決定，不再靠關鍵字猜。

## 2026-08-17｜D021 預設難度降為「新手友善」；個性改由使用者指定

**問題（使用者回報）：** 「一開始 AI 的防備心有點過高，其實不適合新進夥伴練習，容易打擊信心。」

**根因（三個，都在程式裡）：**
1. **難度只有一行文字描述**（例如「1: 友善、願意聊、幾乎不拒絕」），
   對模型行為幾乎沒有約束力。
2. **`MODE_RULES.call` 寫死「你隨時可以說忙、可以想掛電話」，套用到所有難度**——
   這是連 Level 1 都很防備的主因。
3. **初始信任度由模型自己決定**，實測常給 15～25，開場就冷淡到沒辦法練習。
4. 預設難度是 2，不是 1。

**決策一：難度改成有力的控制，關鍵數值由程式把關**

| 控制項 | 由誰決定 | L1 | L5 |
|---|---|---|---|
| 態度與語氣、trust_delta 傾向 | 提示詞（完整規則段落） | 溫和、會幫使用者接話 | 不耐煩、連續拒絕 |
| 初始信任度 | **程式夾在區間內** | 62～80 | 12～30 |
| 能否主動結束對話 | **程式判定** | ❌ | ✅ |
| 引導次數上限 | **程式判定** | 5 | 3 |

・`MODE_RULES` 每個模式拆成 easy／hard 兩版，難度 ≤2 用 easy。
・卡住時的引導指示也分難易：**新手級是「幫他接話」，不是「表達不耐煩」**。
・預設難度改為 **1 新手友善**，UI 顯示「第一次練習建議從這裡開始」。

**實測對照**（同樣餵入結巴、沒重點的爛開場三次）：

```
L1：「嗯，您好啊。沒關係你慢慢說，請問今天打來是有什麼事嗎？」   信任 70 → 80，不掛電話
L4：「保險喔？我都說了不用了，你們怎麼一直打來啦！」             信任 25 → 15
```

**決策二：個性由使用者在「客戶背景」欄指定，優先於模型判斷**

提示詞明確宣告：背景欄若已描述個性、說話方式或態度，
那是使用者刻意指定的，必須完全照著演，不得改成模型自己想的個性。

並且明確區分兩者職責，避免模型混淆：
・**個性** ← 使用者（說話方式、話多話少）
・**難度** ← 選單（抗拒程度、信任度、願意透露多少）
・兩者可並存：「愛聊天」＋高難度 ＝ 話很多但一直閃避重點。

UI 同步調整：背景欄的說明與 placeholder 明確邀請填寫個性，
並列出六種常見型（愛聊天／個性急／客氣難拒絕／疑心病重／很冷淡／理性看數據）。
難度選項下方顯示該級會遇到什麼樣的客戶。

**實測**（背景只差最後一句）：

| 使用者寫的 | AI 演出 |
|---|---|
| 個性很愛聊天、話特別多 | 「哎喲我跟你說，我今天剛好在忙我們家那個剛滿四個月的小寶，他剛剛又溢奶了啦！」 |
| 個性非常冷淡，只回一兩個字 | 「嗯，請說。」→「聊什麼？」 |

**衍生的坑：** 使用者指定的個性與難度看似衝突時（「很冷淡」＋「新手友善」），
模型會把自己的推理寫進人設欄位：
「個性非常冷淡，**但因為難度設定為新手友善**，其實有耐心……」

提示詞加規則擋不住（只在衝突時出現）。依兩層防護原則加了程式層 `scrubMeta()`，
刪掉含後設用語的子句；整段都是後設時退回原文，不留空白人設。

**啟示：**
1. **預設值決定大多數人的第一印象。** 訓練工具打擊使用者信心，等於失去存在意義。
2. **「一行文字的設定」通常等於沒有設定。** 重要參數不要只用提示詞描述，
   關鍵數值要由程式夾住。

## 2026-08-18｜D022 本地模型走「瀏覽器內 WebGPU」，不走本機 runtime

**決策：** 完全離線版採路線 A——模型以 ONNX 格式在瀏覽器內用 WebGPU 執行
（`transformers.js` + ONNX Runtime Web），使用者不裝任何東西、不申請金鑰。
放棄「網頁連本機 Ollama」的路線。

**為什麼：** 從 HTTPS 頁面呼叫 `http://localhost:11434` 要同時通過三層阻擋——
mixed content、Chrome Local Network Access 權限提示、
以及 `Access-Control-Allow-Private-Network` 私有網路 CORS 標頭，
而且各家瀏覽器行為不一致。這與 D017 記錄的 NVIDIA NIM 無法瀏覽器直連是同一類問題：
**架構層的限制，不是寫程式能解決的。**

瀏覽器內推論完全不碰網路，因此這三層麻煩全部消失。

**代價：** 模型格式從 GGUF 換成 ONNX（原本考慮的
`unsloth/Qwen3.5-0.8B-MTP-GGUF` 在此路線用不上），
改用 `onnx-community/Qwen3.5-0.8B-ONNX`。
另外 `transformers.js` 沒有 llama.cpp 的 GBNF grammar，
**無法在解碼層強制 JSON**，必須靠 D009 的編號機制與加強的解析容錯補回來。

## 2026-08-18｜D024 離線語音辨識改用瀏覽器內 Whisper，不用 Web Speech API

## 2026-08-18｜D025 五項評分改由程式計算，模型只負責措辭

**決策：** 分數由程式依 rubric 計算（信任度軌跡、引導次數、挖到幾項隱藏需求、
是否約到時間、開放式問題比例、合規命中、是否在抗拒後仍推進）。
LLM 只做一件事：**依「分數＋證據清單」寫成教練會說的話**，
並由程式檢查回饋是否引用了給定證據，沒引用就重寫。

**為什麼：** handbook §8.1 警告小模型評分會退化成空泛稱讚，而評分是本產品的價值所在。
在手機上 judge tier 也只有 0.8B，直接讓它評分幾乎確定失敗。

但這不只是「為了離線而妥協」——它同時解決三個既有問題：

1. **分數變成可重現的**，handbook §4.6「測試不穩」的根因消失。
2. **評分標準變成可審閱的資產**（rubric 寫成程式＝寫成文件），
   而不是猜模型在想什麼。
3. **杜絕諂媚**：空泛稱讚的根源是模型想討好使用者；分數不由它決定，它就沒得諂媚。

這是 D021「難度由程式控制關鍵數值」與 §2.1 分工原則的直接延伸，
也回應 §9.3 第 15 條：**重要參數不要只用提示詞描述。評分是這個產品最重要的參數。**

**待定：** rubric 的權重與級距屬領域知識，必須由產品負責人審定，非工程判斷。

## 2026-08-18｜D027 放棄「零外部相依」，但把自帶流程寫成腳本

**決策：** 引入 `transformers.js` 與 `onnxruntime-web`，檔案自帶在 `docs/vendor/`（約 36 MB），
不用 npm install，並由 `tools/vendor.mjs` 產生。

**為什麼要放棄零相依：** V1 最自豪的數字之一是「外部相依 0 個」（handbook §1.1）。
但瀏覽器內推論不可能自己寫——ONNX Runtime 是一個 wasm 執行引擎。
硬撐這個數字會變成為了指標而犧牲產品。

**為什麼一定要寫成腳本而不是手動下載：**
自帶的 `transformers.web.min.js` 內含兩個 bare import specifier
（`onnxruntime-web/webgpu`、`onnxruntime-common`），那是給打包工具解析的。
瀏覽器解析不了，而且 **Web Worker 裡沒有 import map，所以連 import map 也救不了**。
必須改寫成相對路徑。

手改一次沒人記得，下次升級版本就會再踩一次。腳本裡有：版本鎖定、改寫清單、
以及「改寫後仍有 bare specifier 就報錯」的檢查——因為這個錯誤在瀏覽器裡
**`worker.onerror` 的訊息是空字串**，是最難查的那一類（handbook §9.2 第 9 條）。

**同時修掉的坑：** `tools/serve.mjs` 的 MIME 對照表沒有 `.mjs` 與 `.wasm`，
瀏覽器會拒絕載入模組，錯誤訊息只說「Failed to fetch dynamically imported module」，
看不出真正原因。

**另一個實測發現：** transformers.js 的 dist 只附了 `ort-wasm-simd-threaded.jsep.mjs`，
很容易以為 WebGPU 走 jsep；實際上 onnxruntime-web 1.26 的 webgpu bundle 請求的是
**asyncify** 變體。照 dist 附的檔案自帶會少檔案，且錯誤訊息同樣沒有指出正確檔名。

## 2026-08-18｜D028 模型必須用 `-OPT` 版本，不用同名的未優化 repo

**決策：** 本機模型固定為 `onnx-community/Qwen3.5-0.8B-ONNX-OPT`。

**實測依據（2026-08-18，RTX 4060、q4f16、WebGPU、同一份提示詞）：**

| repo | prefill 每 token |
|---|---:|
| `Qwen3.5-0.8B-ONNX` | 165～171 ms |
| `Qwen3.5-0.8B-ONNX-OPT` | 1～2 ms |
| `Qwen3-0.6B-ONNX`（傳統 dense，對照組） | 0.8 ms |

**165 倍。** 未優化版本 GPU 使用率只有 19%，且隨提示詞長度線性成長，
882 token 的提示詞跑兩分半仍未完成。推測 Qwen3.5 的混合架構
（Gated DeltaNet 的 conv 與 recurrent 狀態）在未優化的圖裡被展開成逐 token 的序列運算。

**為什麼要記成決策而不只是筆記：**
1. 未優化的 repo 是搜尋時的第一個結果，而且 README 的官方範例就是用它。
2. 兩者的模型權重、量化、行為完全相同，**只有速度差 165 倍**，
   任何紙面比較都看不出來。
3. 對照組證明了問題不在瀏覽器、不在 WebGPU、也不在 0.8B 這個尺寸——
   如果沒做這個對照，很容易誤判成「路線 A 不可行」而放棄整個方向。

**啟示（補充 handbook §9.1 第 3 條）：** 「不要只看紙面規格選模型」要再往前推一步：
**同一個模型的不同匯出版本也必須實測。** 為此保留 `docs/lab-min.html` 的
`?sweep=` 模式——它讓「換一個 repo 會不會好」在三分鐘內有答案。

## 2026-08-18｜D029 角色扮演不再要求模型輸出 JSON，每回合的數字全部由程式計算

**決策：** 本機模型模式下，角色扮演的模型輸出改為**純文字一句話**。
`trust_delta`、`revealed`、`end` 三個欄位不再向模型索取：

| 欄位 | 改由誰決定 | 依據 |
|---|---|---|
| `trust_delta` | `scoring/turn-signals.js` 依業務員這一回合的行為計分，再依難度夾住區間 | D021、D025 |
| `revealed` | 同上，用實詞 2-gram 比對客戶回話與隱藏需求 | D009 的延伸 |
| `end` | `session.js` 狀態機（本來就是） | D004 |

**為什麼（實測逼出來的）：**

第一輪只做提示詞壓縮＋JSON 前綴，四個欄位從 0／5 變成 5／5，看起來成功了。
但數字全是假的——`trust_delta` 五回合都填 0（照抄示範值），信任度完全不動，
難度系統等於沒運作；`revealed` 五回合都是空陣列，隱藏需求 0／3。

接著調高 temperature 讓台詞不要重複，欄位又掉到 2／5，還出現 `trust_delta: 95`。

| temperature | 症狀 |
|---|---|
| 0.2 | 五回合幾乎逐字重複同一句台詞 |
| 0.65 ＋ JSON | 台詞有變化，但欄位掉到 2／5、數值亂填 |
| 0.65 ＋ 純文字 | 結構問題全部消失（因為不再需要結構） |

**「要變化」與「要結構」在 0.8B 上是衝突的。** 純文字模式不是在兩者間取平衡，
而是把衝突整個移除：模型只做它擅長的（這個客戶會怎麼回話），
結構與數字由程式負責。

**量到的效果：**

| 指標 | 壓縮＋JSON | 純文字＋程式算分 |
|---|---:|---:|
| 平均每回合 | 3,067 ms | **1,396 ms**（達成規格 §29 的 ≤2 秒） |
| 提示詞 token | 844 | 756 |
| JSON 解析失敗 | 0／5 | 結構上不可能發生 |
| 信任度是否會變動 | 會（程式算） | 會（程式算） |

**副作用（要記住）：** 雲端模式仍然使用 JSON 版提示詞，因為大模型填得出有意義的數值，
而且 `revealed` 由模型判斷比程式的字面比對更準。
**所以現在有兩條提示詞路徑，`prompts.js` 與 `prompts.small.js`。**
兩者的分界線是「模型有沒有能力做語意判斷」，不是「本機或雲端」——
日後若本機跑得動 2B 以上，這條線要重新畫。

**啟示（補 handbook §9.3 第 15 條）：**
「重要參數不要只用提示詞描述」的下一步是
**「模型做不到的判斷，不要假裝它做得到」**。
逼一個 0.8B 模型輸出它不理解的數字，得到的不是壞數據，是**看起來正常的壞數據**——
欄位齊全、格式正確、值恆為 0。那比明顯的失敗危險得多（handbook §9.2 第 9 條）。

## 2026-08-18｜D030 提示詞裡不得出現可照抄的示範台詞

**決策：** 給小模型的提示詞一律只描述行為，不放任何引號內的示範句子。

**實測依據：** `prompts.js` 的 `DIFFICULTY[1].rules` 寫著
「你要善意地幫他接話，例如『你慢慢說沒關係』『你是說……的意思嗎？』」。
實測發現 0.8B 在 `guidance = 0`（完全沒觸發引導機制）的回合，
也把「你慢慢說沒關係，我聽得很清楚」原句講出來，連續兩回合都講。

大模型看得懂「例如」是舉例；**小模型會把它當成台詞。**

**做法：** `prompts.small.js` 的難度描述改寫成純行為
（「對方講得結巴或沒重點時，你不會不耐煩，會用自己的話幫他把問題問清楚」），
一個引號都不留。同時新增程式層的鸚鵡式重複與自我重複偵測，攔到就重新生成。

| 模型 | 下載 | 每回合 | 台灣繁中 | 對話品質 |
|---|---:|---:|---|---|

| Qwen3.5-2B-OPT | 1,581 MB | 2,091 ms | ⚠ 出現簡體 | ❌ |

0.8B 的實際輸出是「那花多久能拿到貨？」「好巧啦！」——
新人會以為是自己講錯話。handbook §9.3 第 14 條：
**訓練工具打擊使用者信心，等於失去存在意義。**

## 2026-08-18｜D032 瀏覽器內推論的三個硬限制（選模型時必查）

**① 單一 ONNX 檔不得超過約 1.5 GB。**
`Qwen2.5-1.5B-Instruct` q4 是單檔 1,788 MB，載入時 `std::bad_alloc`。
不是 GPU 記憶體不足（4060 有 8 GB），是 ORT-web 的 wasm 記憶體上限。
Qwen3.5 系列把權重拆成 embed／decoder／vision 三檔，因此 3 GB 的 4B 反而載得進去。
→ **選模型時要看「檔案怎麼切」，不只看總大小。**

**② 同一個模型的不同量化，可用性可能是 0 或 1，且必須實測。**
`Qwen2.5-1.5B` 的 q4f16 在 WebGPU 上輸出純亂碼（數值精度問題）、q4 載不進去，
整個 repo 在瀏覽器裡沒有可用組合。已在 `models.js` 標記 `unusableInBrowser`。
這是 D028（同一模型的 OPT 與非 OPT 差 165 倍）的同類問題再一次出現。

**③ Qwen3 世代預設開啟 thinking，必須在對話模板層關掉。**
不關的話 `Qwen3-0.6B` 會先產生一整段簡體中文的思考過程，
每回合 3.8 秒有大半花在思考，而且會外洩到對話氣泡。
已在 `worker.js` 統一傳 `enable_thinking: false`。
程式層另外處理「未閉合的 `<think>`」——被 `max_new_tokens` 截斷時沒有結束標籤，
只用成對標籤的正規表示式會漏掉（handbook §9.2 第 9 條：會安靜給錯答案的 bug 最危險）。

## 2026-08-19｜D033 新增第二條推論路線（GGUF／wllama），與 ONNX 路線介面一致

**決策：** 除了 `transformers.js`（ONNX），再加 `wllama`（llama.cpp 的 WASM 綁定）執行 GGUF。
兩個執行層的介面完全相同（`plan_` / `load` / `generate` / `abort` / `dispose`），
由 `models.js` 的 `engine` 欄位決定用哪一個。

**為什麼（實測逼出來的）：** 使用者指定手機優先並建議試 MiniCPM5-1B。
查證發現 **transformers.js 4.2.0 完全不支援 MiniCPM 架構**
（grep 自帶 bundle：Qwen2／Qwen3／Qwen3.5／Gemma3／DeepSeek2 都在，`minicpm` 零命中），
而 MiniCPM 官方只出 GGUF／MLX／MNN。

**這是比「模型好不好」更根本的限制：** 推論引擎決定了模型選擇的範圍。
綁單一引擎＝把選擇權交給那個引擎的支援清單。

**三個附帶收穫：**

1. **離線快取問題解除。** §13.5 記錄 Cache API 存不了 436 MB 權重
   （`Failed to execute 'put' on 'Cache'`）；wllama 用 OPFS，實測第三次載入只要 2.8 秒、
   完全不碰網路。**「完全離線」在 GGUF 路線上是成立的。**
2. **grammar／json_schema 可用**（實測 grep wasm 確認），
   等於可以把 §14 因為 0.8B 而放棄的 JSON 欄位契約重新拿回來，且零解析失敗。
3. GGUF 生態的模型選擇多一個數量級。

**選引擎前的檢查清單（往後照這個順序做）：**
① grep 引擎二進位／bundle 確認架構在不在　② 確認有無 grammar 能力
③ 確認快取機制（OPFS vs Cache API）　④ 才開始下載模型

## 2026-08-19｜D034 對 assistant 對齊過強的模型改用「續寫模式」而非對話模式

**決策：** 角色扮演在 GGUF 路線上使用 `createCompletion`（續寫）而非
`createChatCompletion`（對話），提示詞以逐字稿形式結尾於「${客戶名}：」。

**為什麼：** MiniCPM5-1B 在 chat 模式下完全不演角色，回的是客服口吻
（「建議您諮詢保險產業的客服熱線」），甚至覆述我們的重試指令
（「我會注意不要重複說話或過度取訪」）。

那是 assistant 對齊太強的典型症狀：**它把每一段輸入都當成「要協助的請求」。**
提示詞加規則沒有用，因為問題不在它不懂規則，而在它的角色被對話格式本身固定了。

續寫模式不給它請求，給它逐字稿讓它接著寫下一句。
**角色由文字結構決定，而不是由模型願不願意配合指令決定。**

**實測效果：**

| 指標 | chat 模式 | 續寫模式 |
|---|---:|---:|
| 平均每回合 | 1,308 ms | **783 ms** |
| 平均首 token | 783 ms | **571 ms** |
| 角色正確 | ❌ 客服口吻 | ✅ 是客戶在說話 |

**啟示（與 D029 的 JSON 前綴同一條）：**
**用結構逼出行為，不要用規則請求行為。** 這條原則在小模型上一再成立：
JSON 前綴讓它不可能輸出散文；續寫格式讓它不可能變成助理。
兩者都不是「更用力地要求」，而是把選項移除。

**注意：** 目前的模型比較因此變得不公平——Qwen 走 chat、MiniCPM 走續寫。
要判斷模型本身的優劣，必須把續寫模式也套到 Qwen 上再比一次（計畫書 §17.5 G2）。

## 2026-08-19｜D035 1B 級模型改用 Q8_0；量化損失必須單獨驗證

**決策：** MiniCPM5-1B 使用 **Q8_0**（1,154 MB）而非 Q4_K_M（688 MB）。

**實測依據：** Q4_K_M 的輸出會出現不成句的詞——「但您問得來」「請告訂時」。
換成 Q8_0 後，同一份腳本、同一個模式，**所有句子都成句**，而且第一次挖到隱藏需求。

| | Q4_K_M | Q8_0 |
|---|---:|---:|
| 下載 | 688 MB | 1,154 MB |
| 每回合 | 783 ms | 897 ms |
| 語法 | ❌ 偶有不成句 | ✅ 全部成句 |

**啟示：** 1B 級模型對量化的敏感度遠高於大模型。
先前我們把「語句不通」歸因於模型能力，其實有一部分是量化損失。
**選型流程要加一步：同一個模型至少測兩種量化，再判斷它的能力上限。**
這是 D032 第②條（同一模型不同量化可用性是 0 或 1）的延伸——
那一條講的是「能不能跑」，這一條講的是「跑起來的品質」。

**代價要誠實記錄：** +466 MB 對手機是實質負擔，iPhone 能不能載入 1,154 MB 仍未驗證。

## 2026-08-19｜D036 續寫模式的停止條件用換行，不用角色標籤

**決策：** 續寫模式的停止條件第一個是換行 `\n`，角色標籤僅作第二道防線。

**為什麼（我自己踩的坑）：** 原本用精確字串 `'業務員：'` 當停止條件。
Qwen3.5-0.8B 實際輸出的是「業務員 :」「業務員……」「業務苑 ...」「業務委員」——
**近似變體全部漏掉**，模型一路自己編完整段對話，該回合完全不能用。

我在做的事情等於「列舉模型可能拼錯的所有方式」，那是永遠列不完的。
回到問題本質：**續寫模式的答案本來就只有一行。** 換行是結構性的停止點，
不依賴模型怎麼拼字。

**這與 handbook §9.2 第 6 條同型：** 不要用文字比對去分類／攔截，
要找結構上不可能出錯的判準。當時的教訓是「不要用錯誤訊息文字分類錯誤」，
這次是「不要用角色標籤文字判斷輸出結束」。

## 2026-08-19｜D037 新增「過度順從」與「照抄人設」兩項程式層攔截

**決策：** `turn-signals.js` 新增 `isTooCompliant()` 與 `copiesPersonaText()`，
攔到就帶著**具名的**修正指示重新生成。

**① 過度順從（比講不通更危險）**

實測：業務員用結巴、沒重點的開場問「下週三過去說明二十分鐘可以嗎」，
客戶回「好的，請您不要擔心，這個保險我一定會買。」

**秒答應購買會給新人虛假的成功感**，讓他以為那套爛開場是有效的。
handbook §9.3 第 14 條說訓練工具不能打擊信心；這一條是它的反面——
**也不能給假的成功**。兩者一樣會毀掉訓練價值。

判定沿用 `DIFFICULTY` 本來的規則：Level 1「會答應合理的請求（例如約時間）」，
所以答應見面放行、承諾購買攔下。**難度規則本來就寫清楚了，只是以前沒有程式在執行它。**

**② 照抄人設文字**

模型把隱藏需求的原句幾乎逐字念出來。程式偵測得到「碰到主題」（好事），
但照抄設定文字不像真人講話。這是 D030 的同一個病換了照抄對象。

**③ 重試指令必須指名問題**

原本重試只說「剛才的回答不對」，對小模型沒有作用。
現在依攔到的類型給具體指示（「你答應得太快了」／「不要照著設定的文字念」／
「你把自己說成打電話來的人了」）。**含糊的糾正對小模型等於沒有糾正。**

**已知缺口：角色反轉。** 「我還有兩個保險產品供您選」沒有自稱業務員，
但扮演了供給方，三個現有檢查都攔不到。這是同類問題的第三種變形，待補。

## 2026-08-19｜D038 角色錯誤有三種變形，需要三個獨立檢查

**決策：** `turn-signals.js` 的角色檢查拆成三個獨立函式，不合併成一個。

| 變形 | 症狀 | 檢查 |
|---|---|---|
| 明說身分 | 「我是做保險的」 | `claimsToBeAgent()` |
| 複製文字 | 逐字念出隱藏需求的設定原文 | `copiesPersonaText()` |
| **做業務員的事** | 「我還有兩個保險產品供您選」「請您查閱」 | `invertsRole()` |

**為什麼不合併：** 三者的修正指示完全不同——
第一種要說「你是接電話的那一位」，第二種要說「用你自己的口語講」，
第三種要說「你是客戶，不是賣東西的人」。
**合併成一個檢查就只能給一個含糊的指示，而含糊的糾正對小模型等於沒有糾正**（D037 第③點）。

這是 handbook §9.2 第 8 條的同型：相似的症狀可能是完全不同的問題，
混在一起會給錯建議。

**誤判防範：** 客戶講「我們公司有幫我們保團保」是完全合理的發言，
所以 `invertsRole()` 只看「提供／安排給對方」這個行為，不看「公司」「保險」這些詞。

**同時記錄一個限度：** 六項攔截全部歸零之後，MiniCPM5-1B Q8_0 的輸出仍然
「一次好一次壞」（同一份腳本兩次執行，一次對題、一次語意不通）。
**程式層能保證「不會做錯事」，但不能保證「講得好」。** 後者是模型容量。

## 2026-08-19｜D039 模型下載改為自建路徑，不用 wllama 的下載器

**決策：** GGUF 路線的模型取得改成兩段分開做——先整檔下載並寫入 OPFS，
再把 `File` 交給 `wllama.loadModel()`，繞過 `loadModelFromUrl` 的內建下載與快取。

**實測依據（iPhone 14 Pro，iOS 18.7，家用 Wi-Fi）：**

用 wllama 的下載器載 1,154 MB，**一分鐘只跑了 1 MB**。
但同一支手機、同一台伺服器分項量測：

| 量測項目 | 結果 |
|---|---|
| 純下載 32 MB（不寫入） | **11.9 MB/s** |
| 純寫入 OPFS 32 MB（不碰網路） | **533 MB/s** |
| 32 個 1 MB 小請求 | 20.7 MB/s |

**網路與儲存都沒問題**，所以瓶頸在 wllama 把兩者串起來的方式
（每收到一小塊就 `await` 一次寫入，在 iOS 上代價極高）。

改成自建路徑後（桌面驗證）：

| | 時間 |
|---|---:|
| 首次：1,154 MB 下載＋寫入 OPFS＋載入 | **9.2 秒** |
| 第二次：純 OPFS 命中，完全不碰網路 | **4.0 秒** |

**方法論記錄：** 這個問題能定位是因為**先分項量測再修**。
如果直接猜「網路慢」或「iOS OPFS 慢」去改，兩個方向都是錯的。
為此保留 `docs/nettest.html`——它把「網路 / 儲存 / 每請求成本」三件事分開量，
下次遇到「載入很慢」可以在一分鐘內知道要修哪一層。

## 2026-08-19｜D040 Safari 沒有 ReadableStream 的 async iterator

**症狀：** iPhone 實機載入失敗，訊息是
`undefined is not a function (near '...chunk of res.body...')`。

**原因：** 我寫的是 `for await (const chunk of res.body)`。
**Chrome 支援對 ReadableStream 做 async 迭代，Safari（含 iOS 18.7）沒有實作。**
桌面 Chromium 完全測不出來。

**修法：** 一律用 `res.body.getReader()` 加 `while` 迴圈——三家瀏覽器都支援。

**為什麼記成決策而不只是修 bug：**

1. 這一類「只有 Safari 缺」的 API 差異會反覆出現，而本專案的主要目標裝置是 iPhone。
   **桌面 Chromium 綠燈不代表 iOS 能跑。**
2. 我在 `nettest.html` 的測試 ③ 用了同一個寫法。
   使用者當時只跑了 ①②④，所以沒暴露——**診斷工具本身也會有平台 bug**，
   而它給的假象是「網路和儲存都正常，所以程式沒問題」。
3. 對策：凡是要在 iPhone 上跑的程式碼，**Web API 一律挑三家都有的寫法**，
   而不是挑 Chrome 上最順手的。

**順帶修掉的第二個問題：** 原本的實作先寫 `.part` 再複製成正式檔名
（因為 OPFS 沒有 rename）。那等於在手機上多寫一次 1.1 GB。
改成直接寫最終檔名，並在完成後用 `content-length` 比對大小；
不符就刪掉重下——半個檔案會讓 wllama 給出很難查的錯誤。

## 2026-08-19｜D041 iPhone 上「瀏覽器內推論」不可行；手機離線需改走原生 App

**結論（iPhone 14 Pro，iOS 26.6，實機驗證）：**
路線 A（瀏覽器內 WebGPU）在 iPhone 上不成立。三個天花板同時存在：

| 限制 | 實測 |
|---|---|
| WebGPU 推論 | **崩潰**——wllama 在生成時、transformers.js 在載入時，兩個獨立引擎都崩 |
| CPU 推論 | 可跑，但 2.9 tok/s、每回合 8.2 秒，且只在 105 MB 的 135M 模型上 |
| 可載入的模型大小 | 105 MB ✅／688 MB ❌（**與記憶體無關**，見下） |

**最關鍵的排除：崩潰不是記憶體不足。**
實機量到 wasm 可成長到 2 GB、ArrayBuffer 可配置 3 GB（都是撞到測試上限才停），
而 688 MB 就崩。若沒有先量這兩個數字，幾乎必然誤判成「手機記憶體不夠，換更小的模型」，
然後在錯誤的方向上反覆嘗試。

**WebGPU 的能力回報會騙人。** iPhone 上 `navigator.gpu` 存在、`shader-f16` 支援、
`maxBufferSize` 回報 1,074 MB——看起來一切就緒，實際跑推論就崩。
**能力偵測只能告訴你 API 在不在，不能告訴你它撐不撐得住真實工作負載。**
唯一可信的是實機跑完整流程。

**桌面的結論相反：完全可行**（MiniCPM5-1B Q8 每回合 804 ms、Qwen3.5-4B 4,340 ms）。
所以「完全離線」在桌面成立、在 iPhone 不成立。

**因此手機離線只剩一條路：原生 App**（`D:\Hao+App\Ai_Sales_Coach_App`）。
Core ML／MLX 不受 WebKit 的限制，而 handbook §7.1 早就列出原生化的四個理由，
本次實測為它補上第五個、也是最硬的一個：**iPhone 上的離線推論只有原生做得到。**

**待使用者裁決**（前一次的 F1～F4 是在「手機優先」的前提下選的，該前提已被推翻）：
見 `12_LOCAL_MODEL_DEV_PLAN.md` §20.3。

## 2026-08-19｜D042 能力偵測不等於可用性；驗收一律要跑完整流程

**這一輪連續踩到三次同型的坑，值得單獨記一條原則。**

| 看起來 | 實際 |
|---|---|
| `navigator.gpu` 存在、`maxBufferSize` 1,074 MB | WebGPU 推論會讓分頁崩潰 |
| 記憶體量到 2 GB／3 GB 可用 | 688 MB 的模型載不進去 |
| 桌面 Chromium 全綠 | Safari 缺 `ReadableStream` 的 async iterator（D040） |

**原則：** 能力偵測（feature detection）只能回答「API 在不在」，
不能回答「它撐不撐得住我們的工作負載」。
本專案的偵測畫面（`caps.js`）因此必須被理解為「篩掉明顯不行的裝置」，
**不能當成「這台裝置可以用」的保證**。

實務上這代表：
1. 任何新裝置／新瀏覽器的支援，都要跑「載入 → 五回合 → 看數字」的完整流程才算驗收。
2. 分項量測（`nettest.html`、`memtest.html`）的價值在**排除**，不在確認：
   它們能證明「不是網路」「不是記憶體」，但不能證明「所以會成功」。
3. 這一輪 `n_ctx` 的錯誤也是同型：前兩回合正常，第三回合才爆。
   **短測試看不到隨對話長度累積的問題**（handbook §10.1）。

## 2026-08-20｜D043 ONNX 的外部權重可能切成多檔；鏡像與載入都必須處理

**症狀：** 4B 從本機鏡像載入時，畫面停在「載入中」，console 才看到真正的原因：
`Could not locate file: ..._decoder_model_merged_q4f16.onnx_data_1`。

**原因：** ONNX 的外部權重檔會被切割。
Qwen3.5-4B 的 decoder 有 **`.onnx_data`（2,066 MB）與 `.onnx_data_1`（368 MB）兩個檔案**，
而我的鏡像工具只抓 `_data`。

**為什麼在小模型上測不出來：** 0.8B 與 2B 的每個子模型都只有一個 `_data`。
**這個 bug 只在夠大的模型上出現**——也就是我們真正想用的那一個。

**修法：** 鏡像時多列 `_data_1`／`_data_2`／`_data_3` 為候選，不存在會收到 404 並自動略過。

**方法論價值（這次判斷對了）：** 使用者原本要直接在 iPad 上測 4B，
我先在桌面用鏡像跑一次才發現這個問題。若沒有先驗，
使用者會在 iPad 上看到「載入中卡住」——而**手機上看不到 console**，
那會被誤判成「iPad 也撐不住 3 GB」，得到完全錯誤的結論。

**推論：** 任何「只在大模型上才出現」的問題，都必須在桌面先用同一條路徑驗過一次，
再交給沒有開發者工具的裝置。這是 D042（能力偵測不等於可用性）的操作面補充。

**同時修掉的另一個缺陷：** 下載器沒有續傳。
2.4 GB 的單檔在一般網路上 `ECONNRESET` 是常態，斷了就得從 0 開始。
現已改成用 Range 從 `.part` 續傳並重試六次。

## 2026-08-20｜D046 瀏覽器內 GGUF 的硬天花板是 2 GiB；Gemma 4 E2B 因此不可行

**天花板：約 2 GiB（2,147 MB）。** wllama 把整個模型放進 32 位元 wasm 的線性記憶體。

桌面實測，三個檔案跨過這條線，**錯誤訊息完全相同**
（`Invalid typed array length: 1163217991`）：

| 模型 | 大小 | MiB | 生成 |
|---|---:|---:|---|
| Qwen3-4B Q3_K_M | 2,076 MB | 1,979 | ✅ **目前最大可用** |
| Qwen3-4B UD-Q3_K_XL | 2,132 MB | 2,033 | ❌ |
| Qwen3-4B IQ4_XS | 2,271 MB | 2,166 | ❌ |
| Gemma 4 E2B Q3_K_M | 2,537 MB | 2,420 | ❌ |

**邊界落在 1,979 與 2,033 MiB 之間**，所以真正的限制是
「模型 ＋ 執行期開銷 < 2,048 MiB」，換算成檔案大小約 **2,100 MB**。
我一度以為 UD-Q3_K_XL「剛好在 2 GiB 以內」所以可行——實測推翻。
**要算的是模型加執行期，不是只算檔案。**

**我一度誤判。** 第一次看到這個錯誤時（Gemma），我把它歸因於
「gemma3n 家族的逐層嵌入張量太大」——那個推論看似合理（E2B 確實有特殊張量），
但**同一個常數接著在 Qwen3-4B 上出現**，證明它與模型架構無關。
教訓：**一個數字在兩個無關的系統上出現，就不該用其中一個系統的特性去解釋它。**

**Gemma 4 E2B 的結論：** 它最小的量化 IQ2_M 就是 2,291 MB（2,185 MiB），
**已經超過天花板**，所以在瀏覽器路線上結構性不可行——與裝置無關。

這也解釋了為什麼使用者在原生 App（Locally）上跑得很順：
原生走 Metal，沒有 32 位元 wasm 的位址空間限制。
**同一個模型、同一台 iPad，原生可行、瀏覽器不可行**——
這是「原生 vs 瀏覽器」差異最乾淨的一個實例。

**設計含意：** 模型選型的第一個篩選條件是「檔案 < 2,147 MB」，
而不是「裝置記憶體夠不夠」。`models.js` 已把這條記在 `ceilingNote`。

## 2026-08-20｜D047 感知延遲要量「客戶何時開始說話」，而且必須先暖身

**兩個發現，都來自桌面實測（Qwen3-4B Q3、串流接系統 TTS）。**

**① 該量的不是生成時間，是「開始說話」的時間。**

語音對練裡使用者感受到的延遲是「對方何時開口」，不是「何時說完」。
規格 §29 的 2 秒目標應該用前者衡量。因此新增 `docs/voicelab.html`，
量五個時間點：送出 → 首 token → **客戶開始說話** → 生成完成 → 語音播完。
「開始說話」用 `SpeechSynthesisUtterance.onstart` 取得，不是估算。

**② 不暖身的第一回合會慢 20 倍。**

| | 沒暖身 | 暖身後 |
|---|---:|---:|
| 首 token | 6,998 ms | **795 ms** |
| 感知延遲 | 7,708 ms | **1,522 ms** |

兩個原因：WebGPU 的 shader 首次編譯，以及 llama.cpp 對**相同前綴**的 KV cache 重用
（我們的 system 提示詞＋兩組角色示範每回合都一樣，約 700 token，
所以第二回合起幾乎不必重新 prefill）。

**因此 `GgufRuntime.warmup(prompt)`：載入完成後立刻用真正的提示詞前綴生成 1 個 token，
把一次性成本挪到使用者還沒開口之前付掉。** 暖身本身 6.4 秒，但不算進對話延遲。

**設計含意：** 暖身必須用**真正要用的提示詞前綴**，否則 KV cache 重用不會發生在對的地方。
這也意味著提示詞前綴應該盡量固定——每回合都變的前綴無法被重用。

**③ 一個沒有預期到的限制：回答很短時，串流 TTS 幾乎沒有幫助。**

實測有一輪的「客戶開始說話」（7,708 ms）竟然晚於「生成完成」（7,234 ms）：
回答只有 8 個 token、一句話，**第一個標點就是最後一個字**，串流無從提前開口。

角色扮演的回答本來就短（1～3 句、10～30 字），所以串流的價值有限，
真正的槓桿是首 token 本身（＝暖身＋前綴 KV 重用）。
串流仍值得保留——長回答（教練回饋、商品說明）會用到。

## 2026-08-20｜D048 本機版接進產品的方式：長得像 gateway 的物件，狀態機一行不改

量測階段結束，開始把已驗證的執行層接進真正的 App。

**接縫在哪裡：`session.js` 只透過一個方法跟外界說話——`gw.generate(prompt, opts)`。**

因此本機版做成一個「長得像雲端 adapter 的物件」（`docs/engine/local/gateway-local.js`），
整台狀態機（INTAKE → READY → ROLEPLAY → COMPLETED → FEEDBACK_READY）、
合規攔截、卡住偵測、信任度夾定、結束條件判定**一行都不用改**。
紅線檔案（`prompts.js`／`session.js`／`compliance.js`／`advisor.js`／`platform.js`）全部維持不動。

`api.js` 只多了一個不需要金鑰的連線函式 `loginLocal()`，以及三處 optional call
（`useSession?.()`／`useArgs?.()`）——雲端 adapter 沒有這些方法，對它是 no-op。

**三種呼叫的分工，是量測結果決定的，不是偏好：**

| session.js 的呼叫 | 雲端版 | 本機版 | 理由 |
|---|---|---|---|
| 建立人設（約 4,000 token JSON） | 模型 | **程式組裝** | 4B 在 17～22 tok/s 下要跑三到四分鐘 |
| 每回合對話 | 模型 | **模型**（唯一一處） | 已驗證感知延遲 0.77 秒 |
| 評分回饋（約 8,000 token JSON） | 模型 | **程式計算** | 比人設更長 |
| 痛點分析 | 模型 | **程式組裝** | 原型本身就帶著痛點與異議 |

**結論一句話：模型只做即時的語言生成，其餘全部由程式負責。**

這是整個量測階段最重要的收斂——小模型做結構化長輸出會塌掉
（實測過 4B 把 `trust_delta` 一律填 0、`revealed` 一律填 `[]`），
但做「接下來這位客戶會說的一句話」表現得很好。

**附帶的好處不是省時間，是品質可審閱。** 手寫的八個客戶原型（護理師單親、
小工廠老闆、新手父母、屆退教師、社會新鮮人、雙薪房貸、自由接案、三明治照顧者）
比小模型即興生成的更貼近台灣壽險現場，而且人設可重現——
同樣的輸入產生同樣的客戶，使用者回報問題時我們重現得出來。

## 2026-08-20｜D049 程式算分的分數下限是 1.0，不是 0

第一版程式算分給「幾乎什麼都沒做對」的新手打了 **fluency 0、awareness 0**。

這違背這個產品自己的前提。`prompts.js` 的難度系統註解早就記錄過同一個判斷：

> 實測發現太弱——連 Level 1 的客戶都會冷淡、想掛電話，
> 對新進夥伴是打擊信心而不是訓練。

**0 分傳達不出任何可以行動的資訊，只會讓他不想再開第二次。**
1.0／5 仍然清楚表示「這一項要重練」，而真正的資訊在改善建議裡。
只有完全沒有發言（`turns === 0`）才會出現 0 分。

**同一輪修掉的反向問題：表現好的人拿到 0 條建議。**
教練工具的價值在「下一步是什麼」。沒有偵測到缺口時改為給進階建議——
還有隱藏需求沒挖到就教怎麼追第二層，全挖到了就叫他把難度調高。

**兩個錯誤是同一個病：把「評分」當成目的，而不是把「下一次進步」當成目的。**

## 2026-08-20｜D050 串流播報要在生成途中就守門，不能等生成完才檢查

串流 TTS 的意義是「第一句一出現就開口」。但這與輸出驗證直接衝突：
等生成完才檢查就沒有串流了；完全不檢查就會把「我是業務員…」這種
跳出角色的句子**直接念給使用者聽**。

**做法：前綴守門（`badPrefix`）。**
在累積的前綴上跑幾個便宜、不會誤判的正規表示式（自稱業務員、角色反轉、
把自己名字又寫一次、以「業務員：」開頭），攔到就：
中止生成 → 通知呼叫端取消已說出的話 → 清掉畫面上的泡泡 → 降溫重抽。

完整的六項檢查仍在生成結束後由 `turnSignals` 做，前綴守門只是提前攔截。

**兩個必須寫下來的細節：**

1. **被守門攔下的那一輪一定要算「壞」。** 截斷的半句話不一定會被六項檢查判壞，
   但它絕對不能拿去當客戶說的話。（第一版漏了這個，會用半句話收場。）

2. **最終文字與串流出去的文字可能不一樣。**
   `validateRoleplay` 會裁切過長的句子、攔截重抽會整段換掉、卡住時會用保底句。
   已經念出去的跟畫面上的不一致是很糟的體驗，所以 `app.js` 會比對，
   不一致就取消重念。

**還有一個老坑的複驗：`voice.unlock()` 必須在按鈕點擊的第一行呼叫，
不能等模型載完再做。** 模型載入要幾十秒，`await` 之後已經不是使用者手勢的上下文，
iOS 的 speechSynthesis 就再也不會出聲。

## 2026-08-20｜D051 本機模式下三個功能明確標示為不支援，而不是讓使用者撞錯誤

商品行銷（要讀 PDF 教材）、理賠諮詢（要長篇條款比對）、行銷諮詢（要長文回覆）
在本機模型上做不到。

三種處理方式裡選最後一種：

1. ~~讓它跑，產出品質很差的結果~~ ——最糟，使用者會以為產品就是這樣。
2. ~~讓它跑到一半才報錯~~ ——填完整張表單才撞牆。
3. **首頁就標示，點下去給明確說明。**

## 2026-08-20｜D052 接上產品後的第一次實機走查，抓到兩個提示詞層面看不見的缺陷

把本機路線接進真正的 App 之後，在桌面用**真模型**（Qwen3-4B Q3、真 WebGPU）
走完整流程：建立客戶 → 開始演練 → 三個回合。兩個缺陷都不是靠讀程式看出來的。

**① 模型照抄提示詞裡的示範句。**

第二回合客戶回了：

> 說真的…就是我要是有一天倒下了，家裡怎麼辦。

與 `roleplayRawPrompt` 裡的第二個示範**一字不差**。

最值得記下來的是：**七項程式層檢查裡，當時的六項全部通過。**
不是鸚鵡式重複（跟業務員說的不像）、不是自我重複（前幾回合沒說過）、
不是句內重複、沒有自稱業務員、沒有角色反轉、也不算照抄人設
（示範句不在隱藏需求裡）。**每一項都盡忠職守，而缺陷從它們中間走過去了。**

這是同一個病的第三次出現（`DIFFICULTY[1]` 的「你慢慢說沒關係」、
我自己寫的 one-shot「嗯…請問是什麼事？」）。前兩次都靠改提示詞解決，
但**改提示詞只降低機率，能保證的只有程式層的檢查**。

兩層修法：

- **移除來源**：示範句的唯一目的是建立逐字稿格式。一旦有了真實對話紀錄，
  格式已經由紀錄自己建立好，示範就只剩被照抄的風險。改成只在第一回合提供。
  附帶好處：提示詞短 79 字，而前綴仍單調成長（KV cache 重用不受影響）。
- **加上第七項攔截**：`copiesExample(say, SHOT_LINES)`，門檻 0.75。
  示範句原文從 `prompts.small.js` 匯出，**不在兩處各寫一份**——
  否則改了提示詞卻忘了改偵測，那道防線會靜靜地失效。

**② 模型會寫舞台指示，而 TTS 會把它唸出來。**

修好照抄之後，同一個回合變成：

> （停頓）大概就是女兒的未來吧。

內容是對的，但這是**語音**對練——`speechSynthesis` 會原音唸出「停頓」兩個字。
括號裡的東西是給讀者看的動作描述，不是客戶說出口的話。

`cleanPlainSay` 因此移除括號、星號、方括號三種變體（模型三種都寫過），
並收拾移除後相鄰的重複標點（「我…（想了一下）…應該」→「我……應該」→「我…應該」）。

**這兩個缺陷的共同點：只有在「真的把整條路徑跑起來」時才會出現。**
單元測試不會產生它們，讀程式也看不出來。實機走查是不可取代的一步。

**同一輪順手修掉的一個潛在錯誤：**
`cleanPlainSay` 原本用 `new RegExp('^' + name + ...)` 組正規表示式，
客戶名稱沒有轉義。目前的名稱都是「陳先生」這類安全字串，所以看不出問題，
但那是碰巧，不是設計。已改為先轉義。

**還有一件事必須寫下來：暖身原本沒有人呼叫。**
`LocalGateway.warmup()` 寫好了，卻沒有任何呼叫點——
第一回合實測 13.3 秒。接到 `/session/begin`（開始演練）之後變成 7.6 秒。
**寫好一個函式不等於它被用到**；D047 量到的 20 倍差距，差點就沒有生效。

暖身刻意不 `await`：呼叫點是「開始演練」，那時客戶的開場白正在播語音，
暖身剛好躲在使用者聽開場白與思考第一句話的時間裡。
代價是暖身可能還在跑，所以 `_turn` 開頭要等它結束——
同一個 wllama 實例不能同時跑兩個生成。

## 2026-08-21｜D053 「說的話跟顯示的文字對不上」有三個獨立原因

使用者在 iPad 實機回報：模型都跑得動，但**有時候 AI 說的話跟出現的文字對不上**。
追下去發現是三個各自獨立的原因，全部都是我自己造成的。

### 原因一：清洗在生成之後才跑，話卻在生成中就唸出去了

`gateway-local.js` 的 `onDelta` 把**原始** delta 送去 TTS（才有 0.77 秒的感知延遲），
但 `cleanPlainSay` 是在生成**結束後**才跑。於是凡是清洗會拿掉的東西——
「（停頓）」、「李先生：」前綴、句尾殘留的「業務員…」、超過 120 字被裁掉的部分——
**都已經先被唸出來，然後畫面才顯示清乾淨的版本**。

原本 `app.js` 有「不一致就取消重念」的退路，但那個退路本身就是症狀。

**修法：`SayStream` 逐字清洗器。** 只送出「確定不會被後續清洗拿掉」的字，
不確定的先扣住（未收尾的括號、可能是寫到一半的「業務員」、句尾引號）。
**最終的 say 就是這個串流吐出去的全部內容，不再另外清洗一次。**

關鍵是那個不變式：唸出＝顯示＝最終文字，是**建構出來的**，
不是靠兩段程式碰巧一致。兩個清洗器就會有兩個結果。

扣住造成的延遲很小（一般一到兩個字）。也順手驗證了 delta 的切法不影響結果——
真實的 delta 是多字 token，不是一個字一個字來。

### 原因二：救援保險絲會取消整個佇列，只重送第一段

昨天為了「iOS 偶爾整段不出聲」加的保險絲有兩個錯：

1. 它掛在**每一段**上，而 `speechSynthesis.cancel()` 取消的是**整個佇列**。
   第一段的保險絲會把還沒播的第二、三段一起取消，然後只重送它自己那一段。
   **結果是使用者只聽到第一句話，畫面卻顯示完整的一段。**
2. 時限 1,200 ms 太短。iPad 實測首次發聲是 765 ms，只剩 435 ms 餘裕——
   語音只要稍慢就會誤觸發，把好好的語音打斷。

**修法：** 保險絲只掛第一段；救援時重送**所有還沒播完的段落**並維持順序；
時限放寬到 2,600 ms。這個保險絲要對付的是「整段完全不出聲」，
那種情況多等 1.4 秒毫無差別，誤觸發的代價卻是真的打斷正常語音。
完成判定也從計數器改成以段落為單位——救援會重新排入同一段，計數器在那時會算錯。

### 原因三：我們自己的重抽會被聽見

第三個原因不是 bug，是取捨沒做好。

語音在 0.77 秒就開口，但七項程式層檢查要等生成結束（約 3.5 秒）才跑得完。
所以生成結束後才攔截到問題時，話已經唸出去了——取消重講聽起來就是
「唸一半突然停掉、換一句重講」。

實機抓到的例子：第一次生成是「嗯，我現在最放不下心的是，」（鸚鵡對方的問法，
`isEcho` 正確攔截），重抽後是「嗯，我現在最放不下心的是女兒的學費和生活費。」

**那為什麼不等驗證完再開口？** 因為感知延遲會從 0.77 秒變回約 3.5 秒，
超過規格 §29 的 2 秒。串流不是效能微調，是這個產品能不能用的前提。

**所以按「聽起來的傷害」把攔截分兩級：**

| | 項目 | 政策 |
|---|---|---|
| **硬性** | 自稱業務員、角色反轉、照抄示範句、照抄人設 | **一定重抽，即使已經開口** |
| **軟性** | 鸚鵡式重複、自我重複、句內重複 | **只在還沒開口時重抽** |

理由：讓使用者聽到「我是保險業務員」或聽到我們的提示詞被唸出來，
比聽到一次卡頓嚴重得多。反過來，客戶偶爾重複業務員的話還算像真人，
唸一半被切斷不像。軟性旗標仍然記錄在 `lastSignals` 裡，不會因為不重抽就消失。

### 順手改掉的一項

「李先生：」這種模型把自己名字又寫一次的情況，原本由 `badPrefix` 攔下重抽。
那是格式雜訊而不是跳出角色，`SayStream` 直接砍掉就好——
為它重抽一次要多等 3.5 秒，不值得。「業務員：」相反，那是真的跳出角色，仍然攔。

### 這一輪學到的

三個原因裡有兩個是**我為了修上一個問題而加的機制自己造成的**
（取消重念的退路、救援保險絲）。共同點是：
**它們都在「已經送出去的東西」上面做補救，而不是在源頭讓它正確。**

`SayStream` 是相反的做法——讓錯誤的內容從一開始就沒有機會被送出去。
這次測試從 110 項加到 124 項，其中 8 項專門釘住串流播報的行為，
因為這個元件已經出過兩次缺陷了。

測試伺服器沒有設 COOP/COEP，所以之前所有成功的 iPad 與桌面實測，

## 2026-08-21｜D055 公開部署的三個必要條件，缺一個就等於不能用

程式能上架不等於別人用得起來。這三件事缺任何一項，拿到手的人都會失敗。

**① 「自己下載」必須是預設，不是選項。**
wllama 內建的下載器在 iOS 上實測 1 MB/分鐘（D039），2 GB 要跑三十四小時。
原本只有 `?dl=self` 才啟用——對開發者夠用，對公開部署等於不能用。
**開發時的旗標與產品的預設值不是同一件事**，這一項我差點漏掉。

**② 依裝置分級，而且要能自我修正。**

三級都是實測過檔案大小的組合：Qwen3 4B Q3（2,076 MB）／MiniCPM5 1B Q8（1,154 MB）／
Qwen2.5 0.5B Q4（398 MB）。三道防線：裝置類別＋配額、崩潰記憶、使用者覆寫。

**只有崩潰記憶是真正可靠的。** D042 已經付過代價：iPhone 14 Pro 的記憶體探測
回報「wasm 2048 MB ✅、ArrayBuffer 3072 MB ✅」，然後載入時分頁被系統殺掉。
分頁被殺掉時 JS 完全沒有機會執行，連 try/catch 都攔不到——
所以不可能在當下記錄任何東西。

做法反過來：**載入前寫旗標，成功後清掉。下次開機若旗標還在，就代表上一次沒有活著回來。**
這是唯一能確定「這台裝置跑不動這個模型」的方法，因為它記錄的是實際發生過的事，
不是推測。實測驗證過：留下旗標 → 重新載入 → 自動加入黑名單、告知使用者、降到 MiniCPM5 1B 並說明原因。

**③ 2 GB 下載前必須先問。**
在行動網路上直接扣 2 GB 是實質傷害。改成兩步：偵測裝置 → 顯示要下載什麼、多大、
品質差異、為什麼選它 → 使用者確認 → 才開始下載。

**順帶修掉一個會擋住真實使用者的缺陷。**
第一版把 `navigator.storage.estimate()` 當權威。實測發現受限環境回報 `quota: 0`，
**而 OPFS 完全正常**（2 GB 模型讀寫都沒問題）。把 0 當成「沒空間」會把跑得動的裝置全部擋掉。
現在查不到或回報 0 一律當成「不知道」，讓使用者去試——
**擋住一台其實跑得動的裝置，比讓他試一次失敗更糟，因為他沒有第二條路可走。**

這個缺陷是實機走查抓到的，不是想出來的。第一次點下按鈕就看到
「可用空間只有約 0 MB，連最小的模型都放不下」——而同一個瀏覽器五分鐘前才剛跑完 2 GB 的模型。

測試從 124 項增加到 140 項，其中 16 項專門釘住分級邏輯的兩個方向：
夠保守（不要讓使用者下載完才崩潰）與不過度保守（不要擋住跑得動的裝置）。

## 2026-08-21｜D056 「自己下載改成預設」在公開部署路徑上根本沒有生效

使用者問「可以直接抓第三方 HuggingFace repo 而不用上傳到自己帳號嗎」。
答案是「已經是這樣了」，但去確認程式的時候發現一個嚴重的錯誤——
**而且正好在我前一天聲稱已經修好的地方。**

`runtime-gguf.js` 的判斷是：

```js
const src = this.mirrorBase ? new URL(this.mirrorBase + file, ...) : null;
...
: this.selfDownload && src        // ← 需要 src
  ? fetchToOPFS(src, ...)
: src ? loadModelFromUrl(src)
      : loadModelFromHF({ repo, file })    // ← 公開部署走這條
```

**公開部署沒有自架鏡像 → `src` 為 null → `selfDownload && src` 為假 →
自己下載整條被跳過，實際走的是 wllama 內建的下載器。**

那個下載器就是 D039 記錄的、在 iOS 上 1 MB/分鐘的那一個。
也就是說 D055 寫的「自己下載改成預設」對真正的公開部署完全沒有作用。

**這件事我沒有從程式看出來，是因為要回答一個看起來無關的問題才去讀那段程式。**
前一天的驗證用的是 `?mirror=1`（有鏡像 → src 不為 null → 走對的路徑），
所以測試通過了，而公開路徑從來沒被測過。
**用開發用的參數驗證產品路徑，會驗出一個假的通過。**

**修法：自己組 HuggingFace 的 URL，讓 `src` 永遠有值。**
順帶拿回了 revision 的控制權（見 D057）。

修完之後實測確認：下載走 `resolve/<sha>/<檔名>`、進度與剩餘時間正常、
自己的 `fetchToOPFS` 生效（Safari 安全的 reader、大小驗證、OPFS 快取）。

**但速度沒有變快**（公司網路 0.7～1.3 MB/s，瓶頸在網路不在下載器），
這一點要說清楚，不能把「修好了路徑」講成「變快了」。
真正的差別在 iOS——那只有 iPad／iPhone 實測能確認。

## 2026-08-21｜D057 第三方模型 repo 必須鎖 commit

模型檔不是我們上傳的，是抓 `unsloth`／`bartowski`／`openbmb` 的公開 repo。
好處是不必自己託管 2 GB；代價是把風險交到別人手上。

原本的 URL 是 `resolve/main/<檔名>`。**`main` 是會移動的分支。**
社群 repo 重新量化、改檔名（例如加上 `UD-` 前綴）、清掉舊量化都是常態——
一旦發生，**我們這邊什麼都沒改，但所有新使用者的第一次下載都失敗**，
而且我們不會事先知道。

改成 `resolve/<commit SHA>/<檔名>`。HF 上某個 commit 的內容不可變，所以：

| 風險 | 鎖 commit 之後 |
|---|---|
| 上游改名或刪檔 | 解決（舊 commit 仍然可取） |
| 上游替換檔案內容（供應鏈） | 結構上不可能 |
| 檔案大小改變 → 大小驗證失敗 | 不會發生 |

附帶的好處：**不需要在瀏覽器裡算 2 GB 的 SHA256。**
WebCrypto 沒有串流 API，那會要求整份 2 GB 放進記憶體——
而我們正是為了避開這件事才用串流寫入 OPFS。鎖 commit 用不可變性取代了雜湊驗證。

鎖定的版本（2026-08-21，都實測過 206 ＋ CORS ＋ 大小一致）：

| 模型 | repo | commit | 大小 |
|---|---|---|---|
| Qwen3 4B Q3 | `unsloth/Qwen3-4B-GGUF` | `22c9fc8a…` | 2,076 MB |
| MiniCPM5 1B Q8 | `openbmb/MiniCPM5-1B-GGUF` | `3d55fac8…` | 1,154 MB |
| Qwen2.5 0.5B Q4 | `bartowski/Qwen2.5-0.5B-Instruct-GGUF` | `41ba88db…` | 398 MB |

授權也一併查了：三個都是 apache-2.0、非 gated。
而且我們並沒有轉散布權重（檔案由 HF 提供），所以散布者的責任不在我們身上。

`selftest.mjs` 現在會檢查「分級裡的每個模型都鎖了 40 位十六進位的 commit、
檔名存在、大小與 `models.js` 一致」——升級上游版本時這三件事必須同時更新。

測試 140 → 155 項。

## 2026-08-21｜D059 崩潰記憶把「手動重整」誤判成崩潰

這是使用者跑到 MiniCPM5 的真正原因，而且是 D055 那個機制自己的缺陷。

崩潰記憶的做法是「載入前寫旗標、成功後清掉；下次開機旗標還在就是崩潰」。
問題是：**使用者在下載中按重新整理，也會留下旗標。**
手動重整和被系統殺掉，在原本的設計裡分不出來——
於是使用者重整一次，4B 就被永久列入黑名單。

**修法：監聽 `pagehide`，正常離開頁面時清掉旗標。**
`pagehide` 在重整、關閉、換網址時觸發；分頁被系統殺掉時**不會**觸發。
那個差別正好就是我們要的。

代價：iOS 把 App 切到背景時 `pagehide` 也會觸發，若系統接著殺掉分頁，
那次真正的崩潰就不會被記錄。這個方向是刻意選的——
**少記一次崩潰，遠好過把一台跑得動的裝置永久降階。**

**另外一定要有回頭路。** 加了「重試（清除上次的失敗紀錄）」按鈕：
黑名單擋住唯一發布的模型時才顯示，按下去清空黑名單並重新偵測。
誤判是不可能完全避免的（例如上面那個 iOS 背景的情況），
所以判斷錯了必須要能救回來，而不是讓使用者永久失去本機模式。

**這一輪的模式跟 D053 完全一樣：我為了修一個問題加的機制，自己造成了下一個問題。**
兩次都是因為那個機制在「事後補救」而不是在源頭區分狀態。
`pagehide` 之所以是對的修法，是因為它去問了一個真正能區分兩種情況的訊號。

## 2026-08-21｜D060 儲存配額改成「警告但讓他試」

原本要求可用空間 ≥ 模型大小 × 2.2 才放行，否則擋掉。兩個問題：

1. `estimate()` 不可靠——實測遇過回報 `quota: 0` 而 OPFS 完全正常。
2. 「寫入需要約兩倍」是觀察到的行為，不是保證值。不同瀏覽器的 OPFS 實作差異很大。

只發布 4B 之後這個問題被放大了：2,076 × 2.2 ≈ **4.6 GB**。
用一個不確定的數字要求 4.6 GB，會擋掉不少其實跑得動的裝置。

現在的規則：

| 可用空間 | 行為 |
|---|---|
| 查不到 / 回報 0 | 當成「不知道」，讓他試 |
| < 模型大小 | 擋（物理上不可能） |
| 一倍 ～ 兩倍 | **警告但讓他試**，並說明「失敗就是空間不足，清一些再來」 |
| > 兩倍 | 直接放行 |

理由與 D055 那個 `quota: 0` 的修法一致：
**擋住一台其實跑得動的裝置，比讓他試一次失敗更糟。**
失敗會得到明確的配額錯誤——那是一般錯誤，不會被記成崩潰，他還有下一步可做。
被擋住的話，他只會覺得這個 App 不支援他的裝置。

## 2026-08-21｜D061 痛點分析輸出了別人的痛點：關鍵字比對不到就用雜湊亂猜

使用者在 iPad 上填「約 40 歲的家庭主婦，有一個女兒，家中經濟來源只靠先生一個人的收入，
女兒今年上幼兒園」，痛點分析輸出的三點是：

> 1. 公司的貸款掛在自己名下，萬一出事太太要一個人背
> 2. 沒有人接手工廠，也沒想過退休之後怎麼辦
> 3. 幾張人情保單自己也不知道保了什麼

那是「小工廠老闆」原型的內容。使用者的原話：「完全不對呀！」

**原因鏈：**

1. 舊版每個原型的 `match` 是一條窄的正規表示式。實測那段背景，**八個原型全部沒有命中**。
2. 沒命中就退回「在年齡帶裡用 seed 挑一個」。40 歲落在五個原型的區間內，雜湊挑到了 sme-owner。
3. **輸出看起來完全有把握**——排版整齊、語氣專業、三點俱全，內容卻與客戶無關。

**這是最糟的失敗模式。** 空白畫面或錯誤訊息會讓人知道要重試；
一份自信而錯誤的分析會讓人拿著它去打電話。

**同一輪還暴露三個較小的缺陷：**

- 三點的「推測原因」是同一句樣板套出來的：
  「以${背景}的處境推測，這一類客戶通常會在意這件事，但不會主動提起。」
  三點一模一樣，等於沒有資訊；而且背景句尾有句號，組出「以…上幼兒園。的處境推測」。
- `profile` 出現「…上幼兒園。，目前的重心…」（句號後面接逗號）。
- 開場組出「這位先生您好」——使用者填「家庭主婦」但性別欄位留在預設的「男」。
  **猜錯稱謂比不猜更糟**，而且真人不會說「這位先生您好」。

### 修法

**① 比對不到時不要猜。** 新增通用原型（`generic`），痛點刻意選成
「收入中斷撐不了多久／不清楚自己保了什麼／想準備一筆確定的錢」——
不涉及職業、家庭結構或財務細節，對任何人都成立。
並回報 `weak: true`，畫面明說「以下是通用方向，**不是**針對您填的背景做的比對」。

**這一項比擴充詞庫重要。** 詞庫永遠會有漏，但「猜錯還裝作沒事」是可以避免的。

**② 關鍵詞分兩級計分。** `match` 從一條正規表示式改成
`{ s: 身分／職業關鍵詞, w: 處境細節 }`，計分 `s×3 + w×1`。

理由來自一個實測案例：「家管，兩個小孩都上小學了」在等權重下
「家管」與「兩個小孩」各得 1 分，同分後用雜湊決定，結果跑到「雙薪房貸」去了。
**職業身分決定這個人是誰，家庭細節只是補充。**

**③ 新增「家庭主婦／單薪家庭」原型。** 這在台灣壽險現場很常見，
而且正是使用者填的那一種——舊版根本沒有它，這才是零命中的直接原因。

**④ 兩種身分同時出現時要說出來。** 例如「公司老闆，同時在照顧失智的父親」——
挑哪一個都說得過去，所以不要安靜地挑一個，而是把另一個也講出來
（判準是「亞軍也命中了至少一個身分關鍵詞」，不是分數接近而已）。

**⑤ 每個痛點自帶 `why` / `need` / `ask`。** 原本痛點的文字與關鍵字在 `personas.js`，
而「可能需求」與「探索問題」放在 `gateway-local.js` 的另外兩個以 id 為鍵的物件裡——
**三個平行結構要同時維護，改了一個忘了另一個不會有任何錯誤訊息。**
這正是這個專案一再踩到的坑（示範句寫兩份、提示詞與偵測寫兩份）。
現在一個痛點就是一個物件，五個欄位在一起，測試會檢查每一項都齊全。

**⑥ 嵌入使用者文字前先修句尾標點**（`trimTail`），
年齡只在背景沒提到時才補（避免「約 40 歲的約 40 歲的家庭主婦」），
開場不猜稱謂（改在「要避免」裡提醒業務員自己加）。

### 這次學到的

**原型比對是這條路線的單點失效。** 人設、隱藏需求、痛點、示範問法全部從原型長出來，
比對錯了，後面每一個環節都會很有信心地錯下去——而程式層的七項攔截檢查
一項都不會響，因為輸出在形式上完全正確。

角色扮演路線的症狀比較輕（客戶的背景描述用的是使用者填的文字，
只有隱藏需求來自原型），所以這個缺陷先在痛點分析暴露出來。
但兩邊是同一個根因，一起修好了。

測試 155 → 180 項，其中 25 項是這次事故的回歸測試
（11 種真實背景的比對、比對不到要用通用原型並標示、
三點原因互不相同、不會出現壞掉的句子）。
