## 1. 三句話總結

1. **桌面上「完全離線」成立。** 瀏覽器內推論已經整條打通，
   MiniCPM5-1B 每回合 804 ms、關掉網路可用、不需要任何金鑰。

2. **iPhone 上「瀏覽器內推論」不成立。** 不是還需要調校——
   WebGPU 推論會讓分頁崩潰（兩個獨立引擎都是）、CPU 模式只跑得動 135M 模型且每回合 8.2 秒。
   **手機要離線，只剩原生 App 一條路。**

3. **能跑的模型都還不夠聰明。** 六種工程手段把「格式與行為」全部修好了
   （JSON、角色、重複、信任度），但 ≤2B 的模型接不住對話；
   要到 4B 才第一次像個真的客戶，而 4B 是 3 GB、每回合 4.3 秒、手機完全不可能。

全部用**真實的角色扮演提示詞**與同一份五回合腳本，不是簡化版。

| 模型 | 引擎 | 下載 | 載入 | 每回合 | 台灣繁中 | 對話品質 |

| SmolLM2-135M | wllama | 105 MB | 3.7 s | — | — | 僅管線測試 |

| **MiniCPM5-1B Q4** | wllama | 688 MB | 2.8 s | **783 ms** | ✅ | 偶有不成句 |
| **MiniCPM5-1B Q8** | wllama | 1,154 MB | 3.5 s | **804～934 ms** | ✅ | 通順，但一次好一次壞 |
| Qwen3.5-2B-OPT | ONNX | 1,581 MB | 148 s | 2,091 ms | ⚠ 出現簡體 | ❌ 接不住 |

### 3.1 品質差異的實例（同一份腳本）

**Qwen3.5-0.8B（空洞）**
```
業務員：請問您現在有在規劃小孩的教育金嗎？
王小姐：我……我不知道，我剛聽到...
```

**MiniCPM5-1B Q8（對題但淺，且不穩定）**
```

王小姐：嗯…沒有。                          ← 這次很好
王小姐：好，那我會去接個客人，會有幾個客人。  ← 同一份腳本的另一次
```

**Qwen3.5-4B（第一次像真的客戶）**
```

王小姐：原來這樣啊…那我剛手邊有筆定存快要到了，正煩惱該怎麼處置，
        不知道能不能一起聊聊看呢？          ← 主動透露隱藏需求

業務員：我下週三下午三點過去跟您說明二十分鐘，可以嗎？
王小姐：好的，那就麻煩你了。只是待會兒我得先去接小孩…  ← 對題＋用了人設的時間壓力
```

## 4. iPhone 實測數據（iPhone 14 Pro、iOS 26.6、Safari）

### 4.1 裝置能力（看起來一切就緒）

| 項目 | 實測 |
|---|---|
| WebGPU | ✅ 可用 |
| `shader-f16` | ✅ 支援 |
| `maxBufferSize` | 1,074 MB |
| CPU 執行緒 | 4 |
| 儲存配額 | 41,232 MB |
| **wasm 記憶體** | **可成長到 2,048 MB**（撞到測試上限，非裝置上限） |
| **ArrayBuffer** | **可配置 3,072 MB**（同上） |
| 網路（自筆電） | 11.9 MB/s |
| OPFS 寫入 | 533 MB/s |

### 4.2 實際跑起來（全部失敗，只有一個例外）

| 組合 | 結果 |
|---|---|
| 下載 1,154 MB 到 OPFS | ✅ 成功 |
| GGUF 載入 1,154 MB（GPU） | ❌ 分頁崩潰 |
| GGUF 載入 688 MB（GPU 與 CPU 都試） | ❌ 分頁崩潰 |
| GGUF 載入 105 MB（GPU） | ✅ 載入成功，**生成時崩潰** |
| **GGUF 載入 105 MB（CPU，`ngl=0`）** | ✅ **唯一完整跑完的組合** |
| ONNX 載入 665 MB（WebGPU） | ❌ 載入中崩潰 |

唯一跑完的那個組合，效能是：

| | 桌面 | iPhone（CPU、135M 模型） |
|---|---:|---:|
| 每回合 | 804 ms（1B 模型） | **8,230 ms** |
| 解碼速度 | 53～59 tok/s | **2.9 tok/s** |

**135M 的參數量只有 MiniCPM5-1B 的八分之一，中文品質不可能演出台灣客戶。**
所以「能跑的那個組合」對這個產品沒有意義。

### 4.3 三個獨立的結論

**① 崩潰與記憶體無關。** 這是最重要的排除。
wasm 可長到 2 GB、ArrayBuffer 可到 3 GB，而 688 MB 就崩。
**若沒有先量這兩個數字，幾乎必然誤判成「手機記憶體不夠，換更小的模型就好」**，
然後在錯誤方向上反覆嘗試。

**② WebGPU 在 iPhone 上「宣稱可用」但撐不住 LLM 推論。**

| 引擎 | WebGPU 的結果 |
|---|---|
| wllama（llama.cpp／asyncify） | 生成中崩潰 |
| transformers.js（ONNX Runtime Web） | 載入中崩潰 |

兩個完全獨立的引擎、兩種不同的失敗階段，而**唯一跑完的組合就是「完全不用 WebGPU」**。
這指向 iOS Safari 的 WebGPU 實作在大型工作負載下不穩，不是某個函式庫的 bug。

**③ 因此手機離線只剩原生 App。** Core ML／MLX 不受 WebKit 限制。
`11_IMPLEMENTATION_HANDBOOK.md` §7.1 原本列了四個原生化的理由，
這次實測補上第五個、也是最硬的一個。

## 5. 踩過的坑（最有價值的部分）

按「會不會再遇到」排序。

### 5.1 選模型時會踩的

| # | 現象 | 真正原因 | 教訓 |
|---|---|---|---|
| 1 | 同一個模型 prefill 慢 **165 倍** | `Qwen3.5-0.8B-ONNX` 未優化圖 vs `-ONNX-OPT`。前者 165～171 ms／token、GPU 使用率 19%；後者 1～2 ms | **同一個模型的不同匯出版本也必須實測**。而且未優化那個是搜尋第一名、官方 README 的範例 |
| 2 | 單一 ONNX 檔 1,788 MB 載入 `std::bad_alloc` | ORT-web 的 wasm 記憶體上限，**不是顯卡不足**（4060 有 8 GB） | 選模型要看**檔案怎麼切**，不只看總大小。3 GB 的 4B 反而載得進去（拆成三檔） |
| 3 | 同一模型的 q4f16 輸出純亂碼、q4 載不進去 | 數值精度問題 | **同一模型的不同量化，可用性是 0 或 1**，整個 repo 可能沒有可用組合 |
| 4 | 1B 模型輸出「您問得來」「請告訂時」這種不成句的詞 | **Q4 的量化損失**，換 Q8 後全部成句 | 1B 級對量化的敏感度遠高於大模型。先前把它歸因於「模型能力不足」是錯的 |
| 5 | 模型先吐一整段簡體中文的思考過程 | Qwen3 世代**預設開啟 thinking** | 要在對話模板層關掉（`enable_thinking: false`），程式層還要處理被截斷的 `<think>` |
| 6 | 想用 MiniCPM 卻發現完全跑不起來 | **transformers.js 不支援 MiniCPM 架構**（grep 其 bundle：Qwen／Gemma／DeepSeek 都在，minicpm 零命中） | **推論引擎決定了模型選擇的範圍**。綁單一引擎＝把選擇權交給它的支援清單 |

### 5.2 提示詞與小模型會踩的

| # | 現象 | 真正原因 | 解法 |
|---|---|---|---|
| 7 | 客戶講出提示詞裡的示範台詞「你慢慢說沒關係」 | `DIFFICULTY[1].rules` 寫了範例句，**小模型把「例如」當成台詞** | 只描述行為，不給任何引號內的句子 |
| 8 | 同一個錯誤犯第二次：客戶一直說「請問是哪方面呢」 | 我自己在 one-shot 示範裡放了「嗯…請問是什麼事？」 | 示範**不只示範格式，也示範了內容可以多空泛**。改成兩組、示範不同行為 |
| 9 | 四個欄位齊全但數字全是假的（`trust_delta` 永遠 0） | **要求錯了對象**。0.8B 不會評估信任度，只會複製看到的格式 | 數字改由程式算（`turn-signals.js`）。**逼小模型輸出它不理解的數字，得到的不是壞數據，是看起來正常的壞數據** |
| 10 | 低溫重複、高溫格式崩壞，找不到平衡點 | 「要變化」與「要結構」在 0.8B 上直接衝突 | **拿掉 JSON**：既然數字都由程式算，就不該再逼它輸出格式。順帶速度快一倍 |
| 11 | MiniCPM 回「建議您聯繫保險產業的客服熱線」 | assistant 對齊太強，把每段輸入都當成「要協助的請求」 | 改用**續寫模式**：給逐字稿讓它接著寫。角色由文字結構決定，不靠它配合指令 |
| 12 | 客戶秒答應「這個保險我一定會買」 | 過度順從 | **比講不通更危險**——會給新人虛假的成功感。已加程式層攔截 |

> 第 7～8、10～11 是同一條原則的四次驗證：
> **用結構逼出行為，不要用規則請求行為。**

### 5.3 跨平台會踩的（最難查的一類）

| # | 現象 | 真正原因 | 教訓 |
|---|---|---|---|
| 13 | Worker 啟動失敗，`worker.onerror` 的訊息是**空字串** | transformers.js bundle 內有 bare import specifier（`onnxruntime-web/webgpu`），**Worker 裡沒有 import map 可以救** | 自帶第三方函式庫要寫成腳本（`tools/vendor.mjs`），含「還有未解析 specifier 就報錯」的檢查 |
| 14 | 「Failed to fetch dynamically imported module」 | `serve.mjs` 的 MIME 表沒有 `.mjs` 與 `.wasm` | 錯誤訊息完全沒指出真正原因 |
| 15 | WebGPU 抓不到檔案 | 實際請求的是 **asyncify** 變體，而 transformers.js 的 dist 只附了 **jsep** | 照著套件附的檔案自帶會少檔案，錯誤訊息也不會指出正確檔名 |
| 16 | iPhone 載入失敗：`undefined is not a function (near '...chunk of res.body...')` | **Safari 沒有實作 ReadableStream 的 async iterator**，Chrome 有 | **桌面 Chromium 綠燈不代表 iOS 能跑**。而且我的診斷頁用了同一個寫法，所以它也是壞的——**診斷工具本身也會有平台 bug** |
| 17 | 我斷定使用者的手機是 iOS 18.7（實際 26.6） | **Safari 從 iOS 26 起回報凍結的 UA 字串** | 不能用 UA 判斷 iOS 版本 |
| 18 | 手機下載 1,154 MB，一分鐘只跑 1 MB | wllama 的下載器「邊下載邊寫入」，每小塊 await 一次，在 iOS 上代價極高 | 分項量測（網路 11.9 MB/s、OPFS 533 MB/s）證明兩邊都正常 → 自建下載路徑後變 9.2 秒 |
| 19 | 精確字串「業務員：」攔不住停止 | 模型寫的是「業務員 :」「業務苑 ...」「業務委員」等變體 | 我在做的是「列舉模型可能拼錯的所有方式」，永遠列不完。**換行才是結構性的停止點** |
| 20 | `n_ctx` 2048 在**第三回合**才爆 | 續寫提示詞本身約 1,000 token，逐字稿累積後超出 | **短測試看不到隨對話長度累積的問題** |

### 5.4 最重要的一條方法論

**能力偵測（feature detection）不等於可用性。**

| 看起來 | 實際 |
|---|---|
| `navigator.gpu` 存在、`maxBufferSize` 1,074 MB | WebGPU 推論會讓分頁崩潰 |
| 記憶體量到 2 GB／3 GB 可用 | 688 MB 的模型載不進去 |
| 桌面 Chromium 全綠 | Safari 缺 ReadableStream async iterator |

`caps.js` 的偵測畫面只能「篩掉明顯不行的裝置」，
**不能當成「這台裝置可以用」的保證**。任何新裝置都要跑完「載入 → 五回合 → 看數字」。

而分項量測工具（`nettest.html`、`memtest.html`）的價值在**排除**，不在確認：
它們能證明「不是網路」「不是記憶體」，但不能證明「所以會成功」。
即使如此，它們兩次把我從錯誤方向上拉回來，是這兩天最划算的投資。

## 7. 現在剩下哪些路

前提釐清：**「運算在哪裡」決定了其他所有事。**
在使用者裝置上運算＝離線、資料不外流、零成本；在伺服器上運算＝三者全部反過來。

| # | 方案 | 手機可用 | 對話品質 | 你的成本 | 資料離開裝置 | 狀態 |
|---|---|---|---|---|---|---|
| **A** | **桌面離線版**（本專案） | ❌ | 1B 尚可／4B 可用 | 0 | ❌ 不離開 | **已驗證可用** |
| **B** | 手機雲端版（使用者自帶金鑰） | ✅ | **最好** | 0 | 是 | **已上線** |
| **C** | 代理到 Gemini（你出金鑰） | ✅ | **最好** | 依用量，可能 0 | 是 | 小工程 |
| **D** | 原生 App（手機離線） | ✅ | 待驗證 | 開發成本 | ❌ 不離開 | 需 macOS |
| **E** | 自架小模型在伺服器 | ✅ | **1B 級（差）** | PRO $9/月＋GPU | 是 | 不建議 |

### 7.1 關於 GitHub Pages 與 HuggingFace Spaces（你問過的）

**GitHub Pages 沒有任何運算能力**，只傳靜態檔案。而且限制對我們不利：
單檔 100 MB、站台 1 GB、每月 100 GB 流量（688 MB × 145 次下載就用完）。

**HuggingFace Spaces 有三種形態：**

| 形態 | 費用 | 運算在哪 | 對我們的意義 |
|---|---|---|---|
| **Static Space** | **免費給所有人** | 使用者瀏覽器 | **比 GitHub Pages 更適合**放桌面離線版：repo 用 Xet／LFS，放得下 688 MB 模型檔 |
| Gradio／Docker Space | **個人帳號需 PRO** | 伺服器 | 手機可用、不需金鑰，但見下方 |
| ZeroGPU | 免費帳號限 2 個 Gradio Space | 伺服器 GPU | 有配額限制 |

Space 的免費硬體是 2 vCPU／16 GB，**48 小時無人使用就休眠**（有人訪問才重啟，冷啟動要重新載入模型）。
T4 GPU 是 $0.40／小時，全天候開著約 **$288／月**。

### 7.2 為什麼不建議方案 E（自架小模型）

一旦接受「資料離開裝置」，就同時失去離線與 local-first（規格 §38）這兩個賣點，
而**花錢買到的品質還比免費雲端差**：

```
自架 MiniCPM5-1B     一次好一次壞      PRO $9/月起，GPU 另計
代理到 Gemini        V1 實測 1.1 秒／回合、品質最好      免費額度內可能是 0 元
```

**本機模型的全部價值建立在「不離開裝置」與「不用金鑰」這兩件事上。**
把它搬到伺服器，這兩個價值都消失，只剩成本。

## 8. 我的建議

**三條線分開，各自做它擅長的事，不要勉強一條線做全部：**

| 場景 | 做法 | 為什麼 |
|---|---|---|
| 桌面＋離線＋零金鑰 | **方案 A**，可放 HF Static Space | 唯一被實測證明可行、且不需伺服器也不需金鑰的組合 |
| 手機＋立刻可用 | **方案 B**（已完成） | 已經上線，品質最好 |
| 手機＋不想讓使用者輸金鑰 | **方案 C** | 工程量小，成本可控 |
| 手機＋離線 | **方案 D** | 唯一的路，但要先解決 macOS／Xcode |

**建議的優先順序：A → C → D。**

先把桌面離線版做到「能真正練習」（接上六大功能、程式化評分、離線語音），
理由是它已經可行、不需要任何外部依賴，而且能驗證一件比技術更重要的事：
**程式化評分（`turn-signals.js`）是否真的能給出有用的教練回饋。**
那個問題的答案跟模型大小無關，卻決定整個產品有沒有價值。

### 8.1 如果選 A，接下來要做什麼

| 順序 | 工作 | 已完成的部分 |
|---|---|---|
| 1 | 桌面模型策略定案（1B 快／4B 準，或依裝置自動選） | 兩者都已實測 |
| 2 | 六大功能接上本機模型（目前只做了角色扮演） | 角色扮演已完成 |
| 3 | 程式化評分的 rubric（權重與級距需你審定） | 每回合訊號已完成 |
| 4 | 離線語音（Whisper ONNX＋系統 TTS） | 尚未開始 |
| 5 | Golden Reference 60 案例（需你審定預期值） | 尚未開始 |
| 6 | 首次啟動的模型下載流程、PWA 離線 | 鏡像機制已完成 |

### 8.2 如果選 C，接下來要做什麼

| 順序 | 工作 |
|---|---|
| 1 | 決定代理放哪裡（HF Docker Space 需 PRO／自架小 VM／Cloudflare Workers） |
| 2 | 金鑰保管、用量上限、濫用防護（否則帳單失控） |
| 3 | 現有 `engine/api.js` 加一個 provider，其餘引擎不動 |
| 4 | 明確告知使用者「對話會傳送到伺服器」（規格 §25 的合規提醒） |

### 8.3 如果選 D，第一個要解決的不是技術

`12_NATIVE_APP_DEV_PLAN.md`（在 `Ai_Sales_Coach_App` 專案）§0 已經寫過：
**最大的阻礙不是技術，是建置環境**——iOS App 必須用 macOS 上的 Xcode 建置與上架。
那一項不解決，後面全部無法開始。

## 9. 最後：這兩天最值得記住的一件事

規格 §63 說這個產品的價值在「會陪業務員反覆練習」。
handbook §12 說「價值不在模型多強，而在程式有多懂業務實務」。

這兩天的實測給了那句話一個很具體的形狀：

**我們把「格式與行為」全部用程式修好了**——JSON 不再失敗、角色不再錯亂、
重複被攔下、信任度會動而且判定可解釋、六項行為攔截加 45 項確定性測試。
**這些成果與模型無關，換任何模型、任何路線都還在。**

**但「聽懂對方在問什麼並且合理回應」修不了。** 那是模型容量，
而手機上跑得動的容量遠遠不夠。

所以真正的產品問題不是「要用哪個模型」，而是：

> **在「離線＋隱私」與「對話品質」之間，這個產品的哪一邊不能妥協？**

桌面可以兩者都要。手機只能選一邊。這是需要你決定的事，
而現在你有實測數字可以據以決定，不必憑猜測。
