## 0. 摘要：四句話

1. **決策已定：瀏覽器內 WebGPU、完全離線、手機也要能跑。**
   這是四條路線中技術限制最嚴、但觸及率最高的一條——使用者什麼都不用裝、
   不用申請金鑰、關掉網路也能練。

2. **「手機瀏覽器」這一項把模型硬鎖在 0.8B。** iPhone 的 WebGPU 要 iOS 26 起才有，
   Safari 的 Metal 後端有緩衝區上限，實測顯示 1B～1.5B 只在旗艦機可行。
   0.8B（q4 約 550 MB）是唯一同時滿足「手機可跑」與「有現成瀏覽器版本」的尺寸。見 §3。

3. **「完全離線」有兩個破口，必須一起解決：語音辨識與評分品質。**
   瀏覽器的 Web Speech API 會把音訊送上雲端（你自己的手冊 §7.1 已記錄），
   所以離線 STT 得改用瀏覽器內 Whisper。而 0.8B 當評審會退化成空泛稱讚
   （手冊 §8.1 明確警告）。見 §5、§6。

4. **評分的解法不是換更大的模型，是把評分搬回程式。**
   信任度軌跡、引導次數、是否問了開放式問題、是否約到時間、合規命中——
   這些程式全部算得出來。讓 0.8B 只負責把已算好的結果寫成人話。
   **這讓「完全離線」不只是可行，而是讓產品更可靠。** 見 §6。

## 3. 模型策略（依決策修正）

### 3.1 你原本指定的 Qwen3.5-0.8B：方向對，但 repo 要換

你給的 `unsloth/Qwen3.5-0.8B-MTP-GGUF` **在路線 A 用不上**——GGUF 是
llama.cpp 的格式，瀏覽器要的是 ONNX。同一個模型的正確來源是：

```
onnx-community/Qwen3.5-0.8B-ONNX      ← 手機與桌面通用（q4 約 550 MB）
onnx-community/Qwen3.5-2B-ONNX        ← 桌面升級選項（q4 約 1.2～1.5 GB）
```

順帶記錄那個 GGUF repo 的兩個陷阱，以免日後又繞回去：

- **MTP** 是推測解碼用的額外層，2026-05-16 才併入 llama.cpp，0.8B 加速幅度本來就小，
  卻多綁一個「只有新版才支援」的相依。
- **`mmproj-*.gguf`（205～402 MB）是視覺投影檔**，我們六大功能沒一項要看圖，純浪費。
- 另外 Unsloth 官方文件明寫「目前沒有 Qwen3.5 GGUF 能在 Ollama 運作，原因是視覺檔分離」，
  但 Ollama 官方 library 有 `qwen3.5:0.8b`。**要用 GGUF 就用 Ollama 官方打包版，
  不要匯入 unsloth 的 MTP 版。**（僅在 §3.4 的對照組會用到。）

### 3.2 「手機瀏覽器」的實際天花板

> ⚠ **本節原本的內容是二手資料，2026-08-19 實機量測後推翻了兩項。**
> 舊說法：WebGPU 要 iOS 26、Safari 的 Metal 緩衝區上限約 256 MB。
> **實測（iPhone 14 Pro，iOS 18.7）：**
>
> | 項目 | 實測值 |
> |---|---|
> | WebGPU | **✅ 可用**（iOS 18.7，不需要 iOS 26，也不需要開功能旗標） |
> | GPU | `apple apple` |
> | `shader-f16` | ✅ 支援（可用 q4f16） |
> | **maxBufferSize** | **1,074 MB**（不是 256 MB——寬鬆得多） |
> | CPU 執行緒 | 4 |
> | 儲存配額 | **41,232 MB**（41 GB，模型大小完全不是問題） |
>
> 這是 handbook §9.1 第 3 條的又一次驗證：**紙面資料不能當結論，要實機量。**
> 差別在這次二手資料是「過度悲觀」，若照著它做決策，會提早放棄一條其實可行的路。

| 項目 | 實際狀況 |
|---|---|
| iPhone WebGPU | ✅ iOS 18.7 實測可用（原以為要 iOS 26） |
| iPhone 緩衝區上限 | **1,074 MB 實測**（原以為約 256 MB） |
| Android | Chrome 旗艦機可行；**中低階機常常 GPU 記憶體不足**，1B 就跑不動 |
| 全球 WebGPU 支援度 | 約 82～90% 瀏覽器流量 |
| 實測可行的模型級別 | **≤ 2B 才有互動速度；手機實務上 ≤ 1B** |

**結論：0.8B 不是「保守選擇」，是手機上唯一的選擇。**

### 3.3 建議：一份程式、兩個模型檔、依裝置自動選

```
偵測 WebGPU 可用性與 GPU 記憶體上限
  ├─ 桌面且記憶體充足   → Qwen3.5-2B-ONNX  （品質優先）
  ├─ 手機或記憶體受限   → Qwen3.5-0.8B-ONNX（唯一可行）
  └─ 無 WebGPU         → WASM 後端跑 0.8B（慢，但仍可用）＋明確告知
```

這完全符合手冊 §2.10「預設聰明，指定時單純」：使用者只看到「本機模型」，
不必理解 0.8B 與 2B 的差別；想知道的人可以在設定裡看到目前用哪個。

### 3.4 Llama-Breeze2-3B：留在計畫裡，但角色改變

Breeze2-3B 是候選中**唯一有「台灣語境」訓練意圖的模型**（聯發科開源，繁中優化），
所以「Qwen 講話有沒有翻譯腔或大陸用語」這題，只有它能當對照。

但它在路線 A **不可交付**：沒有 ONNX 版本、3B q4 約 1.8 GB、手機不可能跑。

因此建議把它降級為**離線對照組**：用 llama.cpp 在開發機上跑，
只跑 Golden Reference 的「語言與口語」那 10 個案例，回答一個問題：

> **Qwen3.5-0.8B 的台灣口語，跟一個專為繁中優化的模型差多少？**

- 若差距小 → 安心用 Qwen，省下所有轉換工作。
- 若差距大 → 這個差距要用**提示詞＋程式層用語過濾**補（把大陸用語當成
  `scrubBrands()` 的同類問題處理），而不是換模型。

**這需要在開發機裝 llama.cpp 或 Ollama，但那只是選型工具，不是交付路徑。**
若你不希望裝任何東西，就放棄這個對照組，改為直接用 Qwen 並加強用語過濾（見 §11 Q8）。

### 3.5 取樣參數與 JSON

Qwen3.5 non-thinking 官方建議值：`temperature 0.7 / top_p 0.8 / top_k 20 / min_p 0.0`。
Qwen3.5 Small 系列**預設關閉 thinking**，這對我們的延遲目標是好事，
但程式層仍要剝除任何 `<think>` 區塊（手冊 §2.7 兩層防護）。

角色扮演可能要把 temperature 壓到 0.6 以下防人設漂移，實測決定。

**JSON 是路線 A 的一個真實弱點，要誠實記錄：**
llama.cpp 有 GBNF grammar、Ollama 有 structured outputs，
可以在解碼層**保證**輸出合法 JSON。**transformers.js 目前沒有等價的強制約束機制。**

因此本專案必須：

1. 依手冊 D009「讓模型挑編號而非複製字串」——小模型更需要，全面套用。
2. `parseJson()` 的容錯要加強（截斷修補、抓第一個合法物件、單引號正規化）。
3. 解析失敗要重試，且重試時把提示詞縮到最短。
4. **關鍵欄位若解析失敗，用程式的預設值兜底**，不要讓整個回合失敗。

### 3.6 提示詞預算：這是 0.8B 上最容易被低估的問題

`prompts.js` 是 38.8 KB，為 Gemini 等級模型寫的。餵給 0.8B 有兩個後果：

1. **prefill 吃掉速度優勢**：手機 GPU 處理長 system prompt 的預填時間很可觀。
2. **規則遵循度下降**：小模型注意力預算有限，規則越多，每條被遵守的機率越低。

但**不能簡單砍短**。手冊 §2.4 的教訓正好相反：「一行文字的設定通常等於沒有設定。」

建議新增 `prompts.small.js` 作為**覆寫層**（原檔不動），取捨原則：

| 保留（不可砍） | 可壓縮或移除 |
|---|---|
| 資訊邊界清單（D012，本專案最重要的發現） | 解釋「為什麼」的段落——模型不需要理解理由 |
| Role Lock 鐵律 | 範例對話（留 1 則，不是 3 則） |
| 難度規則表的**行為**描述 | 難度規則表的**數值**（本來就由程式夾取，不必寫進提示詞） |
| 「回報編號而非複製字串」 | 語氣修飾與客套 |
| 純文字、不得用 Markdown | |

同時**上下文要由程式管理**：0.8B 在手機上建議上限 2～4 K token，
超過時由程式做滾動摘要（而不是讓模型自己忘記）。

**程式層檢查必須加重。** 手冊 §2.7 的兩層防護在小模型上會變成
「提示詞層命中率下降、程式層攔截率上升」，所以 `scrubBrands()`、
`demoLeaksPrivateInfo()`、`validateRoleplay()`、`scrubMeta()` 要在 L0 就量測攔截次數
——**這個數字本身就是模型品質的指標**。

## 4. 技術棧選擇

| 層 | 建議 | 理由 |
|---|---|---|
| 推論引擎 | **transformers.js v4 + ONNX Runtime Web（WebGPU）** | 0.8B 與 2B 都有現成 ONNX 版本且有實跑 demo；**同一個 runtime 也能跑 Whisper**，STT 與 LLM 共用一套（見 §5） |
| 備選 | WebLLM（MLC） | 效能可能更好，但需 MLC 編譯的模型，Qwen3.5 是否在預建清單需確認；**不作為第一選擇** |
| 無 WebGPU 時 | ONNX Runtime Web 的 WASM 後端 | 慢但可用，且要明確告知使用者 |
| 模型與快取 | Cache API／OPFS + IndexedDB | 首次下載後永久快取；需處理配額與中斷續傳 |
| 推論執行緒 | Web Worker | **必須**，否則生成會凍住 UI 與語音 |
| 引擎 | 沿用 `Ai_Sales_Coach_App/engine`，新增 `local` adapter | §1.2 |

### 4.1 不動的部分（紅線）

```
session.js      狀態機、難度數值夾取、結束判定       ← 一行都不改
compliance.js   合規規則引擎                        ← 一行都不改
prompts.js      提示詞 IP                          ← 只新增 small 覆寫層
advisor.js      痛點／理賠／行銷諮詢                ← 只改「分數來源」（見 §6）
platform.js     平台能力層                         ← 一行都不改
```

手冊 §2.3 記錄：「換過三次模型策略、加過六家服務商、從伺服器搬到純前端，
Coach Engine 核心邏輯一行都沒改。」**本專案要延續這個紀錄。**
若做到後來發現 `session.js` 必須改，那代表 adapter 的抽象邊界畫錯了。

### 4.2 新增：`local` provider adapter

```
PROVIDERS.local = {
  label: '本機模型', note: '完全離線，不需要金鑰',
  needsKey: false,          ← 新欄位：登入畫面據此可完全跳過
  file: false,
}
```

| 項目 | 做法 |
|---|---|
| 模型清單 | 由 `local/models.js` 宣告（含 URL、大小、最低裝置要求），不寫死在邏輯裡 |
| 探測 | 檢查 WebGPU 可用性、GPU 記憶體上限、快取中是否已有模型 |
| tier 對應 | `fast` → 已載入的模型；`judge` → **不再是模型的責任**（見 §6） |
| 串流 | 支援 `onDelta`（見 §4.3），角色扮演邊生成邊送 TTS |
| 生命週期 | 模型載入／卸載要可控——記憶體吃緊時要能主動釋放 |

### 4.3 Streaming（建議加入，向後相容）

```
generate(text, { ...opts, onDelta })  →  { text, ms, model }
```

不支援串流的 adapter（現有六家雲端）就在收到完整回應時呼叫一次。
角色扮演與語音演練用它，其他功能不用。

**為什麼重要：** 本地模型首 token 極快，可以「邊生成邊送 TTS」，
感知延遲會比現在雲端的 1.1 秒更短。這是本地模型體驗**優於**雲端的地方，
不只是「勉強追上」。

### 4.4 新的失敗類型（手冊 §8.8 已預告，這裡具體化）

| 類型 | 使用者看到的訊息應該長什麼樣 |
|---|---|
| 裝置不支援 WebGPU | 「這個瀏覽器不支援本機模型」＋列出可用瀏覽器與版本＋仍可用 WASM 慢速模式 |
| 記憶體不足／載入失敗 | 「這台裝置記憶體不足以載入 2B 模型，已改用 0.8B」＋自動降階，不是報錯 |
| 模型下載中斷 | 保留已下載部分、可續傳、顯示剩餘大小 |
| 儲存配額不足 | 顯示需要多少、還缺多少、如何釋放 |
| 首次載入耗時 | 進度條與預估時間（手機可能數十秒） |
| 生成中裝置過熱降頻 | 偵測到逐回合變慢時提示休息，而不是讓使用者以為壞了 |

每一項都要符合手冊 §2.9 第 3 條：**錯誤要能行動。**

## 5. 離線語音管線（因「完全離線」而新增的工作項）

### 5.1 問題

你的手冊 §7.1 已經記錄：**「Web Speech API 會把音訊送到 Apple 伺服器」。**
所以現行網頁版的語音辨識**本來就不是離線的**——這與「完全離線」直接矛盾。

| 環節 | 現行做法 | 是否離線 | 離線版做法 |
|---|---|---|---|
| STT 語音辨識 | Web Speech API | **❌ 音訊上雲** | **瀏覽器內 Whisper ONNX（transformers.js）** |
| LLM 生成 | 雲端 API | ❌ | 瀏覽器內 Qwen3.5 |
| TTS 語音合成 | `speechSynthesis` | **✅ 系統語音是本地的** | 不變 |

**好消息：TTS 不用動。** iOS／Windows 的系統中文語音是本地合成，
`speechSynthesis` 可以直接用，也免費。

### 5.2 代價：記憶體要一起算

| 元件 | 約需 |
|---|---|
| Qwen3.5-0.8B ONNX q4 權重 | ~550 MB |
| KV cache（4 K 上下文） | ~100～200 MB |
| Whisper 模型（tiny／base，繁中辨識率待實測） | ~40～80 MB |
| 執行期額外開銷 | ~100 MB |
| **合計** | **~800 MB～1 GB** |

**這個總和落在手機瀏覽器的天花板上，是本專案最需要實測的風險。**

可能的緩解手段（依偏好順序）：

1. **分時載入**：Whisper 與 LLM 不同時駐留——收音時載 Whisper、生成時卸掉。
   代價是切換延遲，但語音對練本來就是輪替的，可行性高。
2. 用更小的 Whisper（tiny）並接受辨識率下降，靠程式做常見錯字修正。
3. 手機版預設「打字模式」，語音對練標為「需要較高階裝置」。

### 5.3 Barge-in 的誠實預期

手冊 §7.1 明寫：Barge-in 在 iOS Safari 做不到，這是**原生 App 才能解決的限制**，
路線 A 不會改變這件事。所以本專案的語音體驗上限是「點麥克風打斷」，
與現行網頁版相同。**真正的 Barge-in 仍然只在 `Ai_Sales_Coach_App` 那條路上。**

這一點必須寫在文件裡，避免日後誤以為離線化順便解決了語音體驗問題。

## 6. 評分重新設計：讓「完全離線」不只可行，而是更可靠

### 6.1 問題

手冊 §8.1 的警告非常明確：

> **評分是整個產品的價值所在。** 如果小模型把評分做成空泛稱讚
> （「你表現很好，繼續加油」），使用者就不會想練第二次——
> 那麼「完全離線」這個技術成就反而毀掉了產品。

而在手機上，judge tier 也只有 0.8B。**直接讓 0.8B 當評審，幾乎確定會失敗。**

### 6.2 解法：把分數的計算搬回程式，模型只負責措辭

這不是妥協，是手冊 §2.1 的分工原則往前推一步。演練過程中，程式**已經知道**
非常多可量化的事實：

| 可由程式確定計算的 | 資料來源 |
|---|---|
| 信任度起點、軌跡、終點 | `session.js` 已在累加 |
| 使用者用了幾次引導 | 已記錄 |
| 挖到幾項隱藏需求／共幾項 | 已記錄（D009 的編號機制） |
| 是否約到具體時間 | 狀態機判定 |
| 開放式問題 vs 封閉式問題比例 | 正規表示式可判 |
| 合規紅線是否命中 | `compliance.js` 已有 |
| 平均回應長度、是否一直自己講 | 逐字稿統計 |
| 是否在客戶抗拒後仍推進 | 狀態轉移紀錄 |

**這些加起來，已經足以算出五項評分的分數本身。**
模型剩下的工作只有一件：**把這些事實寫成一段像教練說的話**——
而「照著給定事實寫一段話」正是 0.8B 做得還不錯的事。

```
現在（雲端）                        離線版
────────────                        ────────
LLM 讀逐字稿 → 自己給分 → 寫回饋     程式算分（rubric）
                                    ↓
                                    LLM 依「分數＋證據清單」寫回饋文字
                                    ↓
                                    程式檢查回饋是否引用了給定證據，
                                    沒引用就重寫（兩層防護）
```

### 6.3 為什麼這比現在的做法更好，不只是「能離線」

1. **分數變成可重現的。** 同一份逐字稿永遠得到同一個分數，
   手冊 §4.6「測試不穩」那個問題直接消失。
2. **評分標準變成可審閱的資產。** rubric 寫成程式＝寫成文件，
   你可以逐條檢視「這樣算分對不對」，而不是猜模型在想什麼。
3. **杜絕諂媚。** 空泛稱讚的根源是模型想討好使用者；分數不由它決定，它就沒得諂媚。
4. **與難度系統一致。** 手冊 §2.4 已經證明「把關鍵數值交給程式夾住」有效，
   §9.3 第 15 條也明寫「若某個參數很重要，就不要只用提示詞描述它」。
   **評分是這個產品最重要的參數。**

### 6.4 需要你參與的部分

rubric 的權重與級距（例如「約到時間」值幾分、信任度上升 20 算幾分）
**必須由你定**，這是領域知識，不是工程判斷。
我會先產一份草案（依 `02_AI_COACH_ENGINE.md` 的五項評分定義），由你調整。

## 7. Golden Reference：唯一的 Go/No-Go 依據

手冊 §10.3 明寫：

> 這是 V1 的**已知缺口**……**導入本地模型前必須補上這件事**，
> 否則無法回答「小模型的評分品質是否可接受」。

**在 0.8B 的前提下，這件事的重要性又高一級。** 建議規模：

| 節 | 案例數 | 驗證什麼 | 對 0.8B 的意義 |
|---|---:|---|---|
| 語言與口語 | 10 | 繁體中文、台灣用語、不夾簡體／外語 | **最可能失敗的一節** |
| 人設一致性 | 10 | 連續 10 回合不漂移；使用者指定個性優先（D021） | 小模型漂移明顯 |
| 難度行為 | 10 | Level 1 不掛電話且會接話；Level 5 會拒絕 | 手冊 §2.4 的實測對照可直接當案例 |
| 資訊邊界 | 10 | 示範話術不得洩漏隱藏資訊（D012） | **不通過就不能上線** |
| JSON 與結構化 | 5 | 解析成功率 ≥ 95%（無 grammar 約束，見 §3.5） | 高風險 |
| 隱藏需求機制 | 5 | 編號回報正確、不一次全說 | 抽象指令，高風險 |
| 回饋文字品質 | 10 | 是否引用了程式給定的證據、有無空泛稱讚 | **新定義**：不再評「給分準不準」，改評「措辭有沒有引用證據」 |

**預期值必須由你（領域專家）審定**，不能拿雲端模型的輸出當標準答案。
手冊 §9.3 第 12 條：「實務失禮比技術錯誤更難發現，這類問題只有領域專家看得出來。」

跑法沿用 `selftest.mjs` 的設計（可分節、規則層先測、確定性與觀察值分開、
效能一起量、自我清理），新增「同一套案例可指定不同模型／不同裝置跑」並產出並排比較表。

|---|---:|---:|
| `onnx-community/Qwen3.5-0.8B-ONNX` | **165～171 ms** | 約 150 秒（實測跑到兩分半仍未結束） |
| `onnx-community/Qwen3.5-0.8B-ONNX-OPT` | **1～2 ms** | 約 0.9 秒 |

未優化版本的 GPU 使用率只有 **19%**，而且是線性成長（55 token 9.4 秒、98 token 16.2 秒），
推測 Qwen3.5 的混合架構（Gated DeltaNet 的 conv 與 recurrent 狀態）在未優化的圖裡
被展開成逐 token 的序列運算。

對照組（傳統 dense 架構）：`onnx-community/Qwen3-0.6B-ONNX` prefill **0.8 ms／token**，
與 OPT 版同一個量級——**證明問題出在圖的匯出方式，不在瀏覽器、不在 WebGPU、也不在 0.8B 這個尺寸。**

> 這是 handbook §9.1 第 3 條「不要只看紙面規格選模型」最極端的版本：
> 這次連模型都一樣，差別只在匯出方式，而規格文件上完全看不出來。

### 13.3 發現二：速度可用，但沒有達到 2 秒目標

五回合實測（提示詞 1,246～1,346 token）：

| 指標 | 實測 | 規格目標 |
|---|---:|---|
| 平均首 token | 1,506 ms | — |
| 平均每回合 | **3,683 ms** | ≤ 2,000 ms（規格 §29）❌ |
| 解碼速度 | 26.8 tok/s | — |
| 模型載入（首次含 665 MB 下載） | 17.9～44 秒 | — |

**瓶頸拆解：** prefill 1,250 token 約 1.2 秒 ＋ 輸出 43～110 token 約 1.6～4 秒。
兩邊都與提示詞長度直接相關——**提示詞壓縮同時解決速度與品質，不是二選一。**

### 13.4 發現三：完整提示詞下，0.8B 撐不住引擎的契約

這是必須誠實記錄的部分。五回合的結果：

| 檢查項 | 結果 |
|---|---|
| JSON 可解析 | **2／5 失敗**（失敗原因是多一個 `}`，屬可修的解析問題） |
| `trust_delta` 欄位 | **每一回合都沒有** → 信任度五回合都停在 70，難度系統完全沒運作 |
| `revealed` 欄位 | 每一回合都沒有 → 隱藏需求 **0／3**，D009 的編號機制沒有被使用 |
| `end` 欄位 | 沒有（幸好預設不結束，所以 Level 1 行為「看起來」正確） |
| 角色正確性 | **失敗**：回合 1 自稱「我是做保險的」——把自己演成業務員 |
| 內容重複 | 回合 2／5 幾乎逐字重複同一句，且把提示詞裡的引導語當成台詞照抄 |
| `validateRoleplay()` | 0 次攔截——**但它沒攔到「自稱業務員」，因為它只比對後設用語** |
| `scrubBrands()` | 0 次攔截（沒有提到任何保險公司） |

**解讀：** 這不是「模型不會講中文」——它的繁體中文很自然。
問題是 **1,257 token 的規則它只執行了最表層的一部分**：
會演客戶的語氣，但不遵守欄位契約、不維持身分、會複製指令文字。

這正是計畫書 §3.6 預測的情況，也再次驗證 handbook §9.3 第 15 條：
**重要參數不要只用提示詞描述。** 差別是在 0.8B 上，「重要參數」的範圍要擴大到
「連身分與輸出格式都不能只靠提示詞」。

### 13.5 發現四：模型無法被瀏覽器快取（離線要求尚未達成）

實測 console 反覆出現：

```
Unable to add response to browser cache:
UnknownError: Failed to execute 'put' on 'Cache': Unexpected internal error.
```

每次重新載入頁面都會重新下載 665 MB。**這代表「完全離線」目前還不成立。**
推測原因是單一檔案過大（`decoder_model_merged_q4f16.onnx_data` 為 436 MB）超過
Cache API 的實作限制。

**對策方向：** transformers.js 支援自訂快取（`env.useCustomCache` / `env.customCache`），
改用 **OPFS**（Origin Private File System）儲存，它為大檔設計，且 iOS Safari 也支援。
這件事必須在 L0d 手機驗證之前完成，否則手機每次開 App 都要重載 665 MB。

### 13.6 因此 L1 的內容改變了

原本 L1 是「角色扮演離線化」，現在它的實際內容是四件明確的工程工作：

| # | 工作 | 為什麼非做不可 |
|---|---|---|
| L1-a | `prompts.small.js` 提示詞壓縮層 | 同時是速度瓶頸與品質瓶頸的根源（§13.3、§13.4） |
| L1-b | JSON 修復強化（括號平衡、欄位補值） | 2／5 失敗是可修的解析問題，不該讓回合失敗（§3.5） |
| L1-c | 新增程式層檢查：自稱業務員、複製指令文字 | 現有 `validateRoleplay()` 有缺口（§13.4） |
| L1-d | OPFS 自訂快取 | 沒有它就沒有離線（§13.5） |

其中 **L1-a 應該先做**，因為 L1-b／L1-c 的攔截次數要在壓縮後的提示詞下重新量測，
否則會為了現在這版提示詞的症狀寫出過度複雜的防護。

### 13.7 本階段建立的工具

| 檔案 | 用途 |

| 解碼速度 | 26.8 tok/s | 16.6 tok/s | 20.8 tok/s |
| JSON 解析失敗 | 2／5 ❌ | 0／5 ✅ | 結構上不可能 |
| 四個欄位齊全 | 0／5 ❌ | 5／5 ✅ | 由程式提供 |

**規格 §29 的「每回合 ≤ 2 秒」在 C 版達成（1,396 ms）。**

### 14.2 做了哪四件事

| # | 做法 | 解決了什麼 | 檔案 |
|---|---|---|---|
| 1 | 提示詞壓縮層（身分與格式移到結尾、規則 8 條→4 條、**刪掉所有可照抄的示範台詞**） | 演錯角色、照抄指令 | `engine/prompts.small.js` |
| 2 | JSON 前綴（直接幫模型寫好 `{"say":"`） | 四個欄位 0／5 → 5／5 | 同上 |
| 3 | 角色輪替示範（一組假的「業務員說→客戶答」） | 模型不再延續業務員的話 | 同上 |
| 4 | 解碼層重複懲罰（`repetition_penalty` 1.15、`no_repeat_ngram_size` 4） | 低溫時卡在同一句台詞 | `engine/local/models.js` |
| 5 | **每回合數字改由程式算** | trust_delta 永遠 0、revealed 永遠空 | `engine/scoring/turn-signals.js` |
| 6 | **純文字輸出**（不再要求 JSON） | 速度 3,067→1,396 ms，且解析失敗不可能發生 | `engine/prompts.small.js` |

第 5、6 項是同一個判斷的兩半：既然三個數字都不採用模型的值，就不該再逼它輸出。
詳見 `project/DECISION_LOG.md` D029。

### 14.3 兩個實測逼出來的細節

**① 提示詞裡不能放可照抄的台詞。**
`DIFFICULTY[1].rules` 寫著範例「你慢慢說沒關係」，實測發現模型在
`guidance = 0`（沒有觸發引導）的回合也把這句照抄出來。
壓縮版一律只描述行為，不給任何引號內的句子。

**② temperature 有一個很窄的可用區間。**

| temperature | 症狀 |
|---|---|
| 0.2 | 五回合幾乎逐字重複同一句台詞 |
| 0.65 + JSON | 台詞有變化，但欄位掉到 2／5，還亂填 `trust_delta: 95` |
| 0.65 + 純文字 | 結構全部正常（因為不再需要結構） |

**這個對照本身就是「純文字＋程式算分」的最強理由：**
它把「要變化」與「要結構」的衝突整個消除掉，而不是在兩者之間找平衡點。

### 14.4 剩下的問題：語意品質，工程解決不了

結構全部修好之後，剩下的東西很明確。C 版五回合的實際輸出：

```
業務員：呃…王小姐您好，我是…我是做保險的…想跟您介紹一下我們的新商品
王小姐：那花多久能拿到貨？                      ← 「拿到貨」不是保險對話
業務員：喔…那個…我們公司有一個很好的儲蓄型的…
王小姐：我剛才聽不到您剛才說什麼了。             ← 語句不通
業務員：請問您現在有在規劃小孩的教育金嗎？
王小姐：那孩子學校開課多快啊？                   ← 不對題
業務員：我了解，那我下週三下午三點過去說明二十分鐘可以嗎？
王小姐：好巧啦！                                ← 完全不對題
```

繁體中文很自然、沒有簡體、沒有大陸用語、語氣也像在講電話——
**但它接不住對話。** 而且隱藏需求 0／3，因為它從來沒有真的在回答問題。

**這一類問題無法用提示詞或程式修好。** 前面五項工程手段各自都有明確效果，
但它們處理的都是「格式與行為」；「聽懂對方在問什麼並且合理回應」是模型容量問題。

### 14.5 因此下一個關卡是模型選擇，不是工程

| 選項 | 內容 | 代價 |
|---|---|---|
| **C1** | 測 `Qwen3.5-2B-ONNX`（桌面）確認語意品質是否跨過可用門檻 | 下載約 1.5 GB；**iPhone 幾乎確定跑不動**（§3.2） |
| C2 | 手機與桌面用不同模型（手機 0.8B、桌面 2B），並誠實標示手機版是「口說練習」而非「對話練習」 | 兩種體驗，違反 §2.10 的一致性原則 |
| C3 | 回到混合模式：角色扮演走雲端、其餘離線 | 與「一開始就完全離線」的決策衝突 |
| C4 | 換一個同尺寸但對話能力更好的模型（例如專為繁中優化者）並自行轉 ONNX | 轉換工作量大，且 Breeze2-3B 手機仍不可行 |

**建議先做 C1**：它是唯一能回答「這是尺寸問題還是這個模型的問題」的實驗，
而且成本只是一次下載。若 2B 明顯可用，問題就變成「iPhone 上要接受什麼」；
若 2B 也接不住對話，那要重估的就是整個「完全離線」的產品定位，而不是再多寫幾條規則。

## 15. C1 實測：Qwen3.5-2B 沒有解決問題（2026-08-18）

### 15.1 目的

回答一個問題：§14.4 的語意品質問題，**是尺寸問題，還是這個模型的問題？**

### 15.2 結果：不是尺寸問題

同一份五回合腳本、同一套純文字＋程式算分的管線：

| 指標 | Qwen3.5-0.8B | Qwen3.5-2B |
|---|---:|---:|
| 下載大小 | 665 MB | **1,581 MB** |
| 首次載入（含下載） | 18～27 秒 | **148 秒** |
| 平均首 token | 1,047 ms | 1,496 ms |
| 平均每回合 | **1,706 ms ✅** | 2,091 ms ❌ |
| 結構檢查（角色／重複／欄位） | 全部通過 | 全部通過 |
| 挖到隱藏需求 | 1／3 | 0／3 |
| 台灣繁體中文 | 正確 | **出現簡體字** |

2B 的實際輸出：

```
王小姐：嗯？您是王先生吧...我現在剛好有事，等好了再談好不好？   ← 把自己的名字搞錯成對方
王小姐：嗯…請問是要跟王姐預約嗎？                              ← 用第三人稱講自己
王小姐：嗯，請您稍候，我想先跟您確認一下…                       ← 像客服，不像客戶
王小姐：嗯…请问您是问哪方面的问题呢？                           ← 簡體字
```

**2B 更大、更慢、更佔空間，但對話能力沒有變好，還多了簡體字問題。**
而且 1,581 MB 在 iPhone 上幾乎不可能載入（§3.2），所以它連「桌面用 2B」都不划算。

### 15.3 途中發現：我自己犯了 D030 記錄過的錯

2B 五回合有三回是這句的變體：「請問是哪方面呢」「請問是要預約嗎」「请问您是问哪方面的问题呢」。
**來源是我自己在角色輪替示範裡放的那句「嗯…請問是什麼事？」。**

D030 才剛記錄「提示詞裡不得出現可照抄的示範台詞」，然後我把同樣的錯誤換了位置再犯一次：
one-shot 示範不只示範「誰說話」，**也示範了「內容可以多空泛」**。

修正方式是改成兩組示範，而且刻意示範不同行為：
第一組「還不熟時簡短帶過」，第二組「被問到在意的事時會鬆口」（那是當時最缺的行為）。

效果：空泛句型消失，模型開始嘗試回應內容，而且第一次偵測到隱藏需求（1／3）。
**但語意品質仍然不可用：**

```
王小姐：我常為錢花太多日子，所以不想讓別人替我撐起來。   ← 語句不通
王小姐：說真的……我也怕這樣下去，孩子吃不了長久。         ← 模仿了示範的句式，語意不通
王小姐：說真的，要是哪天倒了，大家都不知道該給誰付賬。   ← 「付賬」是大陸用語
```

**這是提示詞層的最後一次嘗試，也確認了提示詞手段已經用盡。**

### 15.4 到此為止的完整結論

| 類別 | 狀態 |
|---|---|
| 瀏覽器內推論管線（WebGPU、Worker、串流、標籤化錯誤、裝置偵測） | ✅ 完成且可用 |
| 速度（規格 §29 每回合 ≤2 秒） | ✅ 桌面達成 1,706 ms |
| 結構與契約（JSON、欄位、角色、重複、信任度變動） | ✅ 全部由工程解決 |
| 確定性測試（不需模型、不需金鑰） | ✅ 35 項全過 |
| **語意品質（聽懂對方在問什麼並合理回應）** | ❌ **0.8B 與 2B 都不行** |
| 模型快取（離線） | ❌ Cache API 失敗，待改 OPFS |

**六種工程手段（壓縮、前綴、輪替示範、重複懲罰、程式算分、純文字）都有明確效果，
但它們處理的全部是「格式與行為」。** 語意品質不在這一層。

### 15.5 下一步的三個候選（需要裁決）

| # | 做法 | 成本 | 風險 |
|---|---|---|---|
| **E1** | 測 **Qwen3.5-4B**（約 2.5 GB，桌面） | 一次下載 | 回答「到底要多大才夠」。但若 4B 才可用，**手機路線就確定不成立** |
| **E2** | 換模型家族：測 **Qwen2.5-1.5B-Instruct**（純文字、無視覺、中文成熟度高） | 一次下載約 1 GB | 便宜且合理——Qwen3.5 Small 是「早期融合的多模態模型」，純文字聊天可能反而不如專做文字的舊版 |
| E3 | 接受現實，改變定位：本機模型只做「口說流暢度暖身」，真正對練走雲端（混合模式） | 無 | 與「一開始就完全離線」的決策衝突，需要你重新裁決 |

**建議順序：E2 → E1。**
E2 比 E1 便宜一半，而且它測的是一個更根本的假設——
**問題可能不在「太小」，而在「這個模型家族在這個尺寸上不是為文字對話最佳化的」。**
若 E2 明顯可用，手機路線就活著；若 E2 也不行，再用 E1 確認尺寸下限，
然後 E3 就變成必須面對的產品決策。

| Qwen2.5-1.5B（q4f16） | 1,222 MB | 48 秒 | — | — | — | ❌ **輸出亂碼** | ❌ |
| Qwen2.5-1.5B（q4） | 1,788 MB | 失敗 | — | — | — | ❌ **載入失敗** | ❌ |

### 16.2 4B 的實際輸出（品質門檻的證據）

```
業務員：喔…那個…我們公司有一個很好的儲蓄型的…
王小姐：原來這樣啊…那我剛手邊有筆定存快要到了，正煩惱該怎麼處置，
        不知道能不能一起聊聊看呢？                    ← 主動透露隱藏需求 3

業務員：請問您現在有在規劃小孩的教育金嗎？
王小姐：教育金嘛…我還算有留意，不過公司那邊的團體保障好像也只限在职期间，
        万一以后没工作了，这部分钱是不是也会受影响？    ← 隱藏需求 2，但夾簡體字

業務員：我下週三下午三點過去跟您說明二十分鐘，可以嗎？
王小姐：好的，那就麻煩你了。只是待會兒我得先去接小孩，
        所以大概只能等你走後再來跟你談，你看行不行？    ← 對題、答應、並使用人設的時間壓力
```

**4B 做到了 ≤2B 完全做不到的三件事：** 聽懂問題、在被問到時才透露隱藏需求、
把人設細節（時間壓力）自然編進回答。

它剩下的問題是**簡體字混入**（在职期间／万一／这部分钱／家里），
而那正好是程式層可以解決的一類——與 `scrubBrands()` 同性質，
需要一張簡繁轉換表加上大陸用語替換表。

### 16.3 三個新的技術限制（實測發現）

**① 單一 ONNX 檔超過約 1.5 GB 在瀏覽器載不進去。**
`Qwen2.5-1.5B-Instruct` 的 q4 是單檔 1,788 MB，載入時 `std::bad_alloc`
——不是顯卡記憶體不足（4060 有 8 GB），是 ORT-web 的 wasm 記憶體上限。
這解釋了為什麼 Qwen3.5 系列把權重拆成 embed／decoder／vision 三個檔，
也解釋了為什麼 3 GB 的 4B 反而載得進去。
**選模型時「檔案怎麼切」和「總大小」一樣重要。**

**② 同一個模型的不同量化，可用性可能是 0 或 1。**
`Qwen2.5-1.5B` 的 q4f16 在 WebGPU 上輸出純亂碼（數值精度問題），q4 則載不進去。
這個 repo 在瀏覽器裡**沒有任何可用組合**。已記錄在 `models.js` 避免日後重試。

**③ Qwen3 世代預設開啟 thinking，必須在模板層關掉。**
`Qwen3-0.6B` 不關的話會先吐一整段簡體中文的思考過程，
每回合 3.8 秒有大半花在思考上，而且會外洩到對話氣泡。
已在 `worker.js` 統一傳 `enable_thinking: false`，並在程式層處理未閉合的 `<think>`
（被 `max_new_tokens` 截斷時沒有結束標籤，只用成對標籤的正規表示式會漏）。

### 16.4 結論：品質門檻在 4B，與「手機也要能跑」直接衝突

```
品質可用的最小尺寸    ≈ 4B（3.0 GB，桌面 4.3 秒／回合）
手機瀏覽器的上限      ≈ 0.8B（665 MB）
                      ↑ 兩者之間差了一個數量級，而且沒有中間地帶
```

2B 已經證明中間地帶不存在——它比 0.8B 大兩倍、慢兩成，品質卻沒有變好。

**這不是多寫幾條規則能縮短的差距。** 六種工程手段（提示詞壓縮、JSON 前綴、
角色輪替示範、解碼層重複懲罰、程式算分、純文字輸出）已經把「格式與行為」全部修好；
剩下的是模型容量。

## 17. 手機優先路線：GGUF 執行層與 MiniCPM5-1B（2026-08-19）

### 17.1 為什麼要加第二個推論引擎

你指定手機優先、可以換模型家族、建議試 MiniCPM5-1B。查證後發現一個硬阻礙：

> **transformers.js 4.2.0 完全不支援 MiniCPM 架構。**
> 實測 grep 自帶的 bundle：Qwen2／Qwen3／Qwen3.5／Gemma3／DeepSeek2 都在，
> `minicpm` 零命中。而 MiniCPM 官方只提供 GGUF／MLX／MNN，沒有 ONNX。

也就是說：**不換引擎，模型選擇就被鎖在少數幾個家族裡。** 這是比模型好壞更根本的限制。

因此新增 `docs/engine/local/runtime-gguf.js`，用 **wllama**（llama.cpp 的 WASM 綁定）
直接執行 GGUF。介面與原本的 `runtime.js` **完全一致**
（`plan_` / `load` / `generate` / `abort` / `dispose`），
所以量測台與之後的 gateway adapter 換引擎不必改邏輯——handbook §2.3 的同一個原則。

選 wllama 之前先驗證了三件事（直接 grep 它的 wasm 二進位）：

| 檢查 | 結果 |
|---|---|
| `minicpm5` 架構 | ✅ 在 |
| `grammar` / `gbnf` / `json_schema` | ✅ 都在——**可在解碼層保證 JSON**，那是 transformers.js 缺的能力（§3.5） |
| WebGPU | ✅ 執行期回報可用 |

### 17.2 意外的收穫：離線快取問題解除

§13.5 記錄過 Cache API 存不了 436 MB 的權重（`Failed to execute 'put' on 'Cache'`），
導致每次開啟都要重新下載、「完全離線」不成立。

**wllama 用 OPFS 快取，實測有效：**

```
第一次   下載 688 MB
第二次   載入 4.7 秒
第三次   載入 2.8 秒   ← 完全來自 OPFS，沒有網路
```

這是本階段最實質的進展之一：**離線這件事在 GGUF 路線上是成立的。**

### 17.3 MiniCPM5-1B 實測

| 指標 | chat 模式 | **續寫模式（raw）** |
|---|---:|---:|
| 下載 | 688 MB | 688 MB |
| 載入（OPFS 命中） | 4.7 秒 | **2.8 秒** |
| 平均首 token | 783 ms | **571 ms**（最快到 116 ms） |
| 平均每回合 | 1,308 ms ✅ | **783 ms ✅** |
| 解碼速度 | 58.2 tok/s | 48.2 tok/s |
| 台灣繁中 | ✅ 零簡體 | ✅ 零簡體 |
| 角色正確 | ❌ 客服口吻 | ✅ 是客戶在說話 |

**783 ms／回合是所有測試中最快的**，比 Qwen3.5-0.8B（1,706 ms）快一倍以上。

### 17.4 chat 模式失敗與續寫模式的修法

MiniCPM5-1B 在 chat 模式下不演角色，回的是客服：

```
王小姐：好的，我明白您的問題。如果您想了解更多保險商品，建議您先諮詢…
        或保險產業的客服熱線。
王小姐：好的，我明白您的需求。請稍等，我會注意不要重複說話或過度取訪。
                                    ↑ 這是在覆述我們的重試指令
```

這是 assistant 對齊太強的典型症狀：**它把每一段輸入都當成「要協助的請求」。**

**續寫模式（raw completion）不給它請求，給它逐字稿讓它接著寫：**

```
業務員：……
王小姐：            ← 生成從這裡開始
```

模型的工作從「回應一個請求」變成「補完一段對話」，
**角色由文字結構決定，而不是由它願不願意配合指令決定。**
這與 JSON 前綴（§14.2）是同一個思路：用結構逼出行為，而不是用規則請求行為。

修好之後：

```
業務員：請問您現在有在規劃小孩的教育金嗎？
王小姐：嗯…沒有。                            ← 對題
業務員：那您平常最擔心的事情，大概是什麼呢？
王小姐：學費、退休金、還是其他方面？          ← 反問，合理
```

### 17.5 剩下的問題與下一步

MiniCPM5-1B 在續寫模式下已經是**手機路線目前最好的組合**：
688 MB、783 ms／回合、繁中乾淨、角色正確、OPFS 離線可用。

但 1B 的語言連貫度仍不足，會出現不通順的詞：

```
「嗯…這個應該很好。但您問得來，這些商品是什麼呢？」   ← 「您問得來」不成句
「好的，請告訂時。」                                ← 「請告訂時」不成詞
```

比 Qwen3.5-0.8B 好（至少對題、至少是客戶在說話），但仍不到 4B 的水準。

**建議接下來三件事，成本都很低：**

| # | 做法 | 為什麼 |
|---|---|---|
| **G1** | 測 MiniCPM5-1B 的 **Q8_0**（1,154 MB） | 量化損失小很多。不通順的詞很可能是 Q4 量化造成的，而不是模型能力。**這是最便宜也最可能有效的一步** |
| **G2** | 把續寫模式套到 Qwen3.5-0.8B（transformers.js 路線也能做） | 目前的比較不公平：Qwen 用 chat、MiniCPM 用續寫。要在同一個模式下比才知道哪個模型真的好 |
| **G3** | 用 GGUF 路線的 grammar 把 JSON 契約收回來 | llama.cpp 可以在解碼層保證合法 JSON，等於把 §14 因為 0.8B 而放棄的欄位契約重新拿回來，而且零失敗率 |

## 18. G1／G2 實測：量化與模式的公平對照（2026-08-19）

### 18.1 G1：Q8_0 證實那些不成句的詞是量化損失

| 指標 | MiniCPM5-1B Q4_K_M | **MiniCPM5-1B Q8_0** |
|---|---:|---:|
| 下載 | 688 MB | 1,154 MB |
| 載入（OPFS 命中） | 2.8 秒 | **3.6 秒** |
| 平均每回合 | 783 ms | **897～934 ms** |
| 解碼速度 | 48.2 tok/s | 53.3 tok/s |
| 語法 | ❌「您問得來」「請告訂時」 | ✅ **全部成句** |
| 挖到隱藏需求 | 0／3 | 1／3 |

**結論：不成句的詞是量化造成的，不是模型能力。** 代價是多 466 MB 與慢約 15%。
1B 這種規模對量化明顯比大模型敏感——這一條要寫進選型流程。

### 18.2 G2：同模式對照，並抓到一個我自己的實作缺陷

先講缺陷。Qwen3.5-0.8B 第一次跑續寫模式時，輸出一路變成：

```
王小姐：我…
業務員 :
業務員:
業務苑 ...
業務委員
```

原因是我的停止字串用**精確比對**（`'業務員：'`），而模型寫的是
「業務員 :」「業務員……」「業務苑」「業務委員」等近似變體，全都漏掉。

**正確的解法是回到問題本質：續寫模式的答案本來就只有一行。**
換行才是最穩的停止點，不必去猜模型會怎麼拼錯標籤。
標籤變體留作第二道防線（handbook §2.7）。

修好後的公平對照（都走續寫模式＋程式算分）：

| 模型 | 下載 | 每回合 | 語法 | 對話內容 | 隱藏需求 |
|---|---:|---:|---|---|---|
| Qwen3.5-0.8B | 665 MB | 1,407 ms | 通順 | **空洞**：「我好像聽不到您的聲音」「我……我不知道」 | 0／3 |
| MiniCPM5-1B Q4 | 688 MB | **783 ms** | 偶有不成句 | 對題但淺 | 0／3 |
| **MiniCPM5-1B Q8** | 1,154 MB | 897 ms | ✅ 通順 | **對題、會透露隱藏需求** | 1／3 |

**另一個發現：模式要配模型。** Qwen3.5-0.8B 在 chat 模式（1,706 ms）比續寫模式好，
MiniCPM5-1B 則相反（chat 1,308 ms／續寫 897 ms，且 chat 模式完全不演角色）。
所以「哪個模式好」沒有通則，**必須每個模型各自實測**。

### 18.3 新增兩個程式層檢查（都由實測逼出來）

**① 過度順從 —— 比講不通更危險**

Q8_0 出現這句：

```
業務員：我下週三下午三點過去跟您說明二十分鐘，可以嗎？
王小姐：好的，請您不要擔心，這個保險我一定會買。
```

**秒答應購買會給新人虛假的成功感**，讓他以為那套結巴、沒重點的開場是有效的。
handbook §9.3 第 14 條說訓練工具不能打擊信心——但同樣不能給假的成功。

判定分兩級，對應 `DIFFICULTY` 本來就有的規則：
Level 1 的客戶「會答應合理的請求（例如約時間）」——**那是約時間，不是買保險**。
所以答應見面放行，承諾購買一律攔下重新生成。

**② 照抄人設文字**

隱藏需求原文是「擔心自己萬一倒下，女兒的生活費與學費沒人接手」，
模型回「我一直很懷疑自己萬一倒下，女兒的生活費與學費沒人接手。」——幾乎逐字。

程式偵測得到「碰到主題」（那是好事），但照抄設定文字不像真人講話。
這與 D030（示範台詞會被照抄）是同一個病，只是換了照抄的對象。

**同時改良了重試指令。** 原本的重試只說「剛才的回答不對」，對小模型沒有作用。
現在依實際攔到的問題給具名指示：

| 攔到什麼 | 重試時告訴模型 |
|---|---|
| 過度順從 | 你答應得太快了。你還不了解對方要賣什麼，不可能馬上決定要買。 |
| 照抄人設 | 不要照著設定的文字念。用你自己的口語說同一件事，句子要短。 |
| 演錯角色 | 你把自己說成打電話來的人了。你是接電話的那一位。 |

確定性測試從 35 項增加到 **41 項**，全部通過，且不需要模型也不需要金鑰。

### 18.4 目前最佳組合與剩下的問題

```
MiniCPM5-1B Q8_0 ＋ 續寫模式 ＋ 程式算分 ＋ 六項程式層攔截
  下載 1,154 MB｜載入 3.6 秒（OPFS）｜每回合 897 ms
  繁體中文通順、零簡體、角色正確、信任度會動且判定可解釋
```

**剩下的問題（下一輪處理）：**

新的失敗型態：**客戶反過來推銷。**

```
王小姐：沒問題，請您查閱，我還有兩個保險產品供您選。
```

`claimsToBeAgent()` 攔不到——它沒有自稱業務員，而是扮演了「供給方」。
這是同一類問題的第三種變形（自稱業務員 → 照抄人設 → 角色反轉），
要在 `turn-signals.js` 補上第三個檢查。

**已補上（2026-08-19）：** H1 角色反轉檢查完成，
`invertsRole()` 攔「供您選」「請您查閱」「我可以幫您安排」這類供給方行為，
且不誤判「我們公司有保團保」這種正常客戶發言。
六項程式層攔截全部就位，確定性測試 **45 項全過**。

實測結果：所有結構檢查歸零（0 次違規），每回合 804 ms。
**但語意連貫度在 1B 上是「一次好一次壞」的**——同一份腳本跑兩次：

```
較好的一次：還沒有，我正在尋找一些解決這些問題的方法。／是健康問題，還是經濟問題？
較差的一次：好，那我會去接個客人，會有幾個客人。
```

這是 1B 的天花板，不是攔截漏掉。**程式層能保證「不會做錯事」，但不能保證「講得好」。**

**還沒做的兩件事：**

| # | 項目 | 為什麼重要 |
|---|---|---|
| **H1** | 角色反轉檢查（客戶提供商品／要對方查閱） | 目前唯一還會漏的角色錯誤 |
| **H2** | 用 llama.cpp 的 grammar 把 JSON 欄位契約收回來 | 解碼層保證合法 JSON，可把模型的 `revealed` 訊號當程式判定的第二來源 |
| **H3** | **iPhone 14 Pro 實機驗證（Go／No-Go）** | 1,154 MB 在 iOS Safari 能不能載入，是整條手機路線的關鍵未知 |

**H3 是唯一的關卡。** 桌面數字再好，手機載不進去就不成立。

| 檢查 | 結果 |
|---|---|
| Wi-Fi 網卡 IP | `10.22.188.36`（DHCP 取得）✅ 位址正確 |
| 伺服器監聽 | `0.0.0.0:8443` ✅ 所有介面都聽 |
| Windows 防火牆 | `node.exe` 在 **Public** 設定檔已允許 TCP 任意埠 ✅ |
| 網路類型 | `AAA000-DOT1x`，Public，**802.1x 企業網路** |

**結論：公司 Wi-Fi 的用戶端隔離（AP isolation）。**
這類企業網路預設禁止裝置之間互連——可以上網，但手機看不到筆電。
不是程式或設定能解決的，換網路即可。

順帶記錄：`192.168.242.1` 與 `192.168.43.1` 是 VMware 虛擬網卡，不是可用的區域網路位址。
`serve.mjs` 會把它們一起印出來，容易誤導。

### 19.2 因此新增「本機模型鏡像」

不論用家裡 Wi-Fi 還是個人熱點，都有一個現實問題：
**模型從 HuggingFace 下載，手機每測一次就吃掉 1,154 MB 行動網路流量**，
用熱點測更是直接燒手機數據。

| 檔案 | 用途 |
|---|---|
| `tools/fetch-model.mjs` | 把 GGUF 抓到 `models/`（不進版控）；寫暫存檔再改名，中斷不會留壞檔 |
| `tools/serve.mjs` | 新增 `/models/*` 路由，**支援 HTTP Range（206）**，模型檔設長期快取 |
| `engine/local/runtime-gguf.js` | `mirrorBase` 選項：改用 `loadModelFromUrl` 從自架路徑載入 |
| `docs/lab.js` | `?mirror=1` 參數 |

Range 支援是必要的而非加分：wllama 與 transformers.js 都會分段抓大檔，
不回 206 會整檔重抓或直接失敗。

**桌面實測（從鏡像載入）：** 1,154 MB 下載＋載入共 8.9 秒；五回合平均 990 ms ✅

**附帶效果：這證明模型可以自架。** 日後若不想依賴 HuggingFace CDN
（公司內網部署、或 HF 被擋），路徑已經驗證可行。

### 19.3 今晚在家要做的事

前提：手機與筆電連同一個家用 Wi-Fi。

```bash
node tools/serve.mjs
```

用 iPhone 開（IP 換成 `serve.mjs` 印出的「手機」那一行，家用網路通常是 192.168.x.x）：

```
https://<IP>:8443/lab.html?m=minicpm5-1b&dt=q8&raw=1&mirror=1
```

第一次會有憑證警告 →「顯示詳細資訊」→「瀏覽此網站」。
接著按「偵測」→「載入」→「跑五回合」。

**要記錄的三件事：**

| # | 項目 | 為什麼 |
|---|---|---|
| 1 | 偵測區塊的 WebGPU 與 **maxBufferSize** | Safari 的 Metal 緩衝區上限是手機上最常見的死因（§3.2） |
| 2 | 載入成功或錯誤訊息 | `[load]` 是記憶體／緩衝區不足；`[download]` 是網路 |
| 3 | 五回合平均每回合毫秒 | 與桌面的 990 ms 對照，看手機掉多少 |

**若 Q8_0（1,154 MB）載不進去**，把網址的 `dt=q8` 改成 `dt=q4`（688 MB）再測。
兩個檔案都已下載到 `models/`，不必再等。

Q4 的代價是語法偶有不成句（§18.1），但那時我們至少知道
「手機的上限落在 688 MB 與 1,154 MB 之間」——那是可以據以決策的事實。

## 20. H3 手機實機驗證結果：iPhone 上瀏覽器內推論不可行（2026-08-19）

**裝置：iPhone 14 Pro，iOS 26.6，Safari，家用 Wi-Fi，模型由開發機提供。**

> 補記一個我判斷錯的地方：我曾依 User-Agent（`iPhone OS 18_7`）斷定裝置是 iOS 18.7，
> 使用者截圖顯示實際是 **iOS 26.6**。**Safari 從 iOS 26 起回報凍結的 UA 字串**，
> 用 UA 推版本是錯的。使用者當時說的版本才是對的。

### 20.1 完整測試矩陣

| # | 組合 | 結果 |
|---|---|---|
| 1 | 記憶體上限（wasm / ArrayBuffer） | **2,048 MB / 3,072 MB 都通過**（撞到測試上限，不是裝置上限） |
| 2 | 網路 / OPFS 寫入 | 11.9 MB/s / 533 MB/s，皆正常 |
| 3 | 下載 1,154 MB（自建路徑） | ✅ 成功 |
| 4 | GGUF 載入 1,154 MB（Q8，GPU） | ❌ 分頁崩潰 |
| 5 | GGUF 載入 688 MB（Q4，GPU 與 CPU 都試） | ❌ 分頁崩潰 |
| 6 | GGUF 載入 105 MB（GPU，`ngl=99`） | ✅ 載入成功，**生成時崩潰** |
| 7 | **GGUF 載入 105 MB（CPU，`ngl=0`）** | ✅ **完整跑完**，1.8 秒載入 |
| 8 | ONNX 載入 665 MB（WebGPU） | ❌ 載入到一半分頁崩潰 |

### 20.2 三個確定的結論

**① 崩潰與記憶體無關。** 這是最重要的排除。
實測 wasm 可長到 2 GB、ArrayBuffer 可到 3 GB，而 688 MB 就崩。
若沒有先量記憶體，幾乎一定會誤判成「手機記憶體不夠，換更小的模型就好」——
那個方向是錯的，會浪費很多時間。

**② WebGPU 在 iPhone 上「宣稱可用」但跑不動 LLM 推論。**
`navigator.gpu` 存在、`shader-f16` 支援、`maxBufferSize` 1,074 MB——**能力回報全部正常**。
但實際跑推論時：

| 引擎 | WebGPU 的結果 |
|---|---|
| wllama（llama.cpp／asyncify） | 生成中分頁崩潰 |
| transformers.js（ONNX Runtime Web） | 載入中分頁崩潰 |

**兩個完全獨立的引擎、兩種不同的失敗階段。** 這指向 iOS Safari 的 WebGPU 實作
在大型工作負載下不穩，而不是某一個函式庫的 bug。
`ngl=0`（完全不用 WebGPU）是唯一跑完的組合——**這就是證明**。

**③ CPU 模式能跑，但速度差兩個數量級。**

| | 桌面（RTX 4060） | iPhone（CPU，135M 模型） |
|---|---:|---:|
| 每回合 | 804 ms（1B 模型） | **8,230 ms（135M 模型）** |
| 解碼速度 | 53～59 tok/s | **2.9 tok/s** |

而且那是 **135M** 模型——參數量只有 MiniCPM5-1B 的八分之一，中文品質完全不能用。
規格 §29 要求每回合 ≤ 2 秒，這裡是 8.2 秒，**而且用的是最小的模型**。

### 20.3 因此路線 A 在 iPhone 上的答案是「不可行」

不是「還需要調校」，而是三個獨立的天花板同時存在：

```
WebGPU 推論      → 崩潰（兩個引擎都是）
CPU 推論         → 2.9 tok/s，每回合 8 秒，而且只能載入 105 MB 級的模型
可載入的模型上限  → 105 MB 可以、688 MB 不行（原因不是記憶體總量）
```

**能跑的那個組合（135M＋CPU）對這個產品沒有意義**：
它既達不到速度目標，中文品質也不可能演出一位台灣客戶。

### 20.4 桌面的結論相反：完全可行

同一套程式在桌面（Chrome／WebGPU）上全部驗證通過：

| 模型 | 每回合 | 備註 |
|---|---:|---|
| MiniCPM5-1B Q8_0（GGUF） | **804 ms** | 繁中乾淨、OPFS 離線可用 |
| Qwen3.5-0.8B（ONNX） | 1,407 ms | |
| Qwen3.5-4B（ONNX） | 4,340 ms | **對話品質唯一可用的等級** |

所以「完全離線」這件事**在桌面上是成立的**，在 iPhone 上不成立。

### 20.5 順帶修掉一個我的設定錯誤

實機出現 `request (2065 tokens) exceeds the available context size (2048 tokens)`。

`n_ctx` 設 2048 太小：續寫模式的提示詞本身約 1,000 token
（system 857 字＋兩組角色輪替示範），逐字稿再累積兩三回就爆。
**這是設定錯誤，不是模型限制**，已改為 4096（記憶體增加很小）。

值得記下來的是它的表現方式：**演練到第三回合才失敗**。
前兩回合完全正常，所以在短測試裡看不到——這類「隨對話長度累積才爆」的問題，
只有跑完整輪次才會出現（handbook §10.1 端到端測試的價值）。

## 20. 最後一句

手冊 §12 說：「這個產品的價值不在模型多強，而在程式有多懂業務實務。」

**本專案是這句話最極端的一次測試。** 我們把模型從雲端等級換成 0.8B，
少掉的能力必須由程式補回來——難度數值由程式夾住、資訊邊界由程式檢查、
分數由程式計算、上下文由程式管理、用語由程式過濾。

如果做成了，它證明的不是「小模型很厲害」，
而是**這套引擎對業務實務的理解已經深到可以不依賴模型的聰明**。

反過來說：如果為了讓 0.8B 跑起來，而把難度規則砍成一行、把評分交還給模型、
把資訊邊界檢查省掉——那就會做出一個能離線但沒有價值的東西。
**離線是手段，不是目的。**
