## 一、執行摘要

這個版本已經不是概念展示，而是一個可安裝、可登入、可接多家模型、具文件解析、語音演練、評分與同步能力的完整 PWA 原型。最值得保留的不是「六個功能很多」，而是已形成一套清楚的產品思想：**讓業務員跟 AI 反覆練習，而不是只向 AI 問答案**；並用程式狀態機約束角色、資訊邊界、難度、結束條件與合規攔截。

目前真正的瓶頸也已經不是「再加功能」，而是從可用原型跨到可信任產品時，必須補上的四件事：

1. **帳號與本機資料隔離**：目前同一裝置切換帳號時，紀錄、文件與 API 金鑰可能跨使用者沿用。
2. **資料傳輸說明正確性**：文件雖不存入 Firebase，內容仍會送往所選 AI 服務商處理；目前介面文字容易使人誤解。
3. **訓練成效可信度**：評分尚未用 Golden Reference 校準，也沒有形成「目標—練習—回饋—再練—比較」的完整成長閉環。
4. **高風險功能邊界**：理賠、法規與商品內容的回答，現階段仍不足以承擔精確諮詢定位。

**總結判斷：**

- 作為內部概念驗證／小規模試用：**已達可用水準**。
- 作為可擴大給公司同仁長期使用的正式產品：**需要先完成 P0 資料與告知修正**。
- 作為可商業化、可對外銷售的 App：**尚未達標**，主要差距在權限、隱私、評分校準、營運監控與核心 IP 架構。
- 下一階段不建議先做更多新功能；應先把「安全、可信、可衡量」做紮實。

## 三、產品定位判斷

目前產品最清楚、也最有差異化的定位是：

> **一個以語音角色扮演為核心，能陪保險業務員反覆練習、給出具體回饋並累積能力成長的 AI 教練。**

這個定位應繼續維持。未來每個功能都應接受三個檢驗：

1. 它是否讓使用者「實際練習」，而不是只拿到一份 AI 答案？
2. 它是否能產生下一次可執行的改善行動？
3. 它是否能證明使用者比上一次進步？

依這三項標準，目前「電話邀約」「發掘需求」「商品行銷演練」最符合核心定位；「痛點分析」是很好的演練前準備；「理賠諮詢」與「問問其他問題」則較像通用 AI 助理，會稀釋產品定位，也帶來較高風險。

### 建議的首頁產品層級

首頁不應讓六個功能看起來同等重要。可重組為：

1. **開始一場練習**：電話邀約、發掘需求、商品行銷。
2. **演練前準備**：客戶假設分析、教材整理。
3. **教練與紀錄**：問教練、我的訓練計畫、進步紀錄。
4. **專業輔助工具**：條款閱讀輔助，清楚標示其限制。

這會讓使用者更快理解：App 的核心是「練」，不是六個彼此分離的 AI 工具。

## 五、值得保留的設計與技術

### 1. 程式控制狀態，模型負責語言

`engine/session.js` 把狀態、最低回合、信任值、揭露需求、結束條件與續命交給程式處理，不把所有控制權交給 LLM。這是整個專案最正確的架構決策之一，必須保留。

### 2. Role Lock、資訊邊界與兩層防護

陌生開發、轉介紹、既有客戶等情境會限制示範話術可使用的資訊；品牌中立化、後設用語清理與繁簡轉換也不只靠提示詞。這些都是「程式懂業務實務」的具體證據。

### 3. Model Gateway 與 Judge 分離

角色扮演重速度、評分重品質；同時提供多服務商、自動選模、429／逾時降階與使用者提示。這個抽象層值得保留，未來接公司代理層、本地模型或原生 App 都能延續。

### 4. PWA 與低維運成本

GitHub Pages、Service Worker、主畫面捷徑、iOS 安裝教學與離線外殼，讓試用門檻與維運成本都很低。對內部試點很合適。

### 5. 新手友善預設與演練續命

難度預設為新手友善、卡住時分級提示、分頁重新整理後可接回演練，符合成人學習與低壓高挑戰的原則。

### 6. 決策紀錄與實測文化

`DECISION_LOG.md` 不只記結果，也記錄錯誤假設、實測發現與推翻原因。這會大幅降低未來 Claude Code、Codex 或其他工程師接手時重踩舊坑的機率，建議繼續維護。

## 六、必須立即改善（P0）

### P0-1：同一裝置切換帳號會造成資料與金鑰跨使用者

目前訓練紀錄使用固定 `aicoach.history`、偏好使用固定 `aicoach.prefs`、API 金鑰使用固定 `aicoach.apikey`，文件也共用同一個 IndexedDB。Firebase 登出只移除帳號 token，刻意保留上述本機資料。

因此若 A 使用者登出帳號，B 使用者在同一瀏覽器登入：

- B 可能直接使用 A 的 API 金鑰，費用算在 A 身上。
- B 可以看到 A 上傳的教材或保單條款。
- `afterAuth()` 會先執行同步，A 的本機訓練紀錄可能被合併並上傳到 B 的 Firebase 節點。

這是目前最嚴重的資料隔離問題。

**立即修正：**

- 所有本機資料以 Firebase `uid` 命名空間隔離，例如 `aicoach.<uid>.history`。
- IndexedDB 文件加上 `ownerUid`，查詢與刪除都必須限定該 uid。
- API 金鑰也應綁 uid，或在 Firebase 帳號登出時一併清除。
- 登入新帳號前先偵測未歸屬舊資料，讓使用者選擇「保留給原帳號／刪除」，不可自動併入新帳號。

### P0-2：「文件不會上雲端」的說法與實際行為不一致

`knowledge.js` 會把 DOCX／PPTX／TXT 的文字內容放進 prompt；PDF 則直接以 base64 傳給 Gemini 或 Anthropic 解析。理賠查詢時還會再次傳送條款原文或 PDF。

所以正確描述是：

> 文件原檔與知識庫不儲存在本專案的 Firebase；但為了產生摘要、演練或條款閱讀結果，文件內容會傳送給使用者選擇的 AI 服務商處理。

目前登入頁、程式註解與 README 多處使用「不會上雲端」「只留在裝置」的表述，容易讓同仁誤以為文件內容從未離開手機。若是公司教材或客戶保單，這個誤解特別嚴重。

**立即修正：**

- 上傳前顯示一次明確告知，列出目前服務商與將傳送的資料種類。
- 把「不上雲端」全部改為「不儲存在 AI業務教練的雲端資料庫」。
- 分別說明：本機保存、Firebase 同步、AI 服務商處理三條資料流。
- 提供「刪除本機文件」與資料處理說明頁。

### P0-3：「清除所有紀錄」無法刪除雲端資料

目前按鈕只執行 `localStorage.removeItem(LS)`，沒有同步刪除語意。下次同步採聯集合併時，雲端舊資料會再次回到本機。

這不只是 UX 問題，也代表使用者無法真正控制自己的訓練資料。

**立即修正：**

- 提供「只清除此裝置」與「刪除所有裝置及雲端紀錄」兩個明確選項。
- 雲端刪除必須是真正 DELETE 或具 tombstone 的同步機制，不能再用聯集還原。
- 刪除後顯示結果與失敗重試，不可靜默忽略。

### P0-4：理賠與法規定位超過目前驗證能力

現在理賠功能依單一文件、最多截取部分文字或保存 6MB PDF，再由模型產生結構化答案。它不知道完整保單組合、批註、保額、生效日、除外責任與個案文件；目前也沒有條款引用的程式驗證、Golden Reference 或人工複核流程。

**立即修正：**

- 先把功能降級為「條款閱讀與核對清單」，不要對外宣稱能算出理賠金額。
- 回答必須逐項附來源頁碼／條款原文；找不到原文就不得下結論。
- 顯示「仍缺哪些資料」與「應向公司理賠單位確認什麼」。
- 「問問其他問題」中的法規回答亦應套用同一原則。

### P0-5：公開倉庫與核心 IP 保護目標互相衝突

`.gitignore` 排除了原始完整 GPT 指令，但 `docs/engine/prompts.js`、完整產品規格、Coach Engine 規則與決策紀錄都已公開。純前端執行也代表提示詞與隱藏需求必然能在瀏覽器中查看；目前「hidden state 不下發到 client」在純前端架構下並不是真正的保密。

**立即決策：**

- 若目標是開放學習與建立個人品牌：保留公開，但補正式授權條款，接受核心方法可被閱讀。
- 若目標是商業化與保護方法論：核心 prompt、評分規則、Persona／隱藏狀態移到受控後端，倉庫改 private 或只公開展示層。
- 壓縮或混淆 JavaScript 不能提供真正的 IP 保護。

### P0-6：強制登入不等於內部使用權限

正式站公開，任何人都可自行註冊 E-mail 帳號。Firebase 規則能防止使用者互看資料，但不能限制誰有資格使用產品。若這是公司內部工具，現在的登入只提供身分與同步，不是門禁。

**立即決策：**

- 公開試用產品：清楚標示公開註冊，並處理濫用與成本風險。
- 公司內部產品：加入網域／名單／邀請碼審核，並在伺服器端真正執行；純前端不能可靠守門。

## 七、重要優化（P1）

### 1. 同步機制仍可能在兩台裝置同時寫入時遺失資料

目前流程是「拉整包 JSON → 本機合併 → PUT 整包 JSON」。若兩台裝置同時拉取、各新增一筆、再先後 PUT，最後寫入者可能覆蓋另一台的新紀錄。程式內的聯集只能合併自己當下看得到的資料，無法解決併發寫入。

**建議：** 每次演練以不可碰撞的 session UUID 存成獨立子節點，用 PATCH／push 寫入；偏好設定使用版本或伺服器時間戳。不要再整包覆蓋 `/users/<uid>`。

### 2. 評分尚未具備跨模型、跨版本可比較性

目前分數由 Judge Model 生成，再被程式四捨五入至 0.5 星。不同模型、模型更新、prompt 更新都可能改變尺度；歷史紀錄卻沒有保存模型、prompt／rubric 版本，因此「進步曲線」可能混合不同尺。

**建議：**

- 每筆紀錄保存 provider、model、rubricVersion、promptVersion。
- 建立 50～100 個 Golden Reference 案例，由業務訓練專家給出合理區間。
- 將可確定的指標（回合數、贅詞、重複、邀約目標是否完成、需求確認數）與 LLM 質性判斷分開呈現。
- 先驗證一致性，再用平均星等做成長指標。

### 3. 「成長閉環」仍不完整

目前有單次回饋與平均星等，但紀錄頁沒有真正使用已保存的 `next challenge`，也沒有依弱項安排下一次練習、同情境重練與前後話術比較。

**建議的最小閉環：**

> 選定一項能力 → 練習 → 一個最重要改善點 → 立即重練 → 並排比較 → 排入下一次挑戰

這一項比增加第七個功能更能提高留存與學習成效。

### 4. 入口摩擦過高

新使用者需完成「安裝 PWA → 建立帳號 → 登入 → 申請服務商金鑰 → 貼金鑰 → 才能開始」。這對技術熟悉者可接受，對一般業務同仁會造成明顯流失。

**建議：**

- 加入不需 AI 的 60 秒腳本式示範，先讓人看見練習流程與回饋長什麼樣。
- 顯示清楚的步驟進度與預估時間。
- 公司試點可提供受控的限額體驗額度，完成第一次演練後再引導 BYOK。
- 以「完成第一場練習」作為啟用成功指標，而不是註冊成功。

### 5. 零外部相依不應成為正式產品的絕對目標

目前零 `node_modules` 讓部署簡單，但也讓專案自行處理 ZIP、XML、Auth REST、同步與格式解析。原型階段是優勢；進入正式產品後，安全更新、瀏覽器相容性與可測試性可能比「零相依」更重要。

**建議：** 保留小而清楚的架構，但允許引入經審核、可鎖版、可掃描的必要依賴，不把零相依當 KPI。

### 6. 安全基線需要提升

- API 金鑰與 Firebase refresh token 都保存在 `localStorage`，任何同頁執行的惡意腳本或 XSS 都可能讀取。
- 頁面沒有明確 Content Security Policy；Google 登入腳本為執行期外部載入。
- Realtime Database 規則只有 uid 隔離，沒有欄位 schema、大小與型別驗證。
- 公開註冊可能造成垃圾帳號與資料庫濫用。

**建議：** 優先消除可插入 HTML 的路徑、加入可行的 CSP、對資料庫加 `.validate`、限制 payload 大小、加上帳號濫用防護；商業版則把長效憑證與共用金鑰移出前端。

### 7. 可及性與裝置測試要正式化

`viewport` 使用 `user-scalable=no`，會妨礙需要放大文字的使用者。畫面以 fixed 全螢幕為主，也需要在鍵盤彈出、動態字級、橫向 iPad、VoiceOver 與低對比環境下實測。

**建議測試矩陣：** iPhone Safari PWA、iPhone Chrome、Android Chrome、iPad 分割畫面、Windows Chrome／Edge；每種測登入、安裝、麥克風、TTS、切到背景、恢復、檔案上傳與長時間演練。

### 8. 文件與實作需建立單一真實來源

## 八、測試與工程成熟度

### 已有優點

- `tools/selftest.mjs` 以實際產品流程驗證模型行為，而非只測函式。
- 合規、繁簡轉換、模型降階、同步合併與資訊邊界已有確定性檢查概念。
- 所有 JavaScript 語法檢查通過；正式站入口可載入。

### 主要缺口

- 沒有 GitHub Actions／CI，每次 push 不會自動檢查語法、資源、確定性測試與部署品質。
- 自我測試在檔案開頭就要求 Gemini 金鑰，導致不需模型的規則測試也無法在無金鑰環境執行。
- 沒有固定的 mock／recorded response 測試，無法區分「程式壞了」與「模型今天輸出不同」。
- 沒有瀏覽器端 E2E 測試、手機裝置矩陣、可及性測試與同步併發測試。
- Golden Reference 尚未建立，評分與教練品質無法客觀回歸。

### 建議測試分層

1. **每次 commit 必跑**：語法、imports、DOM id、純函式、同步、合規、資料隔離、刪除語意。
2. **每次 PR 必跑**：瀏覽器 E2E，使用 mock 模型回應完成六大流程。
3. **每日或手動跑**：使用真實 Gemini／Groq 的整合測試，監控延遲與模型格式漂移。
4. **版本發布前跑**：Golden Reference、iPhone／Android 實機語音、Firebase 安全與資料刪除。

## 九、建議的產品指標

目前管理報表偏向「誰練了幾次、平均幾星」，不足以判斷產品是否真的有效。建議分四層：

| 層級 | 指標 |
|---|---|
| 啟用 | 看過首頁後完成第一場演練的比例、從開啟到完成首練的時間、卡在帳號或 API 金鑰的比例 |
| 體驗 | 建立客戶延遲、每回合延遲、STT 無結果率、演練中斷率、評分生成失敗率 |
| 留存 | 7 日內再次練習比例、每週練習天數、同情境重練比例 |
| 學習 | 指定弱項重練後是否改善、邀約目標達成率、需求探索完整度、教練建議採用率 |

不要只用平均星等做成效證明；在評分尚未校準前，它更適合當回饋介面，而不是績效數據。

## 十、建議執行順序

### 第一階段：0～3 天，先止血

1. 修正跨帳號的歷史、文件、API 金鑰與偏好隔離。
2. 修正「文件不上雲端」的所有文案與上傳前告知。
3. 修正清除紀錄，讓使用者可真正刪除雲端資料。
4. 將理賠功能改名並降低輸出承諾；法規問題加上來源要求。
5. 決定 GitHub 公開／核心 IP 保護的產品路線。

### 第二階段：1～2 週，建立可信任基線

1. 同步改為每筆紀錄獨立寫入，處理併發與刪除。
2. 加入資料處理說明、服務商告知、帳號切換與刪除流程。
3. 拆分確定性測試與真實模型測試，建立 CI。
4. 每筆紀錄保存模型與 rubric 版本。
5. 完成 10～20 位內部使用者的可用性試點。

### 第三階段：2～6 週，強化核心價值

1. 建立第一批 50 個 Golden Reference 案例。
2. 完成「立即重練＋前後比較＋下一次挑戰」成長閉環。
3. 將首頁重組成「練習／準備／教練與紀錄／專業輔助」。
4. 商品與條款回答加入可驗證的來源引用。
5. 建立裝置與語音測試矩陣。

### 第四階段：通過試點後，再決定原生 App

原生 iOS PoC 應只驗證網頁無法解決的價值：真正 Barge-in、回音消除、本地 STT、背景恢復與長時間穩定性。若原生語音沒有顯著提升「完成率、重練率與留存」，就不必急著全面重寫。

## 十二、最終建議

這個 App 最有價值的資產，不是目前六大功能的數量，而是已經被工程化的業務教練方法：角色鎖定、情境資訊邊界、新手友善難度、需求逐步揭露、具體回饋與下一步挑戰。

因此下一版的主題不應是「V1.1 再多兩個功能」，而應是：

> **把 AI業務教練從「功能完整的原型」，升級成「同仁敢放資料、願意反覆練、而且能看見自己進步的訓練產品」。**

建議優先順序只有一句話：

> **先修資料隔離與告知，再建立評分可信度與重練閉環，最後才擴功能或全面原生化。**
