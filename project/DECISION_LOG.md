# DECISION LOG

記錄會影響架構、且事後容易忘記「為什麼這樣選」的決策。

---

## 2026-08-16｜D001 網頁測試版的 LLM 先接 Gemini API，而非本機模型

**決策：** V0.1 走 Gemini API（`gemini-3.7-flash`），本機模型延後到原生 iOS 階段。

**為什麼：** 規格 §27 要求 Local-first，但 iPhone Safari 分頁記憶體上限約 1～1.5GB，
Gemma 3n E2B 量化後仍需 2～3GB，網頁版在 iPhone 上不可能跑本機模型。
若為了「local-first」而在網頁版硬塞小模型，只有桌機能測，反而測不到真正的目標裝置。

**影響：** 未違反 Model-Agnostic 原則——所有模型呼叫都經過 `lib/gateway.js`。
原生 App 階段新增 local adapter 即可，Coach Engine 不需修改。

## 2026-08-16｜D002 語音採用瀏覽器內建 Web Speech API

**決策：** STT/TTS 使用 iOS Safari 內建的 `webkitSpeechRecognition` 與 `speechSynthesis`。

**為什麼：** 零下載、零費用、延遲低、支援 zh-TW，且錄音不需經過我方伺服器，
符合規格 §81「不得預設把完整錄音上傳第三方」。

**代價：** iOS 無法在 TTS 播放時穩定同時收音，因此規格 §31 的 Barge-in
在 V1 降級為「點麥克風打斷」。此限制已記錄於 `app/README.md`。

## 2026-08-16｜D003 核心教練邏輯放伺服器端，前端只留 UI 與語音

**決策：** Prompt、Persona 隱藏狀態、評分邏輯、合規規則全部在 `app/lib/`，
瀏覽器只收到 Public State。

**為什麼：** 規格 §36、§37 要求核心 IP 不明文放在 Client。
副作用是前端變得很小，也符合「程式碼精簡」的要求。

**驗證：** `tools/selftest.mjs` 有一項專門斷言 Client 回應不含 `hidden_needs`。

## 2026-08-16｜D004 演練的結束時機由程式判定，不交給 LLM

**決策：** LLM 回傳的 `end` 訊號，只有在使用者已完成至少 4 個回合後才採信；
連續三次無效回應則強制結束（規格 §17）。

**為什麼：** 實測發現難度 3 的客戶在第 1 回合就回「不用再打來了」並把 `end` 設為 true，
演練還沒開始就結束。這是規格 §92「重要產品邏輯由程式控制」的實例。

## 2026-08-16｜D005 Model Gateway 需處理過載降級

**決策：** 同一模型重試 3 次（指數退避），仍失敗則自動降級到偏好清單的下一個模型。

**為什麼：** 開發當天實際遇到 `gemini-3.7-flash` 回 503 過載與 429 額度用盡。
若不處理，使用者會在演練到一半時看到錯誤而中斷。

**另註：** Gemini 3.x 的思考 token 會計入 `maxOutputTokens`，額度不足時回傳空字串。
額度必須放寬（Persona 4000／回合 1200／評分 8000），這是很容易誤判成「模型不穩」的坑。

## 2026-08-16｜D006 角色扮演改用 flash-lite 作為主要降級目標

**決策：** `PREFER_FAST` 順序調整為 3.7-flash → 3.6-flash → **3.5-flash-lite** → 3.1-flash-lite
→ …→ 3.5-flash（墊底）。

**為什麼：** 實測（同一段提示詞、同一時間）：

| 模型 | 延遲 |
|---|---|
| gemini-3.5-flash-lite | 1.1 秒 |
| gemini-3.1-flash-lite | 1.4 秒 |
| gemini-3.5-flash | 26.5 秒（免費方案被重度限流） |

原本把 3.5-flash 排在 lite 前面，導致降級後每回合要等 26～36 秒，語音對練完全不可用。
客戶回話只有 1～3 句，lite 的品質實測足夠，且 1.1 秒直接達成規格 §29 的 ≤2 秒目標。

**啟示：** 規格 §81「不要只看 Benchmark Leaderboard」在這裡完全應驗——
真正決定體驗的是「這把金鑰、這個方案、這個時段」的實際延遲，不是模型的紙面能力。

## 2026-08-16｜D007 文件解析不裝任何套件：Office 自解，PDF 交給模型

**決策：** `.docx`／`.pptx` 用自寫的 ZIP+XML 解析（`lib/docx.js`，60 行）；
`.pdf` 直接把原始位元組交給 Gemini 讀。不使用 `pdfjs-dist` 等套件。

**為什麼：**
・`.docx`／`.pptx` 本質就是 ZIP 裡的 XML，Node 內建 zlib 就能解，沒必要引入相依。
・PDF 相反——中文 PDF 大量使用 CID 字型與子集嵌入，自寫解析器常常取出亂碼；
　掃描版更是完全取不到字。模型原生讀 PDF 可以連圖表與掃描頁一起理解。

**驗證：** 用使用者自己的 `【AiCoach】AI業務教練.pptx` 實測，13 頁全部正確取字分頁。

## 2026-08-16｜D008 知識庫採「一次結構化，之後查摘要」

**決策：** 上傳時呼叫一次模型，把文件轉成結構化 JSON（商品：FABE 賣點／條款：給付項目窮舉）。
之後的演練與查詢只帶這份摘要，不重送整份文件。

**為什麼：** 對應規格 §41 的 Knowledge Structuring。若每次查詢都重送 100 頁條款，
在免費方案的 TPM 限制下很快就會撞牆，且延遲不可接受。

**例外：** 理賠查詢會回頭附上條款原文（PDF ≤6MB 時送原始檔）。
理賠答錯的代價比多花 token 高，準確度優先。回覆會標示是否有比對原文。

## 2026-08-16｜D009 隱藏需求的揭露改用「編號」而非「原字照抄」

**決策：** 角色扮演時，模型回傳 `revealed: [1,3]` 這種編號，由程式映射回實際文字。

**為什麼：** 原本要求模型把透露的隱藏需求「原字照抄」回 JSON，實測 4 個回合下來
一項都沒記錄到，即使客戶明顯已經鬆口。改成編號後，同樣的情境正確記錄到 2／3 項。

**啟示：** 小任務要遷就模型擅長的形式。要模型在演戲的同時精確複製長字串，
是不必要的認知負擔；讓它挑編號就準確得多。

## 2026-08-16｜D010 教練不得建議捏造聯繫理由

**決策：** 在 `COACH_CHAT` 加入紅線：不得建議假名額、假優惠、假停售、假核保結果、
假裝「剛好經過」。

**為什麼：** 實測時教練回覆建議業務員「給他一個好用的藉口」「最近剛好有一個核保優勢／名額」。
這雖然是業界常見話術，但屬於不實招攬，且與規格 §54「不應鼓勵欺騙」直接衝突。
加上紅線後，同樣的問題模型會主動說「千萬不要假裝路過或用假的停售藉口」。

## 2026-08-17｜D011 示範話術一律不預設保險公司

**決策：** 所有系統產生的示範話術、建議開場、改善示範，公司一律寫「○○人壽」、
人名寫「○○」，自我介紹統一為「○○人壽的○○」。採兩層實作：

1. **提示詞層** — `NO_BRAND` 規則，注入痛點分析、Persona／示範話術、評分回饋、行銷諮詢四支提示詞。
2. **程式層** — `scrubBrands()` 保險絲，在回傳前掃掉漏網的公司名（規則優先，不依賴 LLM 自律）。

**為什麼：** 使用者可能任職於任何一家公司。示範話術若預設了某家公司，
會讓人誤以為那是該公司的標準話術，也不適合跨公司使用。

**不套用的範圍**（刻意）：
・**逐字稿與評分證據** — 那是使用者自己講的話，屬於原始紀錄，改寫會失真。
・**理賠諮詢與商品教材** — 使用者上傳的條款／教材本來就有真實商品與公司名，
　洗掉反而讓人搞不清楚在講哪一張保單。
・**客戶的台詞** — 客戶不會自稱保險公司。

**誤殺防範：** 「台灣」「中國」等字只有接在「人壽／產險／保險／金控」後面才視為公司名，
所以「台灣人的觀念」「中國信託的理專」不會被改掉，這兩個案例已寫進自我測試。

## 2026-08-17｜D012 示範話術必須受「接觸情境」的資訊邊界約束

**問題：** 使用者回報一句陌生開發的示範話術：
「林阿姨，您那筆五百萬的保單放了好幾年了，原來的業務員都沒跟您做過保單健檢嗎？」
第一通電話就講出對方的保額，實務上不但失禮，還會讓客戶覺得個資被調查。

**根因（架構問題，不只是話術不好）：** Persona 與 demo 是同一次生成的。
模型設計出客戶的 hidden_needs 與背景細節後，直接把「客戶心裡的事」
洩漏成「業務員已經知道的事」——這是資訊邊界沒有被明確定義。

**決策：**
1. 演練前新增「接觸情境」欄位，六種：陌生開發／客戶轉介紹／緣故／既有客戶服務／
   之前談過沒成交／活動後追蹤，另可補充自由說明。
2. 每一種情境在 `CONTEXTS` 明確定義「業務員此刻知道什麼」，
   personaPrompt 把這份清單當成設計 demo 的**唯一依據**。
3. 程式層 `demoLeaksPrivateInfo()` 掃描示範話術，若在陌生／轉介紹／緣故／活動後情境中
   出現保額、保單、繳費金額等字樣，**重新產生一次**（規格 §68 Output Validation）。
4. 角色扮演的客戶也知道這層關係——對方若講出他沒說過的私人資訊，
   客戶會直接反問「你怎麼會知道？」並變得防備。
5. 評分提示詞加入同一條檢查，越界提問會被列入 improvements。

**實測（陌生開發）：** 「王太太您好，我是○○人壽的○○……不知道您現在方便講話嗎？」
關鍵問題問的是生活安排，不是錢。
**實測（轉介紹）：** 開場第一句就交代介紹人「是王大哥特別拜託我打這通電話的」。

## 2026-08-17｜D013 話術設計導入 NLP 建立信任感原則

**決策：** 新增 `RAPPORT` 原則區塊，注入 Persona／示範話術、評分回饋、痛點分析、行銷諮詢四支提示詞。

七條原則：先跟後帶（Pacing & Leading）、語言同步（Matching）、尊重自主權（給對方退路）、
開場交代「我是誰／為什麼是現在／為什麼是你」、先處理情緒再處理事情、
第一次接觸只求一個小承諾、問句從生活出發而非從錢出發。

**倫理界線（依規格 §53）：** 明文禁止用 NLP 操控、製造恐懼、假裝熟識、
或暗示自己已掌握對方個資。技巧只能用於提升理解與尊重。

**效果：** 評分回饋開始自然引用這些原則，例如「在客戶表達忙碌時未能先承接情緒並給予退路」。

## 2026-08-17｜D014 改為每位使用者自帶 API 金鑰

**決策：** 進入主程式前新增登入畫面，使用者選擇 AI 服務商並輸入自己的金鑰。
伺服器不再持有任何金鑰，改為依每次請求所帶的憑證建立 adapter。

**為什麼：** 原本共用一把金鑰的模式有三個問題——
所有同事的用量都算在擁有者頭上、免費額度很快撞牆、網址外流等於額度外流。
使用者自帶金鑰後這三個問題同時消失，也不必再靠通行碼保護額度。

**支援的服務商：** Gemini、Anthropic 為原生實作；
OpenAI、Groq、OpenRouter、DeepSeek 走同一套 OpenAI 相容介面。
三條程式路徑涵蓋六家，`PROVIDERS` 新增一筆即可再擴充。

**模型選擇不寫死版本號**：登入時實際呼叫該服務商的 models API，
再用名稱特徵（flash / mini / haiku → fast；pro / sonnet / gpt → judge）挑選，
避免模型改版後整個 App 壞掉。

**金鑰安全措施：**
・只存在使用者瀏覽器的 localStorage，隨每次請求以 header 送出。
・伺服器只快取「已完成模型探測的 adapter 實例」，2 小時後回收；不寫入磁碟、不寫進日誌。
・`scrubKey()` 在回傳錯誤前洗掉可能夾帶的金鑰；已用測試確認回應與日誌都不含金鑰。
・登入時實際打一次該服務商的 API 驗證，問題在登入當下就浮現，不會等到演練到一半才爆。
・`friendlyError()` 把各家原始錯誤轉成使用者看得懂的中文。

**已知落差：** 只有 Gemini 有實際金鑰可測，其餘五家是照官方 API 規格實作但未實測。
登入驗證機制讓任何實作錯誤會在使用者第一次登入時就明確失敗，而不是靜默出錯。

**PDF 限制：** 只有 Gemini 與 Anthropic 能直接讀 PDF。
其餘服務商上傳 PDF 會得到明確的錯誤訊息與替代建議，而不是失敗得不明不白。

## 2026-08-17｜D015 移除伺服器，改為 GitHub Pages 純前端

**決策：** 拿掉 `server.js`，把整個 Coach Engine 搬進瀏覽器，
由瀏覽器直接呼叫 AI 服務商，網站放 GitHub Pages。

**為什麼：** Render 免費方案 15 分鐘沒人用就休眠，下一位使用者要等 30～60 秒。
對「讓業務員願意天天練」的產品來說，這個等待是致命傷。

**為什麼現在可以拿掉伺服器：** 原本伺服器存在的兩個理由都已消失——
1. 保護核心 IP（規格 §36）→ repo 已於 D011 後改為公開，提示詞本來就看得到。
2. 保護 API 金鑰 → D014 改為使用者自帶金鑰後，伺服器端沒有秘密可藏。

**實測前提：** 各家 API 的 CORS 支援（2026-08-17 實測）
Gemini ✅、OpenAI ✅、Groq ✅；Anthropic 需 `anthropic-dangerous-direct-browser-access` 標頭。

**技術移轉：**
・`docx.js` 的 `zlib.inflateRawSync` → `DecompressionStream('deflate-raw')`，
　Node 18+ 與瀏覽器都有，同一份程式碼兩邊都能跑（實測同一份 PPTX 結果完全一致，瀏覽器 17ms）。
・Node `Buffer` 的 readUInt32LE 等 → `DataView` + `TextDecoder`。
・文件儲存從伺服器檔案系統 → IndexedDB（`store.js`；Node 下自動退回記憶體版，
　讓 `tools/selftest.mjs` 仍可執行）。
・新增 `engine/api.js`，保留與伺服器版**完全相同的呼叫介面**，
　UI 層幾乎不需修改，日後若要切回伺服器架構也只換這一層。

**取捨：**
・失去：文件無法團隊共用，每個人要自己上傳教材。
・換得：無冷啟動、永久免費、更快（少一跳）、文件永久保留在自己裝置、
　對話不經過任何第三方伺服器、沒有伺服器要維護。

**注意事項：** `getDoc()` 因 IndexedDB 而變成非同步，所有呼叫端都必須加 `await`。
移轉時自我測試第 5 節就是因為漏掉一個 `await` 而失敗——拿到 Promise 當成文件用，
理賠查詢變成「條款查不到」。這類錯誤不會拋例外，只會安靜地給出錯誤答案，值得記一筆。

## 2026-08-17｜D016 模型可由使用者指定，但自動降階不關閉

**決策：** 新增「模型設定」畫面，使用者可分別指定角色扮演模型與評分模型。
指定後該模型排第一順位，**但降階鏈仍然保留**——額度用盡時照樣自動換下一個。

**為什麼不做成「指定就只用這個」：** 免費方案的額度隨時可能用盡（開發期間實測遇過多次）。
若指定後就不降階，使用者會在演練到一半直接失敗。
產品規格 §58「穩定性 > 功能數量」在這裡的具體應用：
選擇權給使用者，但不讓使用者選到一個會讓 App 壞掉的設定。

**UI 取捨：** 模型清單是即時查詢的（實測 Gemini 回傳 20 個），
API 原始順序把 `gemini-2.5-flash`、`gemma-4-26b` 排在前面，推薦的反而埋在後面。
對非工程背景的使用者，20 個原始代號隨機排列等於不能選。
因此 `status()` 額外回傳 `rank`，UI 依推薦順位排序並標 ★，且顯示服務商提供的友善名稱
（`gemini-3.7-flash` → 「Gemini 3.7 Flash」）。

**降階要讓使用者知道：** 新增 `onEvent` 回呼，額度用盡或改用備援模型時跳提示。
原本只寫 console.warn，使用者只會感覺「今天怎麼變慢／變差」卻不知道原因。

## 2026-08-17｜D017 加入 OpenRouter 一鍵登入；NVIDIA 與 ChatGPT OAuth 確認不可行

**實機驗證（瀏覽器直接呼叫）：**

| 端點 | 結果 |
|---|---|
| OpenRouter `/api/v1/*` | ✅ `access-control-allow-origin: *` |
| OpenRouter `/api/v1/auth/keys`（OAuth 換金鑰） | ✅ 允許 |
| OpenAI `auth.openai.com/oauth/token`（登入） | ✅ 允許 |
| **ChatGPT `chatgpt.com/backend-api/codex/*`（推論）** | ❌ 擋 CORS |
| **NVIDIA `integrate.api.nvidia.com/v1/*`** | ❌ 完全無 CORS 標頭，`Failed to fetch` |

**決策：**
1. **加入 OpenRouter OAuth PKCE**（`docs/engine/oauth.js`）。PKCE 用一次性亂數取代 client secret，
   全程瀏覽器完成，不需伺服器，符合 GitHub Pages 架構。
2. **放棄 NVIDIA。** 不是沒做，是瀏覽器根本呼叫不到。加一個必定失敗的選項只會讓使用者困惑。
3. **放棄 ChatGPT OAuth。** 登入那段可行，但拿到 token 後的推論端點擋 CORS，
   必須自架伺服器代轉每一次呼叫——那會失去無冷啟動與零維護，且條款疑慮未解。

**OpenRouter 的模型挑選問題：** 回傳 342 個模型（已濾掉 `:batch` 非同步介面）。
・自動挑選改為明確偏好中文表現好的：`google/gemini-*-flash` → `anthropic/claude-*-fast`（角色扮演）、
　`anthropic/claude-opus-*` → `google/gemini-*-pro`（評分）。
・`:free` 模型不列入自動挑選——實測 `dots-3-note-preview:free` 回簡體中文、
　`lfm-2.5-2.6b:free` 花 46 秒且中文破碎。但仍列在清單中並標「免費」，讓沒儲值的人能用。
・模型清單超過 30 個時加入搜尋框，未搜尋時只顯示前 30 個，否則數百列 DOM 會很慢。

**402 是新的錯誤類別。** 測試時 OpenRouter 餘額為 0，付費模型回 HTTP 402。
原本沒處理，使用者只會看到「剛剛好像卡了一下」。現在區分：
・402 餘額不足 → 明確告知去儲值或改選 `:free` 模型，**且不把使用者踢回登入畫面**（不是金鑰問題）
・429 額度用盡 → 自動降階並冷卻 10 分鐘
這兩者原因與解法完全不同，混在一起會給錯建議。

## 2026-08-17｜D019 模型選擇簡化為單一選項；免費模型標示 (Free)

**問題（使用者回報）：** 模型設定分成「角色扮演模型」與「評分與分析模型」兩區，太複雜。

**這是設計錯誤，不只是介面問題。** 分成兩區是把我的架構細節（規格 §47 的
Roleplay Model / Judge Model 分離）推給使用者承擔。使用者要練習業務技巧，
不需要理解「為什麼評分要用不一樣的模型」。

**決策：** 使用者只選一個模型，套用到全部功能。
但**自動模式仍保留智慧分配**——角色扮演挑最快的、評分挑最準的。
自動那一列會顯示「演練用 X，評分用 Y」，讓想知道的人看得到，但不必做選擇。

也就是：預設聰明，指定時單純。複雜度留在系統裡，不外露給使用者。

**免費模型標示：** 改為在模型名稱後直接加「(Free)」，比原本另一行寫「免費」明顯。
判定依據改用服務商回報的實際價格（`pricing.prompt === 0 && pricing.completion === 0`），
比只看名稱結尾 `:free` 可靠。實測 OpenRouter 342 個模型中偵測出 20 個免費。

**相容性：** 舊版存的是 `{fast, judge}` 物件，`loadPin()` 讀到物件時取 `fast` 值並就地改寫成字串，
使用者不會因為改版而掉設定。已實測遷移路徑。

## 2026-08-17｜D020 免費模型的三種失敗模式，以及錯誤訊息比對的脆弱性

**使用者回報三個現象，實測後發現前兩個是同一個原因，第三個是免費模型的本質限制。**

實測（2026-08-17，OpenRouter）：

| 模型 | 結果 |
|---|---|
| `openai/gpt-oss-20b:free` | 有時 `429 temporarily rate-limited upstream`，有時完全不回應 |
| `google/gemma-4-31b-it:free` | `429 temporarily rate-limited upstream` |
| `google/gemma-4-26b-a4b-it:free` | 成功，但 6.9 秒（不送 response_format 時 14.2 秒且中文夾雜俄語、印尼語、孟加拉語） |

**根因與修正：**

1. **「額度用盡」訊息誤導。** 免費模型是所有 OpenRouter 使用者共用一個上游流量池，
   被限流跟「你的帳戶額度用完」完全不同。原本兩者都回報「額度用盡」，難怪使用者覺得矛盾
   （明明標示 Free 卻說額度用盡）。現在分開：上游限流 → 「使用的人太多，等一兩分鐘」，冷卻 1 分鐘而非 10 分鐘。

2. **降階會掉到付費模型。** 指定免費模型被限流後，備援鏈掉到付費模型，再回報「餘額不足」——
   使用者明明選了免費的。現在指定免費模型時，備援也只走免費模型。
   另外遇到 402 會記住「這個帳戶沒餘額」，之後直接跳過付費模型。

3. **「卡住」是逾時設計缺陷。** `gpt-oss-20b:free` 有時完全不回應，
   而評分層逾時 120 秒 × 3 次重試 = 最糟 6 分鐘。改為：
   單次逾時（角色扮演 25 秒／評分 45 秒）＋ **整個 generate() 的總時限**，
   且逾時後不重試同一個模型（重試沒意義），直接換下一個。實測從無限卡住變成 30 秒內完成。

4. **免費模型備援要排序。** 免費模型品質落差極大（實測有一個要 46 秒且中文破碎），
   依實測結果排序，別掉到那種。

5. **非對話模型混進清單。** `google/lyria-3-*` 是音樂生成模型，卻出現在備援鏈裡。
   依名稱過濾看不出來（名稱毫無線索），改用 API 回報的 `output_modalities`——
   只保留「輸出僅有 text」的模型。注意 lyria 輸出是 `["text","audio"]`，
   所以條件必須是「只有 text」而不是「包含 text」。

6. **OpenRouter 假金鑰可以登入。** 它的 `/models` 是**公開端點**，假金鑰也拿得到清單，
   所以「登入時驗證金鑰」形同虛設。改為先打需要驗證的 `/api/v1/key`（實測假金鑰回 401）。

7. **response_format 要保留。** 直覺上拿掉 JSON 模式可以提高相容性，
   實測相反——gemma 不用 JSON 模式時輸出品質明顯變差。改為依 API 回報的
   `supported_parameters` 判斷該模型支不支援，支援就送。同時用 `top_provider.max_completion_tokens` 夾住上限。

**最重要的教訓：用訊息文字比對來分類錯誤非常脆弱。**
・`AbortSignal.timeout()` 拋出的訊息是「aborted due to timeout」，不含我判斷用的「timed out」，
　導致逾時錯誤沒被攔截而直接成為未捕捉例外。已改為在 `_fetch` 源頭把底層錯誤正規化成固定字樣。
・`friendlyError()` 原本認不出錯誤時回傳原文，上層再用白名單決定要不要顯示——
　結果新增的逾時訊息不在白名單裡，被換成通用的「剛剛好像卡了一下」。
　已改為認不出來就回 `null`，由呼叫端明確決定，不再靠關鍵字猜。

## 2026-08-17｜D021 預設難度降為「新手友善」；個性改由使用者指定

**問題（使用者回報）：** 「一開始 AI 的防備心有點過高，其實不適合新進夥伴練習，容易打擊信心。」

**根因（三個，都在程式裡）：**
1. **難度只有一行文字描述**（例如「1: 友善、願意聊、幾乎不拒絕」），
   對模型行為幾乎沒有約束力。
2. **`MODE_RULES.call` 寫死「你隨時可以說忙、可以想掛電話」，套用到所有難度**——
   這是連 Level 1 都很防備的主因。
3. **初始信任度由模型自己決定**，實測常給 15～25，開場就冷淡到沒辦法練習。
4. 預設難度是 2，不是 1。

**決策一：難度改成有力的控制，關鍵數值由程式把關**

| 控制項 | 由誰決定 | L1 | L5 |
|---|---|---|---|
| 態度與語氣、trust_delta 傾向 | 提示詞（完整規則段落） | 溫和、會幫使用者接話 | 不耐煩、連續拒絕 |
| 初始信任度 | **程式夾在區間內** | 62～80 | 12～30 |
| 能否主動結束對話 | **程式判定** | ❌ | ✅ |
| 引導次數上限 | **程式判定** | 5 | 3 |

・`MODE_RULES` 每個模式拆成 easy／hard 兩版，難度 ≤2 用 easy。
・卡住時的引導指示也分難易：**新手級是「幫他接話」，不是「表達不耐煩」**。
・預設難度改為 **1 新手友善**，UI 顯示「第一次練習建議從這裡開始」。

**實測對照**（同樣餵入結巴、沒重點的爛開場三次）：

```
L1：「嗯，您好啊。沒關係你慢慢說，請問今天打來是有什麼事嗎？」   信任 70 → 80，不掛電話
L4：「保險喔？我都說了不用了，你們怎麼一直打來啦！」             信任 25 → 15
```

**決策二：個性由使用者在「客戶背景」欄指定，優先於模型判斷**

提示詞明確宣告：背景欄若已描述個性、說話方式或態度，
那是使用者刻意指定的，必須完全照著演，不得改成模型自己想的個性。

並且明確區分兩者職責，避免模型混淆：
・**個性** ← 使用者（說話方式、話多話少）
・**難度** ← 選單（抗拒程度、信任度、願意透露多少）
・兩者可並存：「愛聊天」＋高難度 ＝ 話很多但一直閃避重點。

UI 同步調整：背景欄的說明與 placeholder 明確邀請填寫個性，
並列出六種常見型（愛聊天／個性急／客氣難拒絕／疑心病重／很冷淡／理性看數據）。
難度選項下方顯示該級會遇到什麼樣的客戶。

**實測**（背景只差最後一句）：

| 使用者寫的 | AI 演出 |
|---|---|
| 個性很愛聊天、話特別多 | 「哎喲我跟你說，我今天剛好在忙我們家那個剛滿四個月的小寶，他剛剛又溢奶了啦！」 |
| 個性非常冷淡，只回一兩個字 | 「嗯，請說。」→「聊什麼？」 |

**衍生的坑：** 使用者指定的個性與難度看似衝突時（「很冷淡」＋「新手友善」），
模型會把自己的推理寫進人設欄位：
「個性非常冷淡，**但因為難度設定為新手友善**，其實有耐心……」

提示詞加規則擋不住（只在衝突時出現）。依兩層防護原則加了程式層 `scrubMeta()`，
刪掉含後設用語的子句；整段都是後設時退回原文，不留空白人設。

**啟示：**
1. **預設值決定大多數人的第一印象。** 訓練工具打擊使用者信心，等於失去存在意義。
2. **「一行文字的設定」通常等於沒有設定。** 重要參數不要只用提示詞描述，
   關鍵數值要由程式夾住。
