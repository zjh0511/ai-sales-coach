# DECISION LOG

記錄會影響架構、且事後容易忘記「為什麼這樣選」的決策。

---

## 2026-08-16｜D001 網頁測試版的 LLM 先接 Gemini API，而非本機模型

**決策：** V0.1 走 Gemini API（`gemini-3.7-flash`），本機模型延後到原生 iOS 階段。

**為什麼：** 規格 §27 要求 Local-first，但 iPhone Safari 分頁記憶體上限約 1～1.5GB，
Gemma 3n E2B 量化後仍需 2～3GB，網頁版在 iPhone 上不可能跑本機模型。
若為了「local-first」而在網頁版硬塞小模型，只有桌機能測，反而測不到真正的目標裝置。

**影響：** 未違反 Model-Agnostic 原則——所有模型呼叫都經過 `lib/gateway.js`。
原生 App 階段新增 local adapter 即可，Coach Engine 不需修改。

## 2026-08-16｜D002 語音採用瀏覽器內建 Web Speech API

**決策：** STT/TTS 使用 iOS Safari 內建的 `webkitSpeechRecognition` 與 `speechSynthesis`。

**為什麼：** 零下載、零費用、延遲低、支援 zh-TW，且錄音不需經過我方伺服器，
符合規格 §81「不得預設把完整錄音上傳第三方」。

**代價：** iOS 無法在 TTS 播放時穩定同時收音，因此規格 §31 的 Barge-in
在 V1 降級為「點麥克風打斷」。此限制已記錄於 `app/README.md`。

## 2026-08-16｜D003 核心教練邏輯放伺服器端，前端只留 UI 與語音

**決策：** Prompt、Persona 隱藏狀態、評分邏輯、合規規則全部在 `app/lib/`，
瀏覽器只收到 Public State。

**為什麼：** 規格 §36、§37 要求核心 IP 不明文放在 Client。
副作用是前端變得很小，也符合「程式碼精簡」的要求。

**驗證：** `tools/selftest.mjs` 有一項專門斷言 Client 回應不含 `hidden_needs`。

## 2026-08-16｜D004 演練的結束時機由程式判定，不交給 LLM

**決策：** LLM 回傳的 `end` 訊號，只有在使用者已完成至少 4 個回合後才採信；
連續三次無效回應則強制結束（規格 §17）。

**為什麼：** 實測發現難度 3 的客戶在第 1 回合就回「不用再打來了」並把 `end` 設為 true，
演練還沒開始就結束。這是規格 §92「重要產品邏輯由程式控制」的實例。

## 2026-08-16｜D005 Model Gateway 需處理過載降級

**決策：** 同一模型重試 3 次（指數退避），仍失敗則自動降級到偏好清單的下一個模型。

**為什麼：** 開發當天實際遇到 `gemini-3.7-flash` 回 503 過載與 429 額度用盡。
若不處理，使用者會在演練到一半時看到錯誤而中斷。

**另註：** Gemini 3.x 的思考 token 會計入 `maxOutputTokens`，額度不足時回傳空字串。
額度必須放寬（Persona 4000／回合 1200／評分 8000），這是很容易誤判成「模型不穩」的坑。

## 2026-08-16｜D006 角色扮演改用 flash-lite 作為主要降級目標

**決策：** `PREFER_FAST` 順序調整為 3.7-flash → 3.6-flash → **3.5-flash-lite** → 3.1-flash-lite
→ …→ 3.5-flash（墊底）。

**為什麼：** 實測（同一段提示詞、同一時間）：

| 模型 | 延遲 |
|---|---|
| gemini-3.5-flash-lite | 1.1 秒 |
| gemini-3.1-flash-lite | 1.4 秒 |
| gemini-3.5-flash | 26.5 秒（免費方案被重度限流） |

原本把 3.5-flash 排在 lite 前面，導致降級後每回合要等 26～36 秒，語音對練完全不可用。
客戶回話只有 1～3 句，lite 的品質實測足夠，且 1.1 秒直接達成規格 §29 的 ≤2 秒目標。

**啟示：** 規格 §81「不要只看 Benchmark Leaderboard」在這裡完全應驗——
真正決定體驗的是「這把金鑰、這個方案、這個時段」的實際延遲，不是模型的紙面能力。

## 2026-08-16｜D007 文件解析不裝任何套件：Office 自解，PDF 交給模型

**決策：** `.docx`／`.pptx` 用自寫的 ZIP+XML 解析（`lib/docx.js`，60 行）；
`.pdf` 直接把原始位元組交給 Gemini 讀。不使用 `pdfjs-dist` 等套件。

**為什麼：**
・`.docx`／`.pptx` 本質就是 ZIP 裡的 XML，Node 內建 zlib 就能解，沒必要引入相依。
・PDF 相反——中文 PDF 大量使用 CID 字型與子集嵌入，自寫解析器常常取出亂碼；
　掃描版更是完全取不到字。模型原生讀 PDF 可以連圖表與掃描頁一起理解。

**驗證：** 用使用者自己的 `【AiCoach】AI業務教練.pptx` 實測，13 頁全部正確取字分頁。

## 2026-08-16｜D008 知識庫採「一次結構化，之後查摘要」

**決策：** 上傳時呼叫一次模型，把文件轉成結構化 JSON（商品：FABE 賣點／條款：給付項目窮舉）。
之後的演練與查詢只帶這份摘要，不重送整份文件。

**為什麼：** 對應規格 §41 的 Knowledge Structuring。若每次查詢都重送 100 頁條款，
在免費方案的 TPM 限制下很快就會撞牆，且延遲不可接受。

**例外：** 理賠查詢會回頭附上條款原文（PDF ≤6MB 時送原始檔）。
理賠答錯的代價比多花 token 高，準確度優先。回覆會標示是否有比對原文。

## 2026-08-16｜D009 隱藏需求的揭露改用「編號」而非「原字照抄」

**決策：** 角色扮演時，模型回傳 `revealed: [1,3]` 這種編號，由程式映射回實際文字。

**為什麼：** 原本要求模型把透露的隱藏需求「原字照抄」回 JSON，實測 4 個回合下來
一項都沒記錄到，即使客戶明顯已經鬆口。改成編號後，同樣的情境正確記錄到 2／3 項。

**啟示：** 小任務要遷就模型擅長的形式。要模型在演戲的同時精確複製長字串，
是不必要的認知負擔；讓它挑編號就準確得多。

## 2026-08-16｜D010 教練不得建議捏造聯繫理由

**決策：** 在 `COACH_CHAT` 加入紅線：不得建議假名額、假優惠、假停售、假核保結果、
假裝「剛好經過」。

**為什麼：** 實測時教練回覆建議業務員「給他一個好用的藉口」「最近剛好有一個核保優勢／名額」。
這雖然是業界常見話術，但屬於不實招攬，且與規格 §54「不應鼓勵欺騙」直接衝突。
加上紅線後，同樣的問題模型會主動說「千萬不要假裝路過或用假的停售藉口」。

## 2026-08-17｜D011 示範話術一律不預設保險公司

**決策：** 所有系統產生的示範話術、建議開場、改善示範，公司一律寫「○○人壽」、
人名寫「○○」，自我介紹統一為「○○人壽的○○」。採兩層實作：

1. **提示詞層** — `NO_BRAND` 規則，注入痛點分析、Persona／示範話術、評分回饋、行銷諮詢四支提示詞。
2. **程式層** — `scrubBrands()` 保險絲，在回傳前掃掉漏網的公司名（規則優先，不依賴 LLM 自律）。

**為什麼：** 使用者可能任職於任何一家公司。示範話術若預設了某家公司，
會讓人誤以為那是該公司的標準話術，也不適合跨公司使用。

**不套用的範圍**（刻意）：
・**逐字稿與評分證據** — 那是使用者自己講的話，屬於原始紀錄，改寫會失真。
・**理賠諮詢與商品教材** — 使用者上傳的條款／教材本來就有真實商品與公司名，
　洗掉反而讓人搞不清楚在講哪一張保單。
・**客戶的台詞** — 客戶不會自稱保險公司。

**誤殺防範：** 「台灣」「中國」等字只有接在「人壽／產險／保險／金控」後面才視為公司名，
所以「台灣人的觀念」「中國信託的理專」不會被改掉，這兩個案例已寫進自我測試。

## 2026-08-17｜D012 示範話術必須受「接觸情境」的資訊邊界約束

**問題：** 使用者回報一句陌生開發的示範話術：
「林阿姨，您那筆五百萬的保單放了好幾年了，原來的業務員都沒跟您做過保單健檢嗎？」
第一通電話就講出對方的保額，實務上不但失禮，還會讓客戶覺得個資被調查。

**根因（架構問題，不只是話術不好）：** Persona 與 demo 是同一次生成的。
模型設計出客戶的 hidden_needs 與背景細節後，直接把「客戶心裡的事」
洩漏成「業務員已經知道的事」——這是資訊邊界沒有被明確定義。

**決策：**
1. 演練前新增「接觸情境」欄位，六種：陌生開發／客戶轉介紹／緣故／既有客戶服務／
   之前談過沒成交／活動後追蹤，另可補充自由說明。
2. 每一種情境在 `CONTEXTS` 明確定義「業務員此刻知道什麼」，
   personaPrompt 把這份清單當成設計 demo 的**唯一依據**。
3. 程式層 `demoLeaksPrivateInfo()` 掃描示範話術，若在陌生／轉介紹／緣故／活動後情境中
   出現保額、保單、繳費金額等字樣，**重新產生一次**（規格 §68 Output Validation）。
4. 角色扮演的客戶也知道這層關係——對方若講出他沒說過的私人資訊，
   客戶會直接反問「你怎麼會知道？」並變得防備。
5. 評分提示詞加入同一條檢查，越界提問會被列入 improvements。

**實測（陌生開發）：** 「王太太您好，我是○○人壽的○○……不知道您現在方便講話嗎？」
關鍵問題問的是生活安排，不是錢。
**實測（轉介紹）：** 開場第一句就交代介紹人「是王大哥特別拜託我打這通電話的」。

## 2026-08-17｜D013 話術設計導入 NLP 建立信任感原則

**決策：** 新增 `RAPPORT` 原則區塊，注入 Persona／示範話術、評分回饋、痛點分析、行銷諮詢四支提示詞。

七條原則：先跟後帶（Pacing & Leading）、語言同步（Matching）、尊重自主權（給對方退路）、
開場交代「我是誰／為什麼是現在／為什麼是你」、先處理情緒再處理事情、
第一次接觸只求一個小承諾、問句從生活出發而非從錢出發。

**倫理界線（依規格 §53）：** 明文禁止用 NLP 操控、製造恐懼、假裝熟識、
或暗示自己已掌握對方個資。技巧只能用於提升理解與尊重。

**效果：** 評分回饋開始自然引用這些原則，例如「在客戶表達忙碌時未能先承接情緒並給予退路」。

## 2026-08-17｜D014 改為每位使用者自帶 API 金鑰

**決策：** 進入主程式前新增登入畫面，使用者選擇 AI 服務商並輸入自己的金鑰。
伺服器不再持有任何金鑰，改為依每次請求所帶的憑證建立 adapter。

**為什麼：** 原本共用一把金鑰的模式有三個問題——
所有同事的用量都算在擁有者頭上、免費額度很快撞牆、網址外流等於額度外流。
使用者自帶金鑰後這三個問題同時消失，也不必再靠通行碼保護額度。

**支援的服務商：** Gemini、Anthropic 為原生實作；
OpenAI、Groq、OpenRouter、DeepSeek 走同一套 OpenAI 相容介面。
三條程式路徑涵蓋六家，`PROVIDERS` 新增一筆即可再擴充。

**模型選擇不寫死版本號**：登入時實際呼叫該服務商的 models API，
再用名稱特徵（flash / mini / haiku → fast；pro / sonnet / gpt → judge）挑選，
避免模型改版後整個 App 壞掉。

**金鑰安全措施：**
・只存在使用者瀏覽器的 localStorage，隨每次請求以 header 送出。
・伺服器只快取「已完成模型探測的 adapter 實例」，2 小時後回收；不寫入磁碟、不寫進日誌。
・`scrubKey()` 在回傳錯誤前洗掉可能夾帶的金鑰；已用測試確認回應與日誌都不含金鑰。
・登入時實際打一次該服務商的 API 驗證，問題在登入當下就浮現，不會等到演練到一半才爆。
・`friendlyError()` 把各家原始錯誤轉成使用者看得懂的中文。

**已知落差：** 只有 Gemini 有實際金鑰可測，其餘五家是照官方 API 規格實作但未實測。
登入驗證機制讓任何實作錯誤會在使用者第一次登入時就明確失敗，而不是靜默出錯。

**PDF 限制：** 只有 Gemini 與 Anthropic 能直接讀 PDF。
其餘服務商上傳 PDF 會得到明確的錯誤訊息與替代建議，而不是失敗得不明不白。

## 2026-08-17｜D015 移除伺服器，改為 GitHub Pages 純前端

**決策：** 拿掉 `server.js`，把整個 Coach Engine 搬進瀏覽器，
由瀏覽器直接呼叫 AI 服務商，網站放 GitHub Pages。

**為什麼：** Render 免費方案 15 分鐘沒人用就休眠，下一位使用者要等 30～60 秒。
對「讓業務員願意天天練」的產品來說，這個等待是致命傷。

**為什麼現在可以拿掉伺服器：** 原本伺服器存在的兩個理由都已消失——
1. 保護核心 IP（規格 §36）→ repo 已於 D011 後改為公開，提示詞本來就看得到。
2. 保護 API 金鑰 → D014 改為使用者自帶金鑰後，伺服器端沒有秘密可藏。

**實測前提：** 各家 API 的 CORS 支援（2026-08-17 實測）
Gemini ✅、OpenAI ✅、Groq ✅；Anthropic 需 `anthropic-dangerous-direct-browser-access` 標頭。

**技術移轉：**
・`docx.js` 的 `zlib.inflateRawSync` → `DecompressionStream('deflate-raw')`，
　Node 18+ 與瀏覽器都有，同一份程式碼兩邊都能跑（實測同一份 PPTX 結果完全一致，瀏覽器 17ms）。
・Node `Buffer` 的 readUInt32LE 等 → `DataView` + `TextDecoder`。
・文件儲存從伺服器檔案系統 → IndexedDB（`store.js`；Node 下自動退回記憶體版，
　讓 `tools/selftest.mjs` 仍可執行）。
・新增 `engine/api.js`，保留與伺服器版**完全相同的呼叫介面**，
　UI 層幾乎不需修改，日後若要切回伺服器架構也只換這一層。

**取捨：**
・失去：文件無法團隊共用，每個人要自己上傳教材。
・換得：無冷啟動、永久免費、更快（少一跳）、文件永久保留在自己裝置、
　對話不經過任何第三方伺服器、沒有伺服器要維護。

**注意事項：** `getDoc()` 因 IndexedDB 而變成非同步，所有呼叫端都必須加 `await`。
移轉時自我測試第 5 節就是因為漏掉一個 `await` 而失敗——拿到 Promise 當成文件用，
理賠查詢變成「條款查不到」。這類錯誤不會拋例外，只會安靜地給出錯誤答案，值得記一筆。

## 2026-08-17｜D016 模型可由使用者指定，但自動降階不關閉

**決策：** 新增「模型設定」畫面，使用者可分別指定角色扮演模型與評分模型。
指定後該模型排第一順位，**但降階鏈仍然保留**——額度用盡時照樣自動換下一個。

**為什麼不做成「指定就只用這個」：** 免費方案的額度隨時可能用盡（開發期間實測遇過多次）。
若指定後就不降階，使用者會在演練到一半直接失敗。
產品規格 §58「穩定性 > 功能數量」在這裡的具體應用：
選擇權給使用者，但不讓使用者選到一個會讓 App 壞掉的設定。

**UI 取捨：** 模型清單是即時查詢的（實測 Gemini 回傳 20 個），
API 原始順序把 `gemini-2.5-flash`、`gemma-4-26b` 排在前面，推薦的反而埋在後面。
對非工程背景的使用者，20 個原始代號隨機排列等於不能選。
因此 `status()` 額外回傳 `rank`，UI 依推薦順位排序並標 ★，且顯示服務商提供的友善名稱
（`gemini-3.7-flash` → 「Gemini 3.7 Flash」）。

**降階要讓使用者知道：** 新增 `onEvent` 回呼，額度用盡或改用備援模型時跳提示。
原本只寫 console.warn，使用者只會感覺「今天怎麼變慢／變差」卻不知道原因。

## 2026-08-17｜D017 加入 OpenRouter 一鍵登入；NVIDIA 與 ChatGPT OAuth 確認不可行

**實機驗證（瀏覽器直接呼叫）：**

| 端點 | 結果 |
|---|---|
| OpenRouter `/api/v1/*` | ✅ `access-control-allow-origin: *` |
| OpenRouter `/api/v1/auth/keys`（OAuth 換金鑰） | ✅ 允許 |
| OpenAI `auth.openai.com/oauth/token`（登入） | ✅ 允許 |
| **ChatGPT `chatgpt.com/backend-api/codex/*`（推論）** | ❌ 擋 CORS |
| **NVIDIA `integrate.api.nvidia.com/v1/*`** | ❌ 完全無 CORS 標頭，`Failed to fetch` |

**決策：**
1. **加入 OpenRouter OAuth PKCE**（`docs/engine/oauth.js`）。PKCE 用一次性亂數取代 client secret，
   全程瀏覽器完成，不需伺服器，符合 GitHub Pages 架構。
2. **放棄 NVIDIA。** 不是沒做，是瀏覽器根本呼叫不到。加一個必定失敗的選項只會讓使用者困惑。
3. **放棄 ChatGPT OAuth。** 登入那段可行，但拿到 token 後的推論端點擋 CORS，
   必須自架伺服器代轉每一次呼叫——那會失去無冷啟動與零維護，且條款疑慮未解。

**OpenRouter 的模型挑選問題：** 回傳 342 個模型（已濾掉 `:batch` 非同步介面）。
・自動挑選改為明確偏好中文表現好的：`google/gemini-*-flash` → `anthropic/claude-*-fast`（角色扮演）、
　`anthropic/claude-opus-*` → `google/gemini-*-pro`（評分）。
・`:free` 模型不列入自動挑選——實測 `dots-3-note-preview:free` 回簡體中文、
　`lfm-2.5-2.6b:free` 花 46 秒且中文破碎。但仍列在清單中並標「免費」，讓沒儲值的人能用。
・模型清單超過 30 個時加入搜尋框，未搜尋時只顯示前 30 個，否則數百列 DOM 會很慢。

**402 是新的錯誤類別。** 測試時 OpenRouter 餘額為 0，付費模型回 HTTP 402。
原本沒處理，使用者只會看到「剛剛好像卡了一下」。現在區分：
・402 餘額不足 → 明確告知去儲值或改選 `:free` 模型，**且不把使用者踢回登入畫面**（不是金鑰問題）
・429 額度用盡 → 自動降階並冷卻 10 分鐘
這兩者原因與解法完全不同，混在一起會給錯建議。

## 2026-08-17｜D020 免費模型的三種失敗模式，以及錯誤訊息比對的脆弱性

**使用者回報三個現象，實測後發現前兩個是同一個原因，第三個是免費模型的本質限制。**

實測（2026-08-17，OpenRouter）：

| 模型 | 結果 |
|---|---|
| `openai/gpt-oss-20b:free` | 有時 `429 temporarily rate-limited upstream`，有時完全不回應 |
| `google/gemma-4-31b-it:free` | `429 temporarily rate-limited upstream` |
| `google/gemma-4-26b-a4b-it:free` | 成功，但 6.9 秒（不送 response_format 時 14.2 秒且中文夾雜俄語、印尼語、孟加拉語） |

**根因與修正：**

1. **「額度用盡」訊息誤導。** 免費模型是所有 OpenRouter 使用者共用一個上游流量池，
   被限流跟「你的帳戶額度用完」完全不同。原本兩者都回報「額度用盡」，難怪使用者覺得矛盾
   （明明標示 Free 卻說額度用盡）。現在分開：上游限流 → 「使用的人太多，等一兩分鐘」，冷卻 1 分鐘而非 10 分鐘。

2. **降階會掉到付費模型。** 指定免費模型被限流後，備援鏈掉到付費模型，再回報「餘額不足」——
   使用者明明選了免費的。現在指定免費模型時，備援也只走免費模型。
   另外遇到 402 會記住「這個帳戶沒餘額」，之後直接跳過付費模型。

3. **「卡住」是逾時設計缺陷。** `gpt-oss-20b:free` 有時完全不回應，
   而評分層逾時 120 秒 × 3 次重試 = 最糟 6 分鐘。改為：
   單次逾時（角色扮演 25 秒／評分 45 秒）＋ **整個 generate() 的總時限**，
   且逾時後不重試同一個模型（重試沒意義），直接換下一個。實測從無限卡住變成 30 秒內完成。

4. **免費模型備援要排序。** 免費模型品質落差極大（實測有一個要 46 秒且中文破碎），
   依實測結果排序，別掉到那種。

5. **非對話模型混進清單。** `google/lyria-3-*` 是音樂生成模型，卻出現在備援鏈裡。
   依名稱過濾看不出來（名稱毫無線索），改用 API 回報的 `output_modalities`——
   只保留「輸出僅有 text」的模型。注意 lyria 輸出是 `["text","audio"]`，
   所以條件必須是「只有 text」而不是「包含 text」。

6. **OpenRouter 假金鑰可以登入。** 它的 `/models` 是**公開端點**，假金鑰也拿得到清單，
   所以「登入時驗證金鑰」形同虛設。改為先打需要驗證的 `/api/v1/key`（實測假金鑰回 401）。

7. **response_format 要保留。** 直覺上拿掉 JSON 模式可以提高相容性，
   實測相反——gemma 不用 JSON 模式時輸出品質明顯變差。改為依 API 回報的
   `supported_parameters` 判斷該模型支不支援，支援就送。同時用 `top_provider.max_completion_tokens` 夾住上限。

**最重要的教訓：用訊息文字比對來分類錯誤非常脆弱。**
・`AbortSignal.timeout()` 拋出的訊息是「aborted due to timeout」，不含我判斷用的「timed out」，
　導致逾時錯誤沒被攔截而直接成為未捕捉例外。已改為在 `_fetch` 源頭把底層錯誤正規化成固定字樣。
・`friendlyError()` 原本認不出錯誤時回傳原文，上層再用白名單決定要不要顯示——
　結果新增的逾時訊息不在白名單裡，被換成通用的「剛剛好像卡了一下」。
　已改為認不出來就回 `null`，由呼叫端明確決定，不再靠關鍵字猜。

## 2026-08-17｜D021 預設難度降為「新手友善」；個性改由使用者指定

**問題（使用者回報）：** 「一開始 AI 的防備心有點過高，其實不適合新進夥伴練習，容易打擊信心。」

**根因（三個，都在程式裡）：**
1. **難度只有一行文字描述**（例如「1: 友善、願意聊、幾乎不拒絕」），
   對模型行為幾乎沒有約束力。
2. **`MODE_RULES.call` 寫死「你隨時可以說忙、可以想掛電話」，套用到所有難度**——
   這是連 Level 1 都很防備的主因。
3. **初始信任度由模型自己決定**，實測常給 15～25，開場就冷淡到沒辦法練習。
4. 預設難度是 2，不是 1。

**決策一：難度改成有力的控制，關鍵數值由程式把關**

| 控制項 | 由誰決定 | L1 | L5 |
|---|---|---|---|
| 態度與語氣、trust_delta 傾向 | 提示詞（完整規則段落） | 溫和、會幫使用者接話 | 不耐煩、連續拒絕 |
| 初始信任度 | **程式夾在區間內** | 62～80 | 12～30 |
| 能否主動結束對話 | **程式判定** | ❌ | ✅ |
| 引導次數上限 | **程式判定** | 5 | 3 |

・`MODE_RULES` 每個模式拆成 easy／hard 兩版，難度 ≤2 用 easy。
・卡住時的引導指示也分難易：**新手級是「幫他接話」，不是「表達不耐煩」**。
・預設難度改為 **1 新手友善**，UI 顯示「第一次練習建議從這裡開始」。

**實測對照**（同樣餵入結巴、沒重點的爛開場三次）：

```
L1：「嗯，您好啊。沒關係你慢慢說，請問今天打來是有什麼事嗎？」   信任 70 → 80，不掛電話
L4：「保險喔？我都說了不用了，你們怎麼一直打來啦！」             信任 25 → 15
```

**決策二：個性由使用者在「客戶背景」欄指定，優先於模型判斷**

提示詞明確宣告：背景欄若已描述個性、說話方式或態度，
那是使用者刻意指定的，必須完全照著演，不得改成模型自己想的個性。

並且明確區分兩者職責，避免模型混淆：
・**個性** ← 使用者（說話方式、話多話少）
・**難度** ← 選單（抗拒程度、信任度、願意透露多少）
・兩者可並存：「愛聊天」＋高難度 ＝ 話很多但一直閃避重點。

UI 同步調整：背景欄的說明與 placeholder 明確邀請填寫個性，
並列出六種常見型（愛聊天／個性急／客氣難拒絕／疑心病重／很冷淡／理性看數據）。
難度選項下方顯示該級會遇到什麼樣的客戶。

**實測**（背景只差最後一句）：

| 使用者寫的 | AI 演出 |
|---|---|
| 個性很愛聊天、話特別多 | 「哎喲我跟你說，我今天剛好在忙我們家那個剛滿四個月的小寶，他剛剛又溢奶了啦！」 |
| 個性非常冷淡，只回一兩個字 | 「嗯，請說。」→「聊什麼？」 |

**衍生的坑：** 使用者指定的個性與難度看似衝突時（「很冷淡」＋「新手友善」），
模型會把自己的推理寫進人設欄位：
「個性非常冷淡，**但因為難度設定為新手友善**，其實有耐心……」

提示詞加規則擋不住（只在衝突時出現）。依兩層防護原則加了程式層 `scrubMeta()`，
刪掉含後設用語的子句；整段都是後設時退回原文，不留空白人設。

**啟示：**
1. **預設值決定大多數人的第一印象。** 訓練工具打擊使用者信心，等於失去存在意義。
2. **「一行文字的設定」通常等於沒有設定。** 重要參數不要只用提示詞描述，
   關鍵數值要由程式夾住。

## 2026-08-21｜D022 演練可續命；語音優先挑加強版；串流量過後不做

**背景：** 使用者另建了離線版（`ai-sales-coach-local`），實測後覺得
本地模型的對練體驗與 Gemini 差距明顯，決定回頭優化線上版的整體體驗。
離線版有三個發現值得帶回來。

### 一、串流：量過之後決定不做

離線版做了 `voice-stream.js`（一邊生成一邊開口），在 iPad 上省下 1,091 ms，
效益明確。回頭量線上版：

| 模型 | 首片段 | 完成 | 可搶到 |
|---|---|---|---|
| 離線 Qwen3-4B | 2,434 ms | 3,525 ms | 1,091 ms |
| gemini-3.5-flash-lite | 602 ms | 805 ms | 203 ms |
| gemini-3.7-flash | 1,004 ms | 1,123 ms | 119 ms |

**不做。** 兩個原因：雲端本來就快，串流只能搶 100～300 ms；
而且 **JSON 模式幾乎不串流**——Gemini 為了保證 JSON 合法會先緩衝，
`gemini-3.7-flash` 整個回應只切成 2 個片段、首 byte 到完成差 **2 ms**。

還有架構代價：串流等於在 `validateRoleplay()` 驗證完成前就把話唸出去，
攔到跳出角色時已經唸了。用 100～300 ms 換這個風險不值得。

**留下來的是判斷方法**：先量「首片段 vs 完成」的差距，差距小就不要做串流。

### 二、語音品質：優先挑加強版語音

離線版發現 iOS 給網頁用的預設中文語音是**壓縮版**，聽起來明顯是機器聲；
使用者在「設定 → 輔助使用 → 旁白 → 語音 → 中文」下載加強版之後，
那個語音才會出現在 `getVoices()` 裡，音質差距很大。

`pickVoice()` 改為優先挑名稱含 `enhanced|premium|加強|優化|siri` 的語音。
若只有壓縮版，第一次演練時提示一次下載路徑——**這件事使用者不會自己知道**。

### 三、演練續命（這是這次最有價值的修正）

原本 session 只存在記憶體 Map。手機切到別的 App、Safari 為了省記憶體回收分頁、
或不小心重新整理，練到一半的演練就整個消失，只會看到「連線已逾時，請重新開始」。

改為每個回合同步寫進 `sessionStorage`，首頁出現「接回上次中斷的演練」，
顯示客戶名、難度與已進行回合數，點下去逐字稿完整還原並可繼續。

**修的時候踩到自己的洞：** 加完之後測試發現重新整理仍然救不回來——
因為 `window.addEventListener('pagehide', abort)` 會呼叫 `abort()`，
而 `abort` 現在連儲存體一起清掉。**我自己把 session 刪了，剛好抵銷新功能。**
那個監聽原本是為了清理伺服器端 session，改成純前端後就不該再刪。
現在 `pagehide` 只釋放麥克風與語音，不結束演練。

**啟示：** 加「續命」功能時，要先找出所有會「主動清除」的路徑。
清除邏輯常常是為了上一代架構寫的，留著就會靜靜地抵銷新功能。

### 四、開始量真正的延遲

過去只量 LLM 生成時間。但語音對練裡使用者感知的是
**「我說完 → 客戶開口」**（規格 §44 的 T5−T1），這段包含
STT 收尾等待、LLM、TTS 啟動，我們從來沒量過。

`voice.js` 現在在 STT final 時記時間、在第一句 utterance 的 `onstart` 時停錶，
演練結束後在回饋頁顯示平均／最快／最慢。

**這一項只能在實機用語音量**：打字輸入不計（「說完」沒有意義），
瀏覽器窗格也放不出聲音。開發環境量不到，必須由使用者在 iPhone 上回報。

## 2026-08-21｜D023 做成 PWA；Service Worker 採 network-first

使用者要求「點網址後可以放到桌面成為快速入口」。

**做了什麼**

`docs/sw.js` ＋ `manifest.webmanifest` ＋ 四個 PNG 圖示（192 / 512 / 512 maskable /
apple-touch-icon，全部從 `icon.svg` 用瀏覽器 canvas 轉出）。裝好之後從桌面開啟
是全螢幕、無網址列；長按圖示有三個捷徑直達電話邀約／發掘需求／痛點分析
（`?go=call|needs|pain`，`handleShortcut()` 讀完就把參數從網址清掉）。

**關鍵取捨：快取策略選 network-first，不是 cache-first**

PWA 教學幾乎都教 cache-first（快）。這裡刻意反著做：

| | cache-first | network-first（採用） |
|---|---|---|
| 開啟速度 | 快 | 慢一點（多一次網路往返） |
| 改版後 | 使用者可能卡在舊版很久 | 一定拿到最新 |
| 出錯時 | 需要使用者自己清快取才能救 | 下次開啟自動修正 |

整包 App 不到 400KB，走網路本來就不慢；而「舊快取」這個坑我們已經吃過一次
（開發時伺服器送舊檔，花了時間才發現）。**同事拿去用的 App，我不能接受
「請你清除瀏覽器快取」是唯一的修復方式。** 快取的用途只剩一個：離線時介面
打得開。演練本身一定要網路，因為要呼叫 AI API。

另外兩個防呆：

- `install` 事件逐項 `c.add(...).catch(() => {})`。用 `addAll` 的話任何一個檔案
  404 就整個 SW 裝不起來——最脆弱的環節不該有連坐責任。
- `fetch` 事件先擋掉非 GET 與跨網域。**AI API 呼叫必須直接出去，不能經過 SW。**
  已在正式站實測：從頁面呼叫 Gemini 端點回 HTTP 400（Google 的錯誤），
  代表請求真的送出去了，SW 沒有攔。

**未驗證的部分（誠實記錄）**

SW 註冊在內嵌瀏覽器窗格被政策擋掉（`localhost` 抓得到檔案卻註冊失敗，
錯誤是 `An unknown error occurred when fetching the script`）。
換到正式站 HTTPS 才註冊成功，21 個檔案預快取完成、`./index.html` 離線後備在位。
**真正的離線開啟與 iOS「加入主畫面」仍須實機確認。**

順帶修的：SW 註冊條件原本寫 `location.protocol === 'https:'`，
但 `http://localhost` 也是安全來源、SW 在那裡同樣能註冊，這樣寫等於
自己封掉本機測試的路。改用 `window.isSecureContext`。

**安裝提示卡的平台差異**

## 2026-08-21｜D025 加入帳號與雲端同步；同步範圍刻意收窄

使用者要求「在原本頁面前加一個註冊／登入頁，支援 Google、Apple、E-mail」。

**先講清楚純前端做不到什麼**

沒有後端的情況下，登入畫面**守不住任何東西**——程式碼全在使用者的瀏覽器裡，
打開開發者工具就能跳過。所以登入不是「門禁」，只能是「身分」。
E-mail 註冊更是根本做不到：帳號密碼要有地方存、要能寄驗證信、要能重設密碼。

所以先問使用者這個登入到底要達成什麼，答案是「Google 一鍵登入」＋「真正的帳號與跨裝置同步」。
既然要真的同步，就必須接後端服務——**選 Firebase**，因為 Google 登入原生支援、
E-mail 註冊內建、免費額度對一個團隊綽綽有餘，而且這個專案本來就在用 Google 的 AI API。

**同步範圍：使用者自己劃的線**

問了要同步哪些東西，使用者選了「訓練紀錄」與「偏好設定」，
**沒有選 API 金鑰，也沒有選上傳的教材與條款**。這個決定比我預設的更好：

- 金鑰不上雲端 → README 的「金鑰只存在你的裝置」這句話還能成立
- 公司教材與客戶保單條款不上雲端 → 不會踩到公司規範
- 代價很小：每台新裝置第一次還是要貼一次金鑰，之後就記住了

這條線寫在程式碼裡（`bundle()` 只讀 history 與 prefs），不是設定選項。

**技術選擇**

| 決定 | 理由 |
|---|---|
| 不用 Firebase SDK，全走 REST | 維持零 `node_modules`。Auth 與 Realtime Database 的 REST 都很單純 |
| Realtime Database 而不是 Firestore | REST 進出都是純 JSON。Firestore 的 REST 要包 `stringValue`／`arrayValue` 型別外殼，同樣功能程式碼會多一倍，而我們要存的本來就是一包 JSON |
| Google 登入用官方 GIS 元件 | 自己刻 OAuth 做得到（`oauth.js` 已有 PKCE），但 Google 對純前端取 `id_token` 的規定變動頻繁。這是刻意付出的一個外部相依，而且「按下去才載入」 |
| 未設定就整段關閉 | `firebase-config.js` 留空 → 登入畫面不出現，App 行為與加這個功能之前完全相同。**沒設定好就跳出一個壞掉的登入頁，比沒有登入頁更糟** |
| 登入畫面留「不登入直接使用」的出口 | 登入既然守不住東西，做成強制關卡只會在自己壞掉時把所有人鎖在外面 |

**合併規則：唯一會弄丟使用者資料的地方**

同步最危險的不是失敗，而是**安靜地弄丟幾筆紀錄**——使用者通常不會察覺。

- 訓練紀錄用 `at`（時間戳）當識別碼取**聯集**。用覆蓋的話，
  在手機練完、電腦一開就會把手機那幾筆整批蓋掉。
- 偏好設定比 `updatedAt`，晚的贏。同一個人不會真的同時在兩台裝置改設定。
- **模型指定只在「服務商相同」時才套用**——別家的模型名稱放進來是無效的，
  會讓使用者在新裝置上看到一個根本不存在的模型。

`merge()` 是純函式，所以進了 selftest：11 項斷言涵蓋聯集、排序、去重、
雲端為空、本機為空、兩邊都空、壞資料（沒有 `at`）、100 筆上限。
規則層回歸從 22 項升到 33 項。

**順手補上的：偏好設定本機化**

要同步「難度與情境」，前提是本機得先記住它。原本每次進演練都要重選，
新進夥伴常常忘了調回「新手友善」。現在 `aicoach.prefs` 會記住上次的選擇。
**這是「為了同步而做的準備」意外變成了真正的體驗改善。**

**未完成與已知限制（誠實記錄）**

1. **Firebase 專案只有使用者能建立**（要用他的 Google 帳號進 Console）。
   我寫了 `account-setup.html`：七個步驟＋六個常見問題，
   包含「不要用測試模式的安全規則」的明確警告——測試模式等於把
   所有同事的訓練紀錄公開在網路上。
2. **Google 與 E-mail 登入的成功路徑我無法實測**（沒有專案）。
   已驗證的是：未設定時 App 行為完全不變、設定後會顯示登入頁、
   錯誤訊息會翻成中文、「先不要登入」出口可用、`merge()` 全數通過。
3. **Apple 登入需要付費的 Apple Developer 帳號**（約 NT$3,300／年）才能申請
   Services ID，這是 Apple 的規定。程式碼已寫好但預設關閉，
   註解中特別標明 nonce 的處理需要在啟用時驗證——Apple 與 Firebase 的文件
   在這一點上寫法不一致。
4. **在新裝置上，雲端的模型指定會被丟掉一次**：同步發生在使用者選定服務商之前，
   `provider` 不相符就不套用。下次開啟就正確了。這個洞不值得為它增加複雜度。
5. **README 的「不收集任何資料」已改寫。** 一旦開啟同步，訓練紀錄就會經過
   Google 的伺服器，資料庫擁有者在後台看得到——這一點必須事先告知同事。

## 2026-08-21｜D026 network-first 沒有繞過瀏覽器的 HTTP 快取（D023 的漏洞）

**症狀**

`firebase-config.js` 加上 `googleClientId` 之後 push、Pages 部署完成、
用 `curl` 抓正式站確認是新內容——但頁面上的 Google 登入按鈕就是不出現。
在頁面裡 `fetch('firebase-config.js', {cache:'no-store'})` 抓到的是新的，
而 `import('./firebase-config.js')` 拿到的模組卻還是舊的空值。

**原因**

GitHub Pages 送 `Cache-Control: max-age=600`。SW 的 `fetch(req)`
**會經過瀏覽器的 HTTP 快取**。所以 D023 的 network-first 只繞過了
「SW 自己的 Cache Storage」，沒繞過 HTTP 快取——使用者最久可能吃到
十分鐘前的舊模組。

**「network-first」這個名字讓我以為問題已經解決了。**
D023 寫下「改版後一定拿到最新」的時候，我沒有去確認這條路上還有第二層快取。

**修法**

```js
const fresh = await fetch(req.url, { cache: 'no-cache' });
```

`no-cache` 發出帶 `If-None-Match` 的條件請求：檔案沒改就回 304（幾十位元組），
改了就一定拿到新的。代價是每個外殼檔案多一次條件往返，用這個換
「絕不吃到舊版」——與 D023 原本的取捨方向一致，只是這次真的做到了。

不用 `no-store`：那會完全跳過快取，連 304 的便宜都拿不到。

**啟示（這是這次最值得記的一條）**

**快取是分層的，只解決你看得到的那一層等於沒解決。**
瀏覽器的資源請求至少要穿過：Service Worker Cache Storage → HTTP 快取 →
CDN → 來源伺服器。我當時只想到第一層。

而且這個 bug 的表現形式極具欺騙性：**「重新部署」與「重新整理」都無效，
但用 `fetch` 手動抓又是新的**——因為 `fetch` 的預設快取模式與
ES 模組載入器的行為不同。下次遇到「明明部署了卻沒生效」，
先問「這條路上有幾層快取」，不要只看最外面那一層。

## 2026-08-21｜D027 Firebase 設定由 CLI 完成；剩下的一步誠實交回使用者

使用者設定 Firebase「弄一半不會弄了」，要求我直接幫他完成。

我不代輸入 Google 帳號密碼，也不代接受 Google Cloud 的服務條款。
可行的做法是：裝 `firebase-tools`，**由使用者自己執行 `firebase login`**

**探測比詢問可靠**

`/gsi/status` 這個探測是關鍵：**GIS 按鈕在來源未授權時仍然「畫得出來」，
只有按下去才失敗。**如果只看畫面就宣告完成，會交出一顆壞按鈕。

**做不到的部分不假裝**

修改 OAuth 用戶端的「已授權 JavaScript 來源」沒有公開 API，
只能在網頁上點。於是：

- **不先填 `googleClientId`**。填了會出現一顆按下去就壞的按鈕，比沒有按鈕更糟。
- 給使用者該憑證編輯頁的**直達連結**、要填的**那一行**、以及一段可貼進

`tools/fbcheck.mjs`：註冊 → 寫入 → 讀回 → 跨裝置合併 → **四種越權嘗試**
→ 刪除測試帳號，共 14 項。

安全規則改壞了不會有任何錯誤訊息，只會變成「所有同事互相看得到訓練紀錄」。
**這種 bug 只有主動去撞才發現得到**，所以它必須是一支腳本，不是一次性的檢查。

## 2026-08-21｜D028 改為強制登入（推翻 D025 的一項設計決定）

使用者要求移除「先不要登入，直接使用」的出口，全員都必須登入才能使用。

**我原本的主張與為什麼還是照做**

D025 刻意留了這個出口，理由是「純前端的登入守不住任何東西，做成強制關卡
只會在自己壞掉的時候把所有人鎖在外面」。這個技術判斷沒有變。

但使用者的目標不是存取控制，而是**讓每位夥伴的訓練紀錄都跟著人跑**——
留一個出口就會有人一直按它，然後換手機時發現紀錄不見了。
這是產品決定，不是技術決定，而且理由站得住腳。**已明確告知代價後照做。**

**容易漏掉的地方：舊旗標**

只把按鈕拿掉是不夠的。按過那顆按鈕的人，瀏覽器裡留著
`aicoach.noacct = '1'`，而 `boot()` 原本會讀它——**這些人會繼續繞過登入頁，
而且他們自己不會知道，我也看不出來**。所以 `boot()` 現在主動
`removeItem` 掉這個舊旗標。

這是「移除功能」時的通則：**功能拿掉了，它在使用者端留下的狀態不會自動消失。**
（同一類錯誤在 D022 出現過一次：加「續命」功能時忘了舊的清除路徑會抵銷它。
這次是反過來——移除功能時忘了舊的持久化狀態會讓它繼續生效。）

**兩個刻意保留的緩衝**

1. **判斷依據是本機存的登入狀態，不是連線檢查。** 斷網時 `acct.user()`
   讀 localStorage 仍然回傳使用者，所以進得去。若改成每次開啟都去驗 token，
   一斷線就等於整個 App 被鎖住。
2. **緊急放行的路徑寫進文件：** 清空 `firebase-config.js` 的 `apiKey` 再 push，
   登入關卡就消失（`configured()` 回 false）。Firebase 或 Google 登入真的出事時，
   這是三分鐘內能讓全隊恢復使用的辦法。雲端資料不會消失。

**順手修的**：`initAuth()` 現在可重複呼叫——清空 `#au-google` 容器、
清掉密碼欄與訊息。不清的話，登出再登入會疊出第二顆 Google 按鈕。

## 2026-08-21｜D029 Gemini 預設 3.5 Flash Lite；Groq 預設 Qwen 27B

使用者要求：Gemini 預設推薦 3.5 Flash Lite；加入 Groq 並預設 Qwen3.8-27B。

Groq 其實**早就在服務商清單裡**，缺的只是模型偏好。

**不寫死模型 ID**

`_rank()` 是拿服務商回傳的即時清單去比對模式，沒命中就往下一個模式退。
所以用 `/^qwen\/qwen[\d.]*-?27b$/i` 而不是寫死 `qwen/qwen3.8-27b`——
寫死的話，模型哪天改名或下架就會挑到一個不存在的東西。

**查證的過程本身是個教訓**

Groq 的官方文件頁只列到 `qwen/qwen3.6-27b`，我因此告訴使用者「沒有 3.8 版」。
**錯了**——拿到金鑰後打 `/models` 才發現 3.8 明明就在，是文件過期。

> **服務商的文件是二手資料，`/models` 才是一手的。** 能打 API 就別讀文件。

**順手修的：同模式命中多個時，選版本較新的**

原本 `by()` 是照服務商清單的順序取，等於「誰先出現誰贏」——那是任意的，
而且服務商上架新版時會默默繼續用舊的（3.6 與 3.8 都符合同一個模式，
就一直停在 3.6）。改成同模式內按版本號降冪排序。
寫死完整 ID 的模式只命中一個，不受影響——那些是實測結論，不該被動到。

**實測結果（Groq + Qwen 3.8-27B）**

| 項目 | 數字 |
|---|---|
| 建立客戶 | 2.4 秒 |
| **角色扮演每回合** | **0.66～0.77 秒**（Gemini 是 1.1～1.5 秒） |
| 免費額度 | **每分鐘 8000 tokens**、每日 1000 次請求 |

速度是目前最快的。但 8000 TPM 很緊：建立客戶輸出上限 4000、評分上限 8000，
**評分一次就會超過整分鐘的額度**。

關鍵發現：**Groq 的額度是「每個模型各自計算」**，所以撞到 429 之後
降級到 qwen3.6-27b 就是一份全新的 8000 額度。既有的降級機制真的在做事，
不用為 Groq 特別處理。

## 2026-08-21｜D030 簡體字用程式層擋，不只靠提示詞

**問題**

`BASE` 提示詞第 5 行就寫著「一律使用台灣繁體中文…不使用簡體字」。
但實測 `qwen/qwen3.8-27b` 照樣寫出「打**扰**」「班**级里**」「**什么必须**」。
對台灣的保險業務夥伴，這是會直接影響信任感的瑕疵。

**這是第幾次了**

提示詞層擋不住的事就必須用程式擋。同樣的結論已經出現過三次：
D011（品牌中立化 → `scrubBrands`）、D012（示範話術洩漏隱私 → `demoLeaksPrivateInfo`）、
D021（人設出現後設用語 → `scrubMeta`）。這次是第四次。
**「我已經在提示詞裡寫了」從來不算防護。**

**做法：`docs/engine/zhtw.js`，接在 Gateway 的輸出端**

擋在 `generate()` 裡，六大功能一次涵蓋（演練回覆、人設、示範話術、評分、教練對話）。

刻意只做「一對一、不會有歧義」的字，約 700 組。
**一字多形的（里／裡、干／乾／幹、了／瞭）故意不轉**——
把「公里」轉成「公裡」比留著簡體字更糟。少數高頻歧義字用詞彙規則先處理
（頭髮、理髮、乾淨、幹嘛…），其餘留給提示詞層。

對照表用「成對排列」而不是兩條平行長字串：平行字串少一個字，
後面全部對錯位而且看不出來。成對寫法加上「總長必須是偶數」的檢查，
**當場就抓到我貼進去的一個損毀字元**。

**我自己踩的坑：型別不符 → 轉換靜默失效**

第一版寫成 `const r = toTW(await this._call(...))`。但 `_call()` 回傳的是
`{ text, ms, model }` 物件，`toTW` 收到非字串就原樣回傳——**轉換完全沒生效，
而且不會拋任何錯**。是實測輸出還殘留一個「请」才發現的。

> 這類 bug 的共同點：**函式很寬容，錯了也不吭聲。** `toTW` 對非字串回傳原值

## 2026-08-21｜D031 「加到主畫面」做成按鈕；iOS 只能教，不能代做

使用者要求「在畫面下方加一個按鈕，按了自動在手機、iPad 建立桌面捷徑」。

**先講做不到的部分**

**iPhone／iPad 上沒有任何 API 可以讓網頁自己建立桌面捷徑。**
這是 Apple 的限制，不是這支程式的問題——必須使用者手動按「分享 → 加入主畫面」。
Android／Chrome 則真的可以：`beforeinstallprompt` 攔下來之後 `prompt()`
會跳出系統的安裝視窗，一鍵完成。

所以按鈕的定位是「**做得到就做，做不到就把『按哪裡』講到不會認錯**」。

**原本的東西為什麼不夠**

D023 已經有一張 `#install-card`，但它是「可關閉的提示卡」，
按過「別再提醒」就永久消失，而且 iOS 分支只有一行純文字。
使用者要的是一顆**常駐的按鈕**，而且要真的能用。

**五個分支，每一個都給不同的下一步**

| 情況 | 判斷依據 | 給什麼 |
|---|---|---|
| Android／桌面 Chrome | `beforeinstallprompt` 已觸發 | 直接 `prompt()`，一鍵安裝 |
| **LINE／FB／IG 內建瀏覽器** | UA 含 `Line/`、`FBAN`、`Instagram`、`MicroMessenger` | 先教怎麼換到系統瀏覽器 |
| iOS 但不是 Safari | UA 含 `CriOS`／`FxiOS`／`EdgiOS` | 說明只有 Safari 能裝 |
| iPhone Safari | `/iPhone|iPod/` | 分享鍵在**最下方** |
| iPad Safari | `/iPad/` 或 `MacIntel` 且 `maxTouchPoints > 1` | 分享鍵在**右上角** |

**LINE 那一條是為台灣加的。** 同事之間分享連結十之八九是走 LINE，
而 LINE 的內建瀏覽器**連「加入主畫面」的選項都沒有**。
不處理的話，使用者會照著 iOS 教學一路找不到分享鍵，然後放棄。

**iPad 的分享鍵在右上角，iPhone 在最下方。** 講錯位置比不講更糟。
而 iPadOS 13 之後 UA 自稱 Mac，只能靠 `maxTouchPoints` 分辨。

**把圖示畫出來**

使用者最常認錯的就是「哪個是分享鍵」——iOS 上有「方形加向上箭頭」（分享）
和「圓圈裡的箭頭」（重新載入），長得不像但都是箭頭。
所以教學裡直接內嵌 SVG 畫出分享圖示與「加入主畫面」的方框加號圖示，
並明寫「不是圓圈裡的箭頭」。

**已安裝就不再出現**

`display-mode: standalone` 或 `navigator.standalone` 為真時按鈕隱藏，
`appinstalled` 事件也會重新判斷一次。裝好的 App 裡還放一顆
「加到主畫面」只會讓人以為沒裝成功。

順帶補上標準的 `<meta name="mobile-web-app-capable">`——
`apple-mobile-web-app-capable` 已被標為過時，兩個都留著最保險。

## 2026-08-26｜D032 「加到主畫面」移到登入之前——iOS 的儲存空間是分開的

使用者要分享連結給同事時發現：**必須先用 Google 帳號登入、再輸入 API 金鑰，
才會看到「加到主畫面」的按鈕。** 拿到連結的人第一件想做的事被擋在兩道關卡後面。

**使用者的直覺比我原本的設計對**

我原本把按鈕放在首頁（登入之後），想法是「先確認想用，再決定要不要裝」。
但這在 iOS 上是錯的：

> **iOS 桌面 App 的儲存空間與 Safari 是分開的容器。**
> 在 Safari 登入完再加到桌面，從桌面圖示開啟後 `localStorage` 是空的，
> 還是要重新登入一次。

也就是說「先登入再裝」不只是多一道手續，而是**白做一次**。
「先裝再登入」才是唯一不浪費的順序。

**做法**

按鈕從單一 `id` 改成 `[data-install]`，三個畫面各一顆
（註冊／登入、API 金鑰、首頁），`syncInstallBtn()` 一次處理全部，
點擊改用事件代理。**邏輯只有一份**，不是複製三次。

`show()` 每次換畫面都同步一次可見性（原本只在首頁同步，
換成三顆之後那樣寫會讓另外兩顆永遠不出現）。

註冊頁上按鈕放在**最上面**，下面接一條「或先登入使用」的分隔線——
拿到連結的人第一眼就看到它，但主動作（登入）仍然明確。

**這個改動引入的新風險，順手擋掉**

既然現在鼓勵「先裝再登入」，就會有更多人在 iOS 桌面 App 裡按 Google 登入。
而 Google 的登入元件在某些環境（iOS standalone、App 內建瀏覽器）
**會靜靜地不渲染、也不報錯**——使用者就卡在死路上。

加了一個 6 秒偵測：容器裡沒有任何子元素就隱藏它，並明講
「這個環境無法使用 Google 登入，請改用下方的 E-mail」。
E-mail 登入是純 REST，不需要彈出視窗，在任何環境都能用。

**仍未驗證**：iOS 桌面 App 裡 Google 登入到底成不成功，
我沒有真機可測。若失敗，E-mail 是可用的退路，偵測也會把話講清楚。

## 2026-09-29｜D033 評分失敗不再弄丟整場演練（A1）

**原本的問題（三件事疊在一起）**

1. `finish()` 在呼叫評分**之前**就把 `S.sessionId` 清掉
2. `evaluate()` 一開始就把狀態改成 `EVALUATING`，失敗也不改回來
3. 客戶主動結束通話時 `forget()` 把 session 從 `sessionStorage` 刪掉，
   而「接回中斷的演練」只認 `ROLEPLAY` 狀態

結果：模型逾時或額度用完，**練了十分鐘的逐字稿直接消失**，只跳一個 toast 回首頁。
Groq 每分鐘 8000 tokens、評分單次上限 8000——這條路並不罕見。

**做法**

- 通話結束後仍保存 session，**只有評分成功才刪除**
- 評分失敗時狀態退回 `COMPLETED`（對話已結束、待評分），不是 `ROLEPLAY`
- 等待畫面在失敗時換成「評分沒有完成」＋原因＋「重新評分」／「放棄這場」
- 首頁多一種接回：「完成上次演練的評分」——評分失敗後直接關掉 App 也救得回來
- 金鑰失效（`e.auth`）時**不呼叫 `logout()`**：它會 `abort()` 把逐字稿一起丟掉。
  改成只清金鑰、回登入頁，重新登入後首頁可以完成評分。
  （原本這條路直接 `return`，使用者會卡在轉圈畫面——那是另一個舊 bug）

**驗證**：單元測試 8 項（換回舊版 `session.js` 時 2 項失敗）；
瀏覽器實測兩條恢復路徑（原地重試、關掉 App 重開）。

## 2026-09-29｜D034 帳號失效要真的登出（A2）

`token()` 原本把「沒網路」和「refresh token 被撤銷」當成同一件事，都保留登入狀態。
管理者在後台停用某位同事之後，他的 App 仍判定已登入、照常能用，
只是同步永遠靜默失敗——**他的紀錄從此不會出現在報表裡，而且沒有人會發現**。

**分成兩種處理**：沒網路／逾時／5xx → 保留（離線照常可用）；
400／401／403 → 登出。另外同時有多處要 token 時只送一次更新請求，並加上 20 秒逾時。

**同一處還有第二個謊報**：`pull()` 拿不到 token 時回傳 `null`，
但 `syncNow()` 照樣往下走、最後把徽章設成「**已同步**」——
離線或帳號失效時都在說謊。現在會區分「帳號失效」與「暫時連不上」。

**帳號在使用途中失效**：不在演練中硬切畫面（練到一半被踢出去太粗暴），
在下一次回到首頁時由 `show('home')` 這個單一把關點擋下。

**驗證**：瀏覽器實測時，我注入的假帳號（refresh token 是亂寫的）
被**真的 Firebase 回 400**，App 正確判定失效並登出——不是只有模擬測試過。

## 2026-09-29｜D038 客戶的聲音改用 Gemini 真人語音；內建朗讀也修掉機械感

使用者回報：對練都順，但語音「機械感很重」。

**機械感有兩個來源，一個是我們自己造成的**

1. **在逗號切段**。「嗯，我知道，不過我最近比較忙」被拆成三段分別朗讀，
   每段都被當成完整句子——每個逗號都變成句尾降調＋停頓，聽起來像在唸清單。
   當初這樣切是為了讓第一個字早點發聲，代價是整句的語調全毀了。
2. **人設隨機給音高 0.8～1.2**。瀏覽器改音高是粗糙的訊號處理，偏離 1.0 就更像機器。

修法：只在句尾（。！？）切段；音高固定 1；語速限制在 0.9～1.15。
這是退回內建朗讀時的那條路，所以即使用了真人語音也要修。

**另一個來源是內建朗讀本身的天花板**——而使用者的 Google AI Studio 金鑰
本來就能用 Gemini 的語音合成模型，不需要另外申請服務。

**先做樣本讓使用者聽，而不是先寫程式**

用使用者的金鑰產生三段樣本（男聲輕量版／標準版、女聲）。
「口音像不像台灣人」是我沒辦法判斷的事，只有他能聽。
使用者確認口音可以，選了輕量版（`gemini-3.8-flash-lite-tts`，男 Charon、女 Aoede）。

**做樣本時踩到的三個坑（都寫進 `engine/tts.js` 的註解）**

1. **語氣指示會被唸出來**。在台詞前加「用忙碌但客氣的語氣說：」，音檔從 6.5 秒變 9.2 秒；
   讓另一個 Gemini 模型聽錄音轉成文字，開頭就是「忙碌但客氣的語氣說…」。
   英文指示更糟（16.2 秒）；系統指示這個模型不支援（400）。
   → **只送純台詞**。語氣靠台詞本身的口語詞（喔、嗯、……）與聲線。
   用「音檔長度」當初步判斷、再用轉錄確認——光看長度無法確定是講慢了還是多唸了字。
2. 非串流回的是**完整 WAV**，串流回的是**原始 PCM**（`audio/l16; rate=24000`）。
   第一版我對 WAV 又包了一層檔頭，會在開頭多一聲「喀」。
3. 串流事件用 **`\r\n` 分隔**，只認 `\n\n` 會一段都解析不到。

**延遲（實測）**

| | 第一段聲音 | 整段產生完 | 音檔長度 |
|---|---|---|---|
| 輕量版 36 字 | 0.99 秒 | 2.3 秒 | 6.8 秒 |
| 標準版 36 字 | 1.32 秒 | 3.8 秒 | 7.1 秒 |

產生速度比播放快，所以邊收邊播不會斷。每回合約多 0.8 秒（文字 1.1＋語音 0.9）。
瀏覽器實測（真的滑鼠點擊觸發）：第一段聲音 1.09 秒、99 段、沒有退回內建朗讀。

**播放：Web Audio 排程**

每段只有約 70ms。先累積 0.25 秒再開始播（避免開頭因網路抖動斷音），之後一段接一段
排進時間軸——測試裡相鄰兩段的間隙是 0.00ms。「播完」用時間軸計算，
不依賴 `onended`（被 `stop()` 時各瀏覽器行為不一）。

**所有失敗都退回內建朗讀，但「被打斷」不算失敗**

用一個 `speakTok` 分辨：每次朗讀或打斷就 +1。雲端路徑還沒出聲就失敗 → 退回內建；
使用者在客戶講話時插話（點麥克風）→ 停止播放，**不能**再用內建把同一句念一次。
失敗冷卻：429 → 10 分鐘、403／404 → 24 小時、連續兩次其他失敗 → 3 分鐘，
避免每句都先撞一次雲端再退回，讓每句多等好幾秒。第一段聲音 4 秒沒來就放棄。

**我無法驗證、但先處理掉的 iPhone 風險：靜音開關**

iOS 上 Web Audio 的聲音在**靜音開關打開時會被消音**，內建朗讀不會。不處理的話，
手機切靜音的同事會「聽不到客戶講話」，而且不會有任何錯誤訊息。
播放期間把 `navigator.audioSession.type` 切成 `playback`，播完切回——
需要 Safari 16.4 以上，不支援的環境什麼都不做。這一條**必須在實機上確認**。

**沒做的：Gemini Live 即時語音對話**

最像真人（直接聽、直接用聲音回），但模型自己決定何時開口，會跟兩個核心設計衝突：
合規檢查無法在模型回答前攔下違規話術；信任度、隱藏需求、結束條件都靠程式每回合判斷。
等這次的真人語音用一陣子再評估。

**測試**：規則層 84 → 98 項。換回舊版 `voice.js` 時新測試失敗 8 項，
連「逗號切段」都印出舊的樣子「嗯， | 我知道， | 不過我最近比較忙。」。
其中「音高固定」一開始在舊版也通過——因為測試沒給音高，舊版預設也是 1，
等於沒測到東西。改成真的給 1.2 之後，舊版才正確地失敗。

## 2026-09-29｜D041 理賠諮詢改成「客戶的狀況 → 客戶的保單 → 分析」

使用者的觀察：實際情境是客戶打電話來問「這個病有沒有賠、賠多少」。
業務員先知道客戶和他的狀況，才去看客戶有哪些保單。原本的流程從「上傳條款」開始，順序反了。

看程式時另外找到三個會影響準確度的缺口：
1. 一次只能選一張條款——客戶通常有好幾張（實支實付、日額、癌症、意外）。
2. 不知道客戶保了多少——條款只寫「保險金額的 2 倍」，算不出金額。
3. 判斷理賠的關鍵資訊（天數、手術、門診或住院、自費金額、發病日）全靠業務員自己想到要打。

**使用者決定照建議做：**多張保單、保額欄位、記住客戶的保單、可以直接回覆客戶的話術。

**流程**
- ① 客戶的狀況：稱呼／年齡／性別（選填）、狀況類別（可複選）、客戶怎麼說；
  選了「住院」才出現天數，選了「手術」才出現手術名稱與門診／住院；自費金額、發病日期選填。
- ② 客戶的保單：勾選多張（最多 5 張），每張填投保計劃／保額、生效日；可以在這一步直接上傳，上傳完自動勾起來。
- ③ 分析：合計 → 可以這樣回覆客戶（可複製貼到 LINE）→ 各保單明細 → 還需要問客戶 → 要準備的文件。
  下方輸入框補充客戶的回答，會重新分析整個案件；「修改」回到第一步，資料都還在。

**一張保單一次呼叫，平行進行，最後由程式彙整。**
每張各帶自己的條款原文，不把好幾份條款塞進同一次呼叫互相干擾。代價是勾 3 張就是 3＋1 次呼叫
（最後一次寫回覆話術）。一張失敗不拖垮其他張，全部失敗才往外拋錯。

**金額由程式算（`calcAmount`），模型只給計算要素。**
定額給付：每單位金額 × 倍數 × 次數，有上限取上限；實支實付：實際支出與上限取小。
缺任何一個必要數字就不算，畫面改顯示條款的給付方式。
合計只加「有試算金額、且不是『不確定』」的項目，另外標出沒算進去的有幾項。
生效日到發病日的天數也由程式算好給模型判斷等待期。

**實測踩到的：模型會自己補一個「倍數 1」。**
條款寫「依手術費用表所列倍數」但沒有附表，模型把 multiple 填 1，算出「手術費用 1,000 元」，
還被加進合計、寫進回覆客戶的話術裡——一個完全沒有根據的數字，差點直接講給客戶聽。
兩層都修：提示明講「要查表但沒有表時寫 null，不可自己填 1」；程式把「沒給這個欄位」（當 1）
和「明確寫 null」（查不到→不算）分開。修正後手術費用顯示給付方式、不進合計。
**教訓：「預設值」在金額計算裡很危險——`null` 當成 1 等於替模型補了一個它沒說的數字。**

**回覆話術的保險絲**：只給程式算好的項目與金額，不得產生新數字；
回覆裡沒有「核定／為準」的字樣就由程式補上一句「以保險公司核定為準」。
回覆話術產生失敗時，其餘分析照常顯示。

**個資**
- 「記住這位客戶」只存稱呼＋哪幾張保單＋保額／生效日，存在這支手機（`aicoach.clients`），
  不在雲端同步範圍（同步只有訓練紀錄與偏好設定）。**病況一律不存**，只用在這次分析。
- 取消勾選「記住」再分析，會把這位客戶從手機上移除。
- 畫面上明講：分析時內容會送到使用者自己的 Google AI 帳號處理。

**移除**：舊的單一條款對話（`/claim/ask`、`claimAdvice`、`claimPrompt`）、文件頁的「選擇保單條款」模式與「換條款」按鈕。

**測試**：規則層 115 → 144 項（1o 節：試算、等待期天數、狀況描述、部分失敗、合計規則、話術保險絲）；
第 5 節改成真的呼叫模型走新流程，並檢查「條款沒附手術倍數表時不自己編金額」。

- Google 的「今天用完」並不一致：回了每天上限之後，下一次又成功過。
- 查證時用掉使用者當天約 20 次語音額度——應該先問再做，已向使用者說明。

**討論過、沒採用的**
- Hugging Face：每位學員要再申請一個帳號與金鑰（正是使用者想避免的），免費帳號每月只有 0.1 美元額度。
- 手機上直接跑語音模型：要下載 80～300MB、手機跑很慢、能跑的小模型都是大陸腔。
- 由豪老師統一付費的語音服務：體驗最好，但使用者目前不考慮付費，先擱著。
- 使用者一度以為三個模型要三把金鑰——**同一把金鑰就能用所有模型**，學員不用多申請任何東西。

**做法（使用者確認 ①～⑤）**
1. `TtsRotator`（`engine/tts.js`）：輕量版 → 標準版 → 3.1 版輪流，學員感覺不到。
   四個聲線（客戶 Charon／Aoede、教練 Sadaltager／Sulafat）在三個模型上都實測過。每天約 10 句 → 約 30 句。
2. 分清楚限制：`ttsError` 從 details 解析 `quotaId`（PerMinute／PerDay）與 `retryDelay`。
   - 這一分鐘用完 → 依 Google 給的秒數暫停那個模型、換下一個。
   - 今天用完 → 暫停 30 分鐘再試（因為 Google 的判定不一致，整天鎖死會浪費額度）。
   - 403／404 → 一天內跳過；503 → 暫停 1 分鐘；網路錯誤 → 不換模型，交給 `voice.js`。
   - 已經開始出聲才出錯 → 不換模型重唸（否則同一句會聽兩次）。
   - 狀態存在手機（`aicoach.ttsq`），重開 App 不會重撞。
   - 全部都不能用時，錯誤帶 `retryAt`；`voice.js` 照它的時間恢復，不再自己猜 10 分鐘。
3. 三個模型今天都用完 → 跳出說明（每天一次）：今天的免費真人語音用完了、幾點恢復（`nextPacificMidnight`：
   美西半夜＝台灣下午 3 點，冬令 4 點；已過重算時間就說「明天」）。AI 對話照常。
4. 教練聲音的試聽改成事先錄好的 MP3（`docs/audio/`，各約 35KB），不花學員的額度。
5. iPhone 在同一個說明裡教下載「美佳」加強版內建語音，讓備援的聲音好聽一點。
